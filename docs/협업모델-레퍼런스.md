# 협업 모델 레퍼런스 — 이론을 함께 만드는 레포들의 일하는 방식

> 이 프로젝트의 협업 방식은 다음 다섯 패턴에서 배웠다. "각자 자기 분야를 얹어 확장하되, 충돌 없이 기록을 남긴다"가 목표다.

## 다섯 패턴

| 패턴 | 대표 | 핵심 일하는 방식 | 우리 적용 |
|------|------|----------------|----------|
| RFC 프로세스 | Rust·React RFCs, Kubernetes KEP, Python PEP, TC39 | 변경 제안을 PR로 → 토론 → 상태머신 → 합의 후 머지 | `rfcs/` |
| 원칙 선언 | 12factor.net, 12-factor-agents, Heroku | 번호 매긴 원칙 N개, 각 1장, 이슈·PR로 개선 | 참조 카탈로그·`spec/00-principles` |
| 결정 기록(ADR) | architecture-decision-record | 결정마다 1파일(맥락·결정·근거·결과) 누적, supersede | `decisions/` |
| 큐레이션(Awesome) | sindresorhus/awesome | 엄격한 기여 가이드, 항목 PR + 큐레이터 리뷰 | `references/methods/` |
| 지식 가이드 협업 | system-design-primer, Prompt-Engineering-Guide, og-aws | 섹션별 기여·번역, 메인테이너 큐레이션 | `modules/`·`docs/` |

## 우리가 깐 판

- **`rfcs/`** — 방법론·구조의 큰 변경은 여기서 제안·합의(상태머신 Draft→Accepted→Implemented).
- **`decisions/`** — 주요 결정을 ADR로 보존(플랫폼·공개모델·명세우선 등).
- **`BACKLOG.md`** — 앞으로 채울 자리를 미리 등재. 멤버가 골라 가져감(do-ocracy).
- **`references/methods/`** — 검증된 방법론을 미리 깔아두고 같은 양식으로 확장.

## 일하는 흐름 요약

1. 작은 변경(카드 채우기·오타): 바로 PR.
2. 큰 변경(단계·구조·정책): RFC → 합의 → 머지, 결정은 ADR로 기록.
3. 새로 할 일: BACKLOG에서 가져가 이슈 등록 → 작업 → 리뷰 2인 → 머지.
4. 품질 게이트: 동작 샘플 + 사람 큐레이션 + 문서(회장 강조점).
