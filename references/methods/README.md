# 참조 방법론 카탈로그

> 이 프로젝트는 백지에서 시작하지 않는다. 이미 정립된 방법론들을 **미리 깔아두고**, 우리 통합 라이프사이클이 이들 중 무엇을 어느 단계에 쓰는지 선택·조합한다. 멤버는 자기 전문 방법론을 같은 양식으로 추가(확장)한다.

## 카탈로그

| 방법론 | 유형 | 핵심 | 우리 단계 | 상태 |
|--------|------|------|----------|------|
| [AI-DLC](ai-dlc.md) | 프로세스 | Inception·Construction·Operation, Mob 세션 | 전주기 골격 | 시드 |
| [SDD (Spec-Driven)](sdd.md) | 프로세스 | 스펙=단일 진실, Constitution, ACME | 분석·명세 | 시드 |
| [TDD](tdd.md) | 실천 | 테스트 우선, 환각 억제 | 코딩·검증 | 시드 |

## 유형

- **프로세스(Process)**: 개발 전체를 어떻게 진행하나 (단계·협업·반복)
- **실천(Practice)**: 특정 단계에서 무엇을 어떻게 하나 (테스트·인수조건)
- **아키텍처(Architecture)**: 무엇을 만드나 (시스템 구성·패턴)
- **오픈소스 도구(Tool)**: 참고할 도구·운영 패턴

## 카드 양식 (모든 방법론 공통)

```
# 방법론 이름

> 유형 · 출처

## 핵심 개념        (3~5줄)
## 절차·단계
## 적용 시점·조건·한계   (균형 시각 — 한계도 함께)
## 우리 라이프사이클 매핑   (어느 단계에 어떻게)
## 출처             (1차 출처 우선)
```

## 우리 라이프사이클과의 관계

이 카탈로그는 "정답 하나"를 강요하지 않는다. 같은 단계에 복수의 방법론이 매핑될 수 있고(예: 명세 단계에 SDD와 BDD), 팀·상황에 맞게 선택한다. 우리 통합 라이프사이클 명세(`spec/03-process`)는 각 단계에서 이 카탈로그의 방법론을 인용한다.

## 확장 방법

- 새 방법론은 위 양식으로 `references/methods/{slug}.md`를 추가하고 이 표에 등재한다.
- 자기 산업·도구에 특화된 변형은 카탈로그가 아니라 확장팩(`spec/05-extension`)으로 분리한다.
