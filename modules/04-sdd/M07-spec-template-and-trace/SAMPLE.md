# 완성 예제 — ‘할 일 생성’ 명세와 BDD/TDD 인계

> 자체 교육 예제입니다. [03의 분석 예제](../../03-requirements/M02-template-and-change/SAMPLE.md)와 연결됩니다. 구현 계약의 정본은 기존 [04-spec.md](../../../samples/web-task-system/docs/04-spec.md)이며 아래 표는 그 계약의 해설·추적 보충입니다. S-01~S-03은 이 해설에서 규칙을 찾기 위한 표식이고 새로운 기능 요구가 아닙니다.

## 1. 기준과 범위

- 요구사항 정본: [03-requirements.md](../../../samples/web-task-system/docs/03-requirements.md), UC-01과 R-01~R-03.
- 결정·가정·미결 입력: 03 해설 D-01~D-03(저자가 설정한 예제 기준), A-01(문자열 입력 제약), Q-04(공백 처리 미결).
- 포함: 제목으로 생성, 초기 상태, 빈 문자열 오류. 제외: UI·DB·인증·목록·상태 변경·마감일.
- 시스템 경계: `createTodo` 함수. 웹/API 서버가 아닙니다.
- 검토 상태: 작성된 교육 예제. 실제 프로젝트 승인 근거는 없습니다. 실습자은 본인의 요구와 검토 상태를 넘겨야 합니다.

## 2. 데이터 모델

| 필드 | 타입·허용값 | 필수/초기값 | 제약 | 요구/결정 근거 |
|---|---|---|---|---|
| title | string | 필수, 기본값 없음 | 이번 계약은 `""` 거부. 공백 제거·길이 제한 규정 없음 | R-01, R-03, D-01, D-03 |
| status | `"할 일"`, `"진행"`, `"완료"` 가운데 하나 | 생성 시 ‘할 일’ | 생성 함수는 다른 초기 상태를 입력받지 않음 | R-02, D-02, 기존 모델 |

모델에 다른 상태 값이 존재한다는 이유로 상태 변경 함수를 추가하지 않습니다. ID·생성 시각·담당자도 기존 명세에 없습니다.

## 3. 동작 계약

```ts
createTodo(input: { title: string }): Todo
```

- 호출 전 조건·입력: A-01의 문자열 title. 정적 타입 계약이며 외부 요청의 런타임 검증 기능은 없습니다.
- 정상 출력·호출 후 조건: 입력 제목과 같은 title, status가 ‘할 일’인 객체.
- 오류 조건·형태/메시지: title이 `""`이면 `Error("제목은 필수")`를 던집니다. ‘오류를 반환’이라는 업무 표현을 함수 계약에서는 예외 발생으로 구체화했습니다.
- 부작용·외부 의존: 기존 함수는 객체 반환 또는 예외 발생뿐입니다. 입력 변형·저장·통신은 하지 않습니다.

| 명세 규칙 ID | 조건→관찰 결과 | 관련 요구/결정 | 정상·오류·경계 예 |
|---|---|---|---|
| S-01 | 유효한 문자열 제목 → 같은 title의 Todo | R-01, D-01 | ‘보고서 작성’ → title ‘보고서 작성’ |
| S-02 | 정상 생성 → status ‘할 일’ | R-02, D-02 | ‘보고서 작성’ → status ‘할 일’ |
| S-03 | `""` → ‘제목은 필수’ 오류 | R-03, D-03 | 빈 문자열 → Error. 공백만 있는 문자열은 미결 경계 |

## 4. 기술 선택과 비기능 조건

| 선택/비기능 항목 | 안·이유·대가 또는 측정 기준/방법 | 근거 | 상태·미결·영향 |
|---|---|---|---|
| 함수 경계 | 작은 계약으로 요구→검증 연결을 관찰. 웹 요청 처리는 보여주지 못함 | D-01, 기존 명세 | 예제 기준 |
| 오류 형태 | Error와 메시지로 거부 결과 확인. UI 안내나 HTTP 코드는 별도 계약 필요 | D-03, 기존 명세 | 예제 기준 |
| 문자열 입력 | TypeScript 호출 계약을 사용. `unknown` 입력에 대한 안전성 보장은 없음 | A-01, 함수 시그니처 | 외부 입력 검증은 미포함 |
| 성능·보안·내구성 | 합의된 부하·시간·접근 제어·저장 보장 기준 없음 | 03 비기능 조건 | 이번 실습 범위 밖, 운영 적합성 미검증 |

## 5. 05·06 인계용 추적표

| 요구 ID | UC | 명세 규칙 ID/절 | 인수조건 | 테스트 파일·이름/핵심 단언 | 상태 |
|---|---|---|---|---|---|
| R-01 | UC-01 정상 | S-01, 정본 함수 명세 | ‘제목이 있는 할 일을 만든다’: 제목을 주고 생성 | `test/todo.test.ts` / `제목이 있으면 '할 일' 상태로 생성된다` / title 일치 | 기존 테스트로 확인 |
| R-02 | UC-01 정상 | S-02, status 초기값 | 같은 정상 시나리오: 상태가 ‘할 일’ | 같은 테스트 / `todo.status`가 ‘할 일’ | 기존 테스트로 확인 |
| R-03 | UC-01 오류 | S-03, 빈 title 오류 | ‘빈 제목은 거부한다’: 빈 제목으로 생성하면 오류 | `test/todo.test.ts` / `빈 제목은 거부한다` / `toThrow("제목은 필수")` | 기존 테스트로 확인 |

파일 열기: [인수조건](../../../samples/web-task-system/docs/05-acceptance.feature) · [테스트](../../../samples/web-task-system/test/todo.test.ts) · [구현](../../../samples/web-task-system/src/todo.ts).

**읽는 법:** R-01 행의 title 단언을 코드에서 찾고, 이어 R-02의 status 단언을 찾습니다. 요구는 세 개지만 테스트는 두 개입니다. `toThrow`의 메시지 검사는 거부 동작을 확인하며 실행 시 타입 검증·저장 안전성까지 보장하지 않습니다.

- 05 입력: 명세 정본, R-01~R-03, 정상/오류 입력과 기대 결과, Q-04 보류 경계. 기존 `.feature`는 인수조건 문서이며 현재 `pnpm test`가 직접 실행하지 않습니다.
- 06 입력: 명세와 인수조건, 위 추적표. 새 요구를 추가하면 해당 실패 테스트부터 만듭니다. 기존 성공 테스트 재실행만으로 새로운 TDD Red를 확인했다고 쓰지 않습니다.
- 차단 질문: 이 예제 기준에서는 없음. Q-04는 보류했으므로 공백 거부를 구현하는 근거로 사용할 수 없습니다.
- 실제 검증 명령·결과: [검증 기록](README.md#검증-기록-2026-11-24). 테스트 결과와 사람 검토는 별도입니다.
- 사람 검토 상태·실제 근거: 실제 프로젝트 승인 근거 없음.

## 6. 변경 영향 — 아직 반영하지 않은 연습 제안

| 변경 요구/결정 | 이전→변경 제안 | 영향 | 승인 상태 | 실제 반영·검증 상태 |
|---|---|---|---|---|
| R-03/Q-04 | `""` 거부 → 공백만 있는 제목도 거부 | 03의 경계·UC 오류 흐름 → S-03 입력 정의 → 인수조건 추가 → 새 실패 테스트 → 구현 변경 | 제안 | 미반영 |
| Q-04 추가 질문 | 앞뒤 공백을 그대로 둘까, 제거할까? | S-01 제목 보존 계약, title 단언, 구현 | 미결 | 미반영 |

현재 `if (!input.title)`은 `""`를 거부하지만 `"   "`나 `" 보고서 작성 "`은 그대로 수락합니다. 이 관찰은 공백 허용 요구를 새로 확정한 것이 아닙니다. 경계를 바꿀 때는 거부와 정규화 두 결정을 분리하세요.

## 7. 작성 완료 점검과 실습 확인

모델·동작·오류·범위·미결·추적표가 연결된 예제입니다. 실습자은 빈 양식으로 자기 명세를 만든 뒤, 다음을 스스로 확인합니다.

1. 자신이 쓰지 않은 요구가 명세에 추가되지 않았는가?
2. 인수조건을 읽고 정상/오류 결과를 예측한 뒤 테스트의 실제 단언과 비교했는가?
3. 누락된 검사가 있다면 미검증으로 남겼는가?
4. 다음 단계에서 열어야 할 문서와 검토 상태가 명확한가?

공통 함수 코드의 동작 확인은 웹 앱 완성·모든 도구 실행·실습자 이해 검증과 다릅니다.
