# 양식으로 명세를 쓰고 요구에서 테스트까지 추적하기 가이드

> 검증 기준: Claude Code 2.1.330(모델 Sonnet 5.5), Node.js v24.22.0, pnpm 12.21.0, 2026-11-24. 3장의 요청문과 명령은 이 환경에서 실제로 실행했고, ‘검증 실행에서 본 것’은 그 결과에서 옮겼습니다. AI의 응답은 실행마다 달라집니다.

## 이 단원이 말하려는 것

양식도 도구입니다. 양식을 채우는 것이 목적이 아닙니다. 요구가 명세와 테스트의 기준으로 이어지는지 확인하는 것이 목적입니다. 그래서 물음은 하나입니다. 양식의 칸이 채워졌을 때, 요구가 테스트까지 이어진다는 것을 **무엇을 보고 판단하는가**.

이 과정은 네 가지 원칙으로 답합니다. 1~6단계는 넷 가운데 하나 이상을 연습합니다.

| 원칙 | 이 단원에서는 |
|---|---|
| ① AI는 제안하고, 결정은 사람이 한다 | 양식은 AI가 채웁니다. 요구에 없는 함수 이름이나 오류 형태는 제안으로 남기고, 사람이 답한 기술 선택만 결정으로 기록합니다. AI가 표시한 `[x]`는 사람이 확인한 것이 아닙니다 |
| ② 말이 아니라 실행 결과로 확인한다 | 추적표에 ID가 적혀 있어도 뜻이 맞는지는 문장과 실제 단언을 읽어야 압니다. 작은 사례의 테스트를 직접 실행하고, ‘파일이 있다’와 ‘실행해서 통과했다’를 구별해 적습니다 |
| ③ 맡길수록 절차가 필요하다 | 요청마다 고칠 범위를 정해 맡깁니다. 양식의 구성과 표의 열은 바꾸지 않게 하고, 변경 요청은 반영하기 전에 영향 목록부터 만듭니다 |
| ④ 앞 단계가 뒤 단계의 기준이다 | 요구 ID가 명세 규칙으로, 명세 규칙이 인수조건과 테스트로 이어지는지 따라갑니다. 모듈 05(인수조건)와 모듈 06(TDD)이 빈칸을 추측하지 않게 넘깁니다 |

그래서 3장의 단계는 네 마디로 나뉩니다.

- **맡긴다**: AI에게 하는 요청입니다. AI가 내놓는 것은 제안입니다.
- **확인한다**: 직접 실행하는 명령과 그 출력, 직접 열어 읽는 파일입니다.
- **정한다**: 그것을 보고 사람이 내리는 판단입니다. 받아들일지, 무엇을 뺄지, 다음으로 넘어갈지를 정합니다.
- **넘긴다 (산출물)**: 다음 단계의 기준이 되는 산출물입니다. 커밋 명령도 여기에 둡니다.

단계 첫머리의 **입력**은 앞 단계에서 넘어온 기준입니다. AI에게 맡길 일이 없는 단계(0, 3, 6단계)에는 ‘맡긴다’가 없습니다. 직접 실행하는 명령은 ‘한다’에 두었습니다(0, 4단계). 2단계는 사람이 먼저 답을 정한 다음 AI에게 기록을 맡기므로 ‘정한다’가 ‘맡긴다’ 앞에 옵니다. 해당하는 내용이 없는 마디는 두지 않았습니다. 단계 제목 아래에는 그 단계에서 주로 연습하는 원칙을 적었습니다.

## 1. 요구사항과 명세의 차이

요구사항은 사용자에게 필요한 결과와 제약을 정의합니다. 명세는 그 결과를 구현·검증할 수 있도록 입력·출력·규칙·예외를 구체화합니다. 둘은 종류가 전혀 다른 문서가 아닙니다. 얼마나 자세한지와 맡은 역할이 다릅니다. 도구가 `spec`이라고 이름 붙인 파일에 요구사항이 들어 있기도 하므로 이름보다 내용을 보세요.

예를 들어 R-03 “빈 제목은 거부하고 오류를 반환한다”만으로는 ‘오류를 반환한다’가 오류 값을 돌려준다는 뜻인지 예외를 던진다는 뜻인지 알 수 없습니다. 저장소의 명세는 문자열 `title`을 받아 `""`이면 `Error("제목은 필수")`를 던지는 계약으로 구체화했습니다. 반면 공백 제거, 길이 제한, DB 저장은 기존 요구에 없는 선택입니다. 합의가 필요한 선택은 명세에 확정해 쓰지 않고 질문이나 제안으로 남깁니다.

이 단원에서 SDD는 **명세를 개발의 기준으로 작성·검토·변경하고, 구현과 테스트를 그 기준에 연결하는 방식**을 뜻합니다. 마크다운 문서가 있다고 해서 ‘실행 가능한 명세’가 되지는 않습니다. 저장소의 작은 사례는 명세를 인수조건과 Vitest 테스트로 연결해 일부 동작을 실행해서 검증합니다. 명세 문서를 직접 실행하는 도구는 구성하지 않습니다.

추적성은 어떤 요구를 어느 명세 규칙이 충족하고 어느 검사로 확인하는지를 양쪽 방향으로 찾을 수 있는 상태를 말합니다. 표에 ID가 적혀 있어도 뜻이 맞는지는 문장과 실제 단언을 읽어야 알 수 있습니다.

문자열 타입은 TypeScript로 호출하는 코드에 적용되는 정적 계약입니다. 외부에서 들어온 값을 실행 중에 검사한다는 뜻이 아닙니다.

## 2. 범위와 비기능 조건을 명세에 반영하기

03에서 정한 비기능 요구는 구체적인 조건과 검증 방법으로 연결합니다. 예를 들어 성능 목표가 합의되었다면 부하·측정 지점·허용 기준·도구를 명세합니다. 합의하지 않은 숫자는 채우지 않고, 정해지지 않아서 생기는 영향을 적습니다. 작은 사례의 테스트는 보안과 저장을 다루지 않습니다. 이 테스트가 통과했다고 해서 운영에 쓸 수 있다고 말하지 않습니다.

## 3. 단계별 실습

작업 위치는 자기 실습 폴더입니다. 이 가이드와 양식에서 03, 05, 06은 모듈 03(요구사항), 모듈 05(BDD 인수조건), 모듈 06(TDD)을 가리킵니다. 요청은 Claude Code에 그대로 입력합니다. 1·2·4·5단계의 ‘검증 실행에서 본 것’은 같은 요청을 두 번씩 실행해 얻은 결과입니다. 자기 결과는 문장도 항목 수도 다를 수 있습니다.

### 1단계 — 명세 양식 채우기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다. ④ 앞 단계가 뒤 단계의 기준이다. 제안에 답하는 일은 2단계에서 합니다.

**목적:** 요구를 모델, 동작 계약, 추적표로 구체화한 초안을 만듭니다. 요구가 정한 것과 AI가 제안한 기술 선택을 구별합니다.

**입력:** `requirements.md`, 빈 양식 `spec.md`.

**맡긴다**

```text
requirements.md를 입력으로 spec.md의 빈 양식을 채워 줘. 양식의 구성과 표의 열은 바꾸지 마.
목적은 구현·인수조건·테스트가 따를 계약과 추적표를 만드는 것이다.
요구 ID와 UC를 유지하고 모델, 입력/출력, 정상/오류 규칙, 부작용,
비기능 조건, 범위 제외, 미결을 적어 줘.
요구에서 정하지 않은 기술 선택은 이유와 상태를 붙인 제안으로 구분해 줘.
미결에 임의로 답하거나 승인 근거를 만들지 말고, 확정을 막는 질문을 알려 줘.
추적표에는 05 인수조건 후보와 06 테스트에서 관찰할 결과를 연결하되,
없는 파일·미실행 검사는 작성 예정/미실행으로 표시해 줘.
코드·테스트·다른 문서를 수정하거나 도구 설치·커밋·푸시하지 마.
```

**확인한다**

채워진 `spec.md`를 읽습니다. 요구에 없는데 들어온 것(함수 이름, 식별자, 오류 형태)이 제안으로 표시되어 있는지 봅니다. 요구별 계약을 읽고 정상 입력 하나와 거부 입력 하나의 결과를 예측할 수 있는지 확인합니다.

**넘긴다 (산출물)**

모델, 계약, 명세 규칙, 추적표가 채워진 `spec.md` 초안.

```bash
git status --short        #  M spec.md 한 줄만 나온다
git add -A && git commit -m "docs: 명세 초안"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `spec.md`만 고쳤습니다. 양식의 일곱 절과 표의 열을 유지했습니다.
- 두 번 모두 명세 규칙이 다섯 개(S-01~S-05)였습니다. S-01~S-03을 R-01~R-03에 하나씩 연결하고, 공백만 있는 제목을 미결 규칙으로 따로 두었습니다. 나머지 하나는 달랐습니다. 한 번은 문자열이 아닌 입력을 미결 규칙으로 두었고, 한 번은 ‘거부하면 할 일이 생성되지 않는다’를 R-03에서 끌어낸 규칙으로 두었습니다.
- 요구에는 함수 이름이 없습니다. 두 번 모두 `createTask`라는 이름을 제안으로 적었습니다. 저장소의 작은 사례가 쓰는 이름은 `createTodo`입니다. 이름은 사람이 정할 기술 선택입니다.
- 추적표의 인수조건과 테스트 칸은 두 번 모두 ‘작성 예정’, 상태는 ‘미실행’이었습니다. 검토 상태는 ‘초안’, 사람 검토 근거는 ‘[미제공]’이었습니다.
- 두 번 모두 ‘공백만 있는 제목도 빈 제목인가’를 확정을 막는 질문으로 올렸습니다.
- 두 번 모두 7절의 다섯 항목 가운데 네 개를 스스로 `[x]`로 표시했습니다. ‘인수조건·테스트의 파일과 확인할 결과가 명확하다’는 두 번 모두 표시하지 않았고, 파일이 아직 없고 미결이 남아 있다는 이유를 옆에 적었습니다. `[x]` 표시는 사람이 확인한 것이 아닙니다.

**검토**

- [ ] 요구가 정한 것(초기 상태, 빈 제목 거부)과 AI의 제안(함수 이름, 오류 형태)이 구별되어 있다.
- [ ] 저장, 인증, 화면처럼 요구에 없는 기능이 계약에 들어 있지 않다.
- [ ] 아직 없는 인수조건 파일과 테스트가 ‘작성 예정’, ‘미실행’으로 적혀 있다.

### 2단계 — 기술 선택에 답하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 사람이 정한 기술 선택만 결정으로 기록합니다.

**입력:** 1단계의 `spec.md`.

**정한다**

제안과 질문을 읽고 자기 답과 이유를 정합니다. 정하지 못한 것은 답하지 않고 둡니다.

**맡긴다**

아래는 검증 실행에서 쓴 답입니다. 저장소의 [명세](../../../samples/web-task-system/docs/04-spec.md)와 [SAMPLE](SAMPLE.md)에 적힌 선택과 같습니다. 첫 줄은 그대로 두고 항목은 자기 답으로 바꿔 씁니다.

```text
기술 선택에 대한 내 답은 다음과 같아. 이 답의 범위만 spec.md에 반영해 줘. 결정 주체는 "실습자 본인"으로 적고, 내가 답하지 않은 것은 제안이나 미결로 남겨 줘. 내가 말하지 않은 승인 기록은 만들지 마.
- 시스템 경계는 TypeScript 함수 하나다. 이름은 createTodo이고 { title: string }을 받아 Todo를 돌려준다. 요구가 생성 하나뿐이라 가장 작은 경계를 골랐다.
- Todo의 필드는 title과 status 둘이다. status의 허용값은 "할 일", "진행", "완료"이고 생성할 때는 "할 일"이다.
- 빈 문자열 제목이면 Error("제목은 필수")를 던진다. 요구의 "오류를 반환한다"를 함수에서는 예외로 구체화한다.
- 저장, 통신, 입력 변형은 하지 않는다.
- 공백만 있는 제목과 길이 제한은 아직 정하지 않았다.
```

**넘긴다 (산출물)**

내 답이 결정으로 기록되고, 답하지 않은 것은 제안이나 미결로 남은 `spec.md`.

```bash
git diff --stat           # spec.md만 바뀌었는지 본다
git add -A && git commit -m "docs: 기술 선택 반영"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `spec.md`만 고쳤습니다. 내 답은 ‘실습자 본인 결정’으로 기록됐고, 계약의 이름이 `createTask`에서 `createTodo`로, 오류가 `Error("제목은 필수")`를 던지는 것으로 바뀌었습니다.
- 두 번 모두 공백만 있는 제목은 확정을 막는 미결로 남았습니다. 길이 제한도 미결로 남았습니다.
- 문서의 검토 상태는 ‘초안’ 그대로였습니다. 두 번 모두 ‘실습자 본인의 답을 옮긴 것이며 별도의 검토·승인 기록은 없다’고 적었습니다.
- 두 번 모두 1단계에서 제안했던 식별자(id)를 두지 않는 것으로 정리했습니다. 한 번은 모델 표에서 행을 지우고 ‘채택되지 않음’이라고 적었고, 한 번은 행을 남기고 ‘없음’으로 적었습니다.
- 두 번 모두 ‘입력 변형은 하지 않는다’는 답을 ‘앞뒤 공백도 제거하지 않는다’는 뜻으로 풀어 반영했고, 그렇게 풀었다고 보고에 밝혔습니다. 내 뜻과 다르면 바로잡습니다.

**검토**

- [ ] ‘실습자 본인 결정’으로 적힌 것은 내가 답한 것뿐이다.
- [ ] 검토 상태가 ‘승인’으로 바뀌어 있지 않다.
- [ ] 미결로 남은 질문이 어느 규칙의 확정을 막는지 적혀 있다.

### 3단계 — 예제와 비교하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 개수나 파일 이름이 아니라 범위, 판단 근거, 추적성을 기준으로 자기 명세를 점검합니다.

**입력:** 자기 `spec.md`, [SAMPLE](SAMPLE.md), 저장소의 [명세](../../../samples/web-task-system/docs/04-spec.md).

**확인한다**

아래 표의 순서로 읽습니다. 예제의 함수 이름과 오류 형태는 그 명세의 선택이지 모든 프로젝트의 정답이 아닙니다.

| 볼 곳 | 예제 | 내 명세에서 확인할 것 |
|---|---|---|
| 시스템 경계 | `createTodo` 함수 하나입니다. 웹이나 API 서버가 아닙니다 | 요구에 없는 HTTP 경로, DB 테이블, 로그인이 없는가 |
| 모델 | title과 status 두 필드입니다. 식별자와 생성 시각은 없습니다 | 필드마다 근거가 되는 요구나 결정이 있는가 |
| 오류 계약 | 제목이 `""`이면 `Error("제목은 필수")`를 던집니다 | ‘오류를 반환한다’를 어떻게 구체화했는지 적혀 있는가 |
| 타입과 검증 | 문자열 타입은 정적 계약이고 런타임 검증이 아닙니다 | 정적 타입과 런타임 검증을 구분했는가 |
| 추적표 | R-01·R-02는 시나리오 하나, R-03은 다른 하나에 연결됩니다 | 요구, 시나리오, 테스트의 수를 억지로 맞추지 않았는가 |
| 공백 제목 | 미결로 둡니다 | 정하지 않은 것을 정한 것처럼 쓰지 않았는가 |

**정한다**

7절의 `[x]`는 AI가 표시한 것입니다. 모두 `[ ]`로 되돌린 다음 직접 확인한 항목만 `[x]`로 바꿉니다.

**넘긴다 (산출물)**

예제와 다른 곳과 그 이유를 적은 메모(실습 폴더 밖에 둡니다). `spec.md`를 고쳤으면 `git add -A && git commit -m "docs: 예제 비교 반영"`으로 커밋합니다.

**검토**

- [ ] 예제와 다른 선택마다 이유를 말할 수 있다.
- [ ] 7절의 점검 항목을 직접 확인한 것만 다시 표시했다.

### 4단계 — 요구에서 테스트까지 따라가기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ② 말이 아니라 실행 결과로 확인한다.

**목적:** 완성된 작은 사례에서 요구가 명세, 인수조건, 테스트, 구현으로 이어지는지 직접 확인합니다. 새 기능을 TDD로 만드는 것이 아니라 완성된 코드의 대응을 읽는 연습입니다.

**한다**

git 명령을 실행하던 터미널 창에서 강의 자료 저장소의 루트 폴더로 돌아갑니다. 0단계에서 띄운 Claude Code 창은 5단계에서 다시 쓰므로 그대로 둡니다. 작은 사례를 저장소 밖으로 복사하고 테스트를 실행합니다.

```bash
cp -R samples/web-task-system ~/work/web-task-system
cd ~/work/web-task-system
pnpm install --frozen-lockfile --ignore-scripts
pnpm test                 # Test Files  1 passed (1), Tests  2 passed (2)
pnpm exec tsc --noEmit    # 오류 없이 끝난다
```

**맡긴다**

같은 창에서 `claude`를 실행하고 아래 요청을 입력합니다.

```text
docs/03-requirements.md, docs/04-spec.md, docs/05-acceptance.feature, test/todo.test.ts, src/todo.ts를 대조해 줘.
R-01~R-03이 어떤 명세 규칙·시나리오·테스트 단언으로 연결되는지 설명해 줘.
공백 처리·저장·인증이 무엇을 보장하거나 보장하지 않는지 실제 코드로 확인하고,
파일 존재와 실행 결과를 구별해 줘. 파일 수정·설치는 하지 마.
```

**확인한다**

대응표를 읽은 뒤 `/exit`로 끝내고 `cd ~/work/task-create-spec`으로 돌아옵니다. 작은 사례의 `.feature`에 적힌 조건·실행·결과는 Given·When·Then에 해당합니다.

**넘긴다 (산출물)**

요구에서 구현까지의 대응표와, 이 사례가 보장하지 않는 것의 목록.

**검증 실행에서 본 것 (명령 1회, 요청 3회)**

- 명령은 그대로 실행됐습니다. 테스트 파일 1개에서 테스트 2개가 통과했고 타입 검사는 종료 코드 0이었습니다.
- 요청에서는 세 번 모두 파일을 고치지 않았습니다. 세 번 모두 요구, 명세, 시나리오, 테스트 단언, 구현을 줄 번호와 함께 표로 이었습니다.
- 세 번 모두 R-01과 R-02가 시나리오 하나와 테스트 하나를 함께 쓴다는 것을 짚었습니다. 명세의 ‘명세에 없는 필드는 추가하지 않습니다’를 확인하는 테스트가 없다는 것도 세 번 모두 찾았습니다.
- 세 번 모두 공백만 있는 제목이 거부되지 않는다는 것을 코드에서 읽어 냈습니다.
- 세 번 모두 테스트를 실행하지 못했다고 밝혔고, 코드를 읽어 추론한 것과 실행해 확인한 것을 구별해 적었습니다. 처음 두 번은 가이드의 순서와 달리 `pnpm install`을 하기 전의 사본에서 요청했습니다. 세 번째는 설치를 마친 사본에서 `pnpm test`를 허용하고 요청했는데, Claude가 `npx vitest`와 `node`를 골라 허용한 범위를 벗어났습니다. 대화형으로 따라 하면 이런 명령을 실행해도 되는지 묻습니다.
- `docs/05-acceptance.feature`는 이 패키지에서 직접 실행되지 않습니다. 실제로 실행되는 것은 `test/todo.test.ts`입니다.

**검토**

- [ ] R-01~R-03마다 명세의 해당 줄, 시나리오, 테스트 단언을 찾았다. R-01은 명세의 규칙 목록이 아니라 추적성 표에 있다.
- [ ] ‘파일이 있다’와 ‘실행해서 통과했다’를 구별해 적었다.
- [ ] 이미 완성된 사례의 테스트 통과를 새 변경의 Red 확인으로 적지 않았다.

### 5단계 — 변경 영향 찾기

> 연습하는 원칙: ③ 맡길수록 절차가 필요하다. ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 변경 요청을 반영하기 전에, 그 변경이 명세와 뒤 단계에 주는 영향을 목록으로 만듭니다.

**입력:** 자기 실습 폴더(`~/work/task-create-spec`)의 `requirements.md`와 `spec.md`.

**맡긴다**

요청은 0단계에서 띄워 둔 Claude Code 창에 입력합니다. 4단계에서 연 창에 입력하지 않습니다.

```text
"공백만 있는 제목도 거부해 주세요"라는 변경 요청이 들어왔어. 아직 승인된 변경이 아니야.
requirements.md와 spec.md를 읽고 이 변경이 영향을 주는 모델·계약·인수조건·테스트·구현을 목록으로 만들어 줘.
앞뒤 공백을 제거할지는 별도의 질문으로 나눠 줘.
spec.md의 변경 영향 표에 제안으로만 기록하고, 다른 절은 고치지 마.
```

**확인한다**

영향 목록을 읽습니다.

**정한다**

공백만 있는 제목을 거부하는 것과 앞뒤 공백을 제거하는 것은 서로 다른 결정입니다. `trim()`을 쓰면 두 동작이 한꺼번에 바뀌므로 하나의 결정으로 다루지 않습니다. 받아들일지는 사람이 정합니다.

**넘긴다 (산출물)**

변경 영향 표에 제안이 더해진 `spec.md`.

```bash
git diff --stat           # spec.md 한 파일만 바뀐다
git add -A && git commit -m "docs: 변경 제안 기록"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `spec.md`의 6절(변경 영향)에만 내용을 더했고 다른 절은 고치지 않았습니다. 승인 상태는 ‘제안’, 반영 상태는 ‘미반영’이었습니다. 한 번은 표에 두 줄을 더했고, 한 번은 표에 한 줄을 더하고 그 아래에 영향 목록을 따로 적었습니다(27줄).
- 두 번 모두 모델(필드와 타입은 그대로이고 제약 문구만 바뀜), 계약(오류 조건과 미결 규칙), 인수조건(보류했던 경계 시나리오), 테스트(공백 입력의 단언 추가), 구현(검증식)을 영향으로 들었습니다.
- 두 번 모두 앞뒤 공백 제거를 별도의 질문으로 나눴습니다. 제거하면 ‘반환한 제목이 입력과 같다’는 규칙과 ‘입력을 변형하지 않는다’는 결정이 바뀐다고 적었습니다.

두 변경이 모두 승인되어 인수조건으로 정해진 뒤의 구현 과정은 [모듈 06 단원 M02](../../06-coding-tdd/M02-tdd-rules/README.md)에 있습니다. 그 단원은 별도의 실습 폴더(`todo-app`)에서 ‘공백만 있는 제목 거부’와 ‘앞뒤 공백 제거’를 테스트부터 구현합니다.

**검토**

- [ ] 변경 영향 표의 승인 상태가 ‘제안’이고, 다른 절은 바뀌지 않았다.
- [ ] 공백 거부와 앞뒤 공백 제거가 별도의 질문으로 나뉘어 있다.

### 6단계 — 05와 06으로 넘기기

- [ ] 모델의 각 필드와 정상·오류 규칙이 요구나 명시된 기술 선택에 연결된다.

## 4. 양식의 절마다 판단할 것

3장의 단계에서 명세를 읽고 고칠 때 아래 기준을 씁니다.

**입력으로 쓸 수 있는 것:** 모듈 03의 요구·UC·원요청·결정·가정·미결, 기존 명세·코드·테스트(있을 때), 기술 제약. 작은 사례를 분석할 때는 [요구사항](../../../samples/web-task-system/docs/03-requirements.md)과 [모듈 03 단원 M02의 예제](../../03-requirements/M02-template-and-change/SAMPLE.md)를 함께 읽습니다. 작은 사례의 명세는 [04-spec.md](../../../samples/web-task-system/docs/04-spec.md)이고 이 단원의 [SAMPLE](SAMPLE.md)은 그 해설입니다. 같은 내용을 서로 다른 정본으로 두지 않습니다.

### 기준과 범위 (1절)

요구 ID, UC, 상태를 읽고 이번 명세의 범위를 고릅니다. 사람이 결정한 근거가 없는 것을 ‘승인됨’으로 쓰지 않습니다. 진행을 막는 미결은 질문으로 돌려보내고 그 규칙을 확정하지 않습니다. 진행을 막지 않는 미결도 보류한 이유와 영향 범위를 명세에 남깁니다.

이번 명세의 시스템 경계가 함수, API, 화면 가운데 무엇인지 적습니다. 작은 사례의 경계는 `createTodo` 함수 하나입니다. HTTP 경로, 상태 코드, DB 테이블, 로그인 처리를 요구도 없이 더하지 않습니다.

### 데이터 모델 (2절)

필드 이름, 타입, 허용값, 필수 여부, 초기값을 적고 어떤 요구를 위한 것인지 표시합니다. 작은 사례의 `Todo`는 title과 status뿐입니다. status 타입에 ‘진행’과 ‘완료’가 있어도 생성 함수가 그 상태로 만들거나 상태를 바꾸는 것은 아닙니다.

### 동작 계약 (3절)

호출 전 조건, 입력, 출력, 처리 규칙, 오류 조건과 오류 형태·메시지, 부작용을 적습니다. 정상 입력 하나와 거부 입력 하나를 골라, 계약만 읽고 결과를 예측할 수 있는지 확인합니다. 경계가 미결이면 임의로 채우지 않습니다.

### 기술 선택과 비기능 조건 (4절)

구현 선택에 여러 안이 있으면 요구를 만족하는 이유, 대가, 승인 상태를 적습니다. 예제의 함수 이름과 오류 형태는 그 명세의 선택이지 모든 프로젝트의 정답이 아닙니다. 합의하지 않은 비기능 목표에는 숫자를 채우지 않습니다.

### 05·06 인계용 추적표 (5절)

표를 만들 때 요구가 빠진 행, 근거 없는 명세 규칙, 아직 테스트가 없는 칸을 찾습니다. 요구, 시나리오, 테스트의 수를 억지로 같게 맞추지 않습니다. 경계값이 여럿 필요하면 요구 하나에 테스트 여러 개를 연결합니다.

BDD는 사용 상황과 기대 동작을 인수조건으로 확인하는 단계입니다. Given은 전제, When은 행동, Then은 관찰할 수 있는 결과를 뜻합니다. 인계에는 요구 ID, 정상 입력과 오류 입력, 관찰 결과, 진행을 막는 미결, 검토 상태를 넣습니다. 이미 완성된 사례의 통과하는 테스트를 다시 실행한 것은 Red를 재현한 것이 아닙니다.

### 변경 영향 (6절)

‘공백만 있는 제목 거부’는 R-03의 경계를 바꾸는 변경입니다. 영향 목록은 요구·UC → 명세의 빈 값 정의와 오류 → 인수조건 → 실패하는 테스트 → 구현 순서로 만듭니다. 사람이 변경을 받아들이기로 정한 뒤에 반영합니다. 지금 코드가 공백만 있는 제목을 받아들인다는 사실은 그 동작을 계속 보장해야 한다는 요구가 아닙니다. 기존 계약과, 변경으로 달라질 기존 동작은 확인합니다. 다만 코드에서 본 사실과 요구, 변경 제안은 구별해 적습니다.

## 5. 자주 막히는 곳

| 증상 | 확인하고 고칠 것 |
|---|---|
| 양식의 절이나 표의 열이 바뀌었다 | `git diff`로 확인합니다. `git checkout -- spec.md`로 되돌린 뒤 다시 요청합니다. 마지막 커밋 뒤에 고친 내용이 모두 사라지므로 남길 변경은 먼저 따로 적어 둡니다 |
| 요구에 없는 저장, API, 로그인이 계약에 들어 있다 | 요구 ID를 근거로 대지 못하는 항목은 지우거나 제안으로 내립니다 |
| 추적표에 테스트가 ‘통과’로 적혀 있다 | 이 단계에서는 테스트 파일이 없습니다. ‘작성 예정’, ‘미실행’으로 고칩니다 |
| `pnpm install`이 저장소 루트에서 실패한다 | 루트에는 `package.json`이 없습니다. `samples/web-task-system` 폴더나 그 사본 안에서 실행합니다 |
| Claude Code가 스크립트(python 등)를 실행해도 되는지 묻는다 | 검증 실행의 2단계에서 두 번 모두 먼저 스크립트로 한꺼번에 고치려 했고, 실행되지 않자 편집 도구로 `spec.md`를 직접 고쳤습니다. 거절하고 파일을 직접 고쳐 달라고 해도 됩니다 |
| `cp`가 “No such file or directory”로 실패한다 | 강의 자료 저장소의 루트 폴더가 아닙니다. `ls samples`가 되는 폴더로 이동합니다 |
| `~/work/web-task-system` 안에 `web-task-system` 폴더가 또 있다 | `cp -R`을 두 번 실행한 것입니다. 폴더를 지우고 다시 복사합니다 |
| `git commit`이 “Author identity unknown”으로 실패한다 | `git config --global user.name "이름"`과 `git config --global user.email "메일 주소"`를 먼저 실행합니다 |
