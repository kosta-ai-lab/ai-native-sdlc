# 요구사항에서 구현 검증까지 — SDD 가이드

> 검증 기준: Claude Code 2.1.330(모델 Sonnet 5.5), Node.js v24.22.0, 2026-11-24. 5장의 요청문은 이 환경에서 실제로 실행했고, ‘검증 실행에서 본 것’은 그 결과에서 옮겼습니다. AI의 응답은 실행마다 달라집니다.

## 이 단원이 말하려는 것

SDD 도구는 수단입니다. 도구는 계속 바뀌지만 판단하는 능력은 남습니다. 그래서 이 단원에서는 SDD 도구를 설치하지 않고, 일반 파일 작업으로 판단 과정을 직접 연습합니다. 물음은 이것입니다. 요구사항을 명세, 설계, 작업, 코드로 옮길 때 단계마다 **무엇을 정하고 어떻게 확인하는가**. 문서가 생긴 것으로 끝내지 않고 브라우저에서 실행 결과를 확인합니다.

이 과정은 네 가지 원칙으로 답합니다. 1~6단계에서는 단계마다 넷 가운데 하나 이상을 연습합니다.

| 원칙 | 이 단원에서는 |
|---|---|
| ① AI는 제안하고, 결정은 사람이 한다 | `spec.md`, `design.md`, `tasks.md`와 코드는 AI가 씁니다. 새로 제안된 결정을 받아들일지, 어느 작업 묶음부터 구현할지, 변경을 어떤 정책으로 반영할지는 사람이 정합니다 |
| ② 말이 아니라 실행 결과로 확인한다 | AI가 작업을 완료로 표시해도 테스트를 직접 실행해 출력을 읽고, 브라우저에서 화면, 저장, 키보드 동작을 확인합니다 |
| ③ 맡길수록 절차가 필요하다 | 명세, 설계, 작업 분해, 구현을 한꺼번에 맡기지 않습니다. 한 단계의 결과를 읽고 고친 뒤 다음으로 가고, 구현은 한 묶음씩 맡깁니다 |
| ④ 앞 단계가 뒤 단계의 기준이다 | 요구사항은 명세의 기준이고, 명세는 설계의 기준이며, 설계는 작업의 기준입니다. 검토한 네 문서는 구현과 검증의 기준이 되고, 변경할 때는 명세가 기준이 됩니다 |

그래서 5장의 단계는 네 마디로 나뉩니다.

- **맡긴다**: AI에게 하는 요청입니다. AI가 내놓는 것은 제안입니다.
- **확인한다**: 직접 열어 읽는 파일과 직접 실행해 읽는 출력입니다. 1~4단계에서 실행할 명령은 ‘넘긴다’의 명령 블록에 있습니다. 5단계의 명령은 SAMPLE 5장에 있습니다. 6단계에는 새 명령이 없고 앞 단계의 명령을 다시 씁니다.
- **정한다**: 그것을 보고 사람이 내리는 판단입니다. 받아들일지, 어느 작업 묶음부터 구현할지, 변경을 어떤 정책으로 반영할지를 정합니다.
- **넘긴다 (산출물)**: 다음 단계의 기준이 되는 산출물입니다. 바뀐 파일을 보는 명령, 테스트 실행 명령, 커밋 명령을 여기에 모았습니다.

단계 첫머리의 **입력**은 앞 단계에서 넘어온 기준입니다. AI에게 맡길 일이 없는 단계(0, 5단계)에는 ‘맡긴다’가 없습니다. 0단계는 준비 명령을 직접 실행하므로 ‘한다’를 씁니다. 6단계는 영향을 찾게 한 다음 정책을 정해 고치는 일을 다시 맡기므로 ‘맡긴다’가 두 번 나옵니다. 해당하는 내용이 없는 마디는 두지 않았습니다. 단계 제목 아래에는 그 단계에서 주로 연습하는 원칙을 적었습니다.

## 1. 요구·명세·설계의 관계

‘완료 필터에서도 남은 개수를 알 수 있어야 한다’는 요구를 읽고 곧바로 화면을 만들면, 표시된 목록만 세는 실수를 할 수 있습니다. 같은 요구를 데이터와 행위로 풀어 쓰는 과정이 필요합니다.

**요구사항**은 이해관계자가 느끼는 필요, 시스템이 갖춰야 할 능력이나 성질, 또는 그것을 문서로 나타낸 것입니다. **명세**는 대상의 성질을 일정 기준에 따라 체계적으로 기술한 것입니다. 따라서 요구사항 문서도 명세의 한 종류이며, ‘요구사항에는 자세한 내용이 없고 명세에만 있다’라고 나눌 수는 없습니다. IREB [CPRE 용어집의 Requirement·Specification·Requirements specification](https://cpre.ireb.org/en/downloads-and-resources/glossary)이 이 관계를 설명합니다.

이 실습에서는 역할을 나눠 읽기 위해 `requirements.md`에 사용자 목적·범위·인수조건을, `spec.md`에 데이터와 동작의 계약을, `design.md`에 그 계약을 지킬 구조와 선택 이유를 둡니다. 이는 이 수업의 파일 구분이지 공인된 유일한 문서 체계가 아닙니다. 설계도 명세에 포함될 수 있고, 다른 도구에서는 이름이 다를 수 있습니다.

예를 들어 ‘전체 미완료 수를 표시한다’는 요구는 ‘필터 전 목록에서 미완료를 세며, 필터 변경은 그 수를 바꾸지 않는다’는 행위 계약으로 구체화됩니다. 설계에서는 전체 목록을 보관하는 상태와 필터 결과를 분리하고, 같은 전체 목록에서 표시 목록과 개수를 각각 계산하도록 선택할 수 있습니다. **요구를 더 길게 옮겨 적는 것이 아니라 잘못 구현할 수 있는 차이를 없애는 과정**입니다.

## 2. SDD가 문서 작성에서 끝나지 않는 이유

GitHub Spec Kit 저자의 [Specification-Driven Development, Core Principles·Workflow](https://github.com/github/spec-kit/blob/main/spec-driven.md)는 명세를 구현의 중심 입력으로 두고, 계획·코드·테스트를 그 명세에서 도출하며 실제 결과를 다시 명세 개선에 반영하는 관점을 제시합니다. 원문은 명세가 동작하는 시스템을 생성할 만큼 정밀해야 한다는 뜻으로 ‘실행 가능한 명세’라고 씁니다. 이 실습에서는 이 말을 ‘Markdown 파일을 저장하면 저절로 올바른 앱이 된다’로 읽지 않습니다. 명세에 적은 조건을 구현과 검증이 계속 사용한다는 뜻으로 좁혀 적용합니다.

이 글은 **도구 저자의 방법론 제안**이며 국제 표준이나 생성 코드의 정확성 보증이 아닙니다. 문서에 적은 조건과 AI 구현이 어긋날 수 있으므로, 실제 테스트와 사용으로 비교해야 합니다. AI가 작업을 완료로 표시했어도 저장에 실패했을 때 데이터가 사라진다면 그 요구는 충족되지 않은 것입니다.

NASA의 소프트웨어 공학 요구사항 [NPR 7150.2D 4.1.7(SWE-055)](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter4)은 요구사항 validation의 목적을 ‘소프트웨어가 고객의 환경에서 의도한 대로 동작하도록 보장하는 것’으로 적습니다. 이 실습은 여기서 한 걸음 더 나아가, 문서 검토만으로는 사용자 환경의 동작을 확인할 수 없다고 봅니다. 그래서 자동 테스트로 핵심 로직을, 브라우저로 화면·저장·키보드 동작을 나누어 확인합니다.

## 3. 명세에서 함께 볼 세 관점

### 모델 — 서로 구별할 정보

모델은 목적을 위해 필요한 대상을 추려 표현한 것입니다. 이 앱의 Todo는 `id`, `text`, `completed`를 갖도록 선택할 수 있습니다. `id`는 같은 제목의 두 항목을 구별하고, `text`는 제목, `completed`는 완료 여부입니다. 필터는 항목 속성이 아니라 화면이 무엇을 보여 줄지 정하는 별도 상태입니다.

모든 값을 저장할 필요는 없습니다. 남은 개수와 표시 목록은 전체 목록에서 계산할 수 있으므로 별도로 저장하면 서로 어긋날 수 있습니다. ‘전체 목록 → 필터 적용 → 표시 목록’과 ‘전체 목록 → 미완료 집계 → 남은 개수’는 같은 원본을 두 방식으로 읽는 관계입니다. 이 화살표는 데이터 의존 관계이며 시간 순서나 네트워크 호출을 뜻하지 않습니다.

### 행위 — 조건에 따라 달라지는 것

상태가 바뀌는 사건과 바뀐 뒤 관찰할 결과를 적습니다. 아래 표에서 각 행은 현재 상태에 행동 하나를 적용했을 때의 결과를 뜻합니다.

| 현재 조건 | 행동 | 성공 후 결과 | 실패 후 결과 |
|---|---|---|---|
| 정상 목록, 유효한 제목 | 추가 | 새 미완료 항목 저장 후 목록·개수 갱신 | 저장 실패면 기존 목록 유지·오류 안내 |
| 지정 항목이 미완료/완료 | 완료 전환 | 그 항목만 반대 상태로 저장 후 다시 표시 | 저장 실패면 이전 완료 상태 유지·오류 안내 |
| 필터가 전체/진행 중/완료 | 필터 변경 | 표시 목록만 변경 | 저장 작업이 필요 없음 |

추가가 성공해도 완료 필터에서는 새 미완료 항목이 보이지 않습니다. ‘추가 성공=화면에 한 행이 보인다’라고만 명세하면 W-01과 W-05가 충돌합니다. 이처럼 여러 요구를 같은 장면에서 함께 읽는 것이 행위 명세의 역할입니다.

### 제약과 불변조건 — 계속 지켜야 하는 것

제약은 가능한 해법을 제한하고, 불변조건은 정상 동작 중 계속 유지해야 하는 성질입니다. 이 예제에서 외부 서버 전송 금지는 제약이고, ‘남은 개수는 전체 미완료 수와 일치한다’는 불변조건입니다. 앞뒤 공백 제거 후 길이 검사, ID 유일성, 실패 시 이전 상태 유지도 명세와 시험에서 확인할 조건입니다.

구현에 사용할 JavaScript의 `String.length`는 사람이 보는 글자 수와 다를 수 있습니다. 예제 D-01은 비교 기준을 분명히 하기 위해 UTF-16 코드 단위 수를 선택했습니다. 어떤 이모지는 2 이상으로 셉니다. 사용자가 보는 글자 수가 진짜 필요라면 요구를 다시 확인하고 그에 맞는 계산·화면 안내·경계 시험을 함께 바꿔야 합니다.

## 4. 설계·작업·검증으로 이어지는 해설 예제

저장 실패 시 이전 화면을 유지해야 한다면 두 설계가 가능합니다.

- 화면부터 바꾸고 나중에 저장: 반응이 즉각적이지만 실패 시 화면·개수·완료 상태를 모두 되돌리는 처리가 필요합니다.
- 다음 목록을 메모리에서 계산한 뒤 저장하고, 성공하면 화면 상태 교체: 이 작은 앱에서는 실패 전 상태를 유지하기 쉽습니다.

예제는 두 번째를 선택합니다. 구조는 **화면 담당 → 목록 처리 로직으로 다음 상태 계산 → 저장 담당으로 저장 시도 → 성공하면 화면 갱신 / 실패하면 오류 안내**입니다. 목록 처리 로직이 DOM과 저장소를 직접 다루지 않게 나누면 입력과 기대 출력만으로 테스트할 수 있습니다. 저장 담당은 읽기·쓰기 오류를 구별하고, 화면 담당은 사용자에게 알릴 책임을 가집니다. 이것은 저장 방식 선택의 근거이지 모든 앱에 적용되는 최적 구조라는 뜻은 아닙니다.

추적성은 표의 ID 개수를 맞추는 것이 아닙니다. IREB 용어집은 Traceability를 요구의 출처, 설계·코드·시험, 의존하는 요구를 서로 따라갈 수 있는 능력으로 설명합니다. W-08에서 시작해 저장 순서의 설계와 실패 시험을 찾을 수 있어야 하고, 반대로 `storage.js`를 수정할 때 W-07·W-08에 어떤 영향이 있는지도 찾아야 합니다.

작업은 ‘명세 작성, 개발, 테스트’처럼 큰 제목으로 끝내지 않습니다. ‘W-08 저장 실패 시험을 추가하고 실패를 관찰한다 → 저장에 성공하기 전에는 상태를 교체하지 않게 구현한다 → 같은 실패를 재시험한다’처럼 바꿀 대상과 완료 근거를 함께 적습니다.

## 5. 단계별 실습

작업 위치는 자기 실습 폴더 `my-todo-sdd`입니다. 요청은 Claude Code에 그대로 입력합니다. 한 단계의 자기 결과를 읽고 고친 뒤 다음으로 갑니다. 1~4단계와 6단계의 ‘검증 실행에서 본 것’은 요청을 실제로 실행해 얻은 결과이고, 5단계는 그렇게 만들어진 앱을 브라우저에서 직접 확인한 결과입니다. 자기 결과는 파일 구성도 문장도 다를 수 있습니다.

### 0단계 — 실습 폴더 준비하기

**목적:** 요구사항 파일 하나만 있는 실습 폴더를 만듭니다.

**한다**

강의 자료 저장소의 루트 폴더에서 아래 명령을 실행합니다. 저장소 안에서 실습하면 강의 자료가 바뀌므로 저장소 밖에 폴더를 만듭니다. 모듈 03 단원 M01에서 자기 요구사항을 만들었다면 준비된 파일 대신 그 파일을 복사합니다.

```bash
mkdir -p ~/work/my-todo-sdd
cp modules/03-requirements/M01-ai-requirements/requirements.md ~/work/my-todo-sdd/requirements.md
cd ~/work/my-todo-sdd
node --version
python3 --version
git init
git add -A && git commit -m "chore: 요구사항"
claude
```

`claude`를 실행한 창은 그대로 두고, 터미널 창을 하나 더 열어 `cd ~/work/my-todo-sdd`로 이동한 뒤 그 창에서 git과 테스트 명령을 실행합니다. 단계가 끝날 때마다 `git status --short`로 바뀐 파일을 보고 커밋합니다. Claude Code가 파일을 만들거나 명령을 실행하기 전에 허용할지 물으면 내용을 읽고 허용합니다.

**넘긴다 (산출물)**

`requirements.md` 한 파일이 있는 git 저장소.

**검토**

- [ ] `node --version`과 `python3 --version`이 버전을 출력한다.
- [ ] `git status --short`가 아무것도 출력하지 않는다.

### 1단계 — 요구를 동작 계약으로 구체화하기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 화면·데이터·오류에서 다르게 해석할 수 있는 조건을 드러냅니다.

**입력:** `requirements.md`.

**맡긴다**


**정한다**

**넘긴다 (산출물)**

**검증 실행에서 본 것 (4단계에서 만들어진 앱 하나)**

- SAMPLE 6장 표의 1~7번과 9번은 기대대로였습니다. 공백 입력 거부와 한국어 안내, 같은 제목 두 항목, 한 항목만 완료, 필터 세 가지와 남은 개수, 완료 필터에서 추가, 되돌리기와 삭제, 새로 고침 뒤 보존과 필터 초기화, 외부 요청 없음입니다. 7번은 새로 고침만 확인했고 브라우저를 닫았다 여는 것은 하지 않았습니다.
- 길이 경계도 기대대로였습니다. 200자는 추가됐고 201자는 ‘제목은 200자까지 입력할 수 있습니다. (현재 201자)’라는 안내와 함께 거부됐습니다.
- SAMPLE 7장의 쓰기 실패에서는 목록과 개수가 그대로였고 ‘저장하지 못해 변경하지 않았습니다. 다시 시도해 주세요.’가 나왔습니다. 새로 고친 뒤에도 그 항목은 없었습니다. 손상된 초기 데이터에서는 오류 안내가 나오고 입력 칸과 버튼이 비활성화됐으며, 저장된 값은 덮어쓰이지 않았습니다.
- 8번(키보드)에서 결함을 하나 찾았습니다. Enter로 추가하고, Tab으로 이동하며 초점 표시를 보고, Enter로 삭제하는 것은 됐습니다. 그런데 Space로 완료를 표시한 직후 초점이 사라졌고, Space를 바로 다시 눌러도 아무 일도 일어나지 않았습니다. Tab을 누르면 초점이 목록의 첫 항목으로 돌아가므로, 방금 완료한 항목을 되돌리려면 다시 찾아가야 합니다. Q-01의 ‘초점을 식별할 수 있다’와 SAMPLE 6장 8번의 기대 결과에 어긋납니다.
- 이 결함은 구현만의 문제가 아니었습니다. 삭제한 뒤의 초점은 명세, 설계, 테스트에 모두 있었지만, 완료를 바꾼 뒤의 초점은 세 곳 어디에도 없었습니다. 요구에서 명세로 옮길 때 빠진 것이 구현까지 그대로 이어졌습니다.
- 이 결함은 자동 테스트 104개가 모두 통과한 상태에서 나왔습니다. 자동 테스트가 모두 통과해도 요구를 모두 충족했다는 증거는 되지 않습니다.
- 브라우저 콘솔의 오류는 `favicon.ico`가 없다는 것 하나였습니다.

**검토**

- [ ] 브라우저에서 W-07, W-08, Q-01을 따로 확인했다.
- [ ] 실패를 찾았다면 조건, 기대, 관찰, 원인 가설을 구별해 적었다.
- [ ] 고친 뒤 같은 조건을 다시 시험했다.

### 6단계 — 변경 영향과 재검증

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 명세를 한 번 쓰고 마는 문서가 아니라 변경의 기준으로 사용합니다.

**입력:** 현재 문서, 코드, 검증 결과. 연습 변경은 ‘제목 최대 길이를 200에서 100으로 줄인다’입니다.

**맡긴다**

```text
제목 길이 제한을 200에서 100으로 바꾼다면 영향을 받는 요구·명세·설계·작업·코드·테스트를 찾아 줘.
이미 저장된 101~200 길이의 제목을 어떻게 다룰지는 아직 결정하지 않았으니 대안과 영향을 먼저 설명해 줘.
지금은 수정하지 마.
```

**정한다**

저장된 긴 제목을 그대로 둘지, 새 입력만 100자로 제한할지, 불러올 때 거부할지 같은 정책을 정합니다.

**맡긴다**

이 부분의 요청문은 제공하지 않습니다. 정한 정책과 고칠 순서를 자기 말로 요청해 관련 파일을 함께 고칩니다. 입력 칸의 제한만 고치고 끝내지 않습니다.

**확인한다**

새 입력의 100·101 경계, 기존 저장 데이터의 복원, 기존 기능의 회귀를 확인합니다.

**넘긴다 (산출물)**

변경 이유와 재검증 결과를 반영한 문서와 구현.

**검증 실행에서 본 것 (2회)**

- 두 번 모두 파일을 고치지 않고 영향 목록과 대안만 냈습니다.
- 두 번 모두 요구(D-01, W-02), 명세, 설계, 작업, 코드의 기준값, 테스트의 경계값을 찾았습니다. 화면의 안내 문구(`index.html`)와 오류 문구(`src/messages.js`)에 200이 따로 적혀 있다는 것도 두 번 모두 짚었습니다.
- 두 번 모두 저장된 101~200자 제목을 핵심 쟁점으로 들었습니다. 이 앱은 불러올 때 길이 규칙으로 저장 내용이 정상인지 판정합니다. 숫자만 바꾸면 이미 저장된 긴 제목 때문에 저장 내용 전체가 손상으로 분류될 수 있습니다.
- 정책을 정해 실제로 고치고 다시 검증하는 과정은 실행하지 않았습니다.

**검토**

- [ ] 변경 전의 통과 기록을 새 변경의 증거로 다시 쓰지 않았다.
- [ ] 원래 필요가 바뀐 것인지 구현 결함을 고친 것인지 구별해 설명할 수 있다.

## 자주 막히는 곳

| 증상 | 확인하고 고칠 것 |
|---|---|
| `node --test`가 테스트를 하나도 실행하지 않는다 | 테스트 0개는 성공 증거가 아닙니다. `package.json`의 테스트 명령과 테스트 파일의 위치를 확인합니다 |
| 구현 전 실패가 ‘모듈을 찾을 수 없음’뿐이다 | 단언 실패가 아닙니다. 동작 없는 뼈대를 먼저 만들게 하고 테스트가 단언에서 실패하는 것을 본 뒤 구현하게 합니다 |
| Claude가 다른 묶음을 골랐다 | `tasks.md`에 검토 완료 표시를 하거나, 요청에 묶음 이름을 적습니다 |
| 설계에 없는 파일이 생겼다 | 이유를 묻습니다. 받아들이면 `design.md`와 `tasks.md`에 반영합니다 |
| 자동 테스트는 통과하는데 브라우저에서 다르게 동작한다 | 요구가 그대로라면 요구를 코드에 맞춰 바꾸지 않습니다. 관찰을 `verification.md`에 적고, 실패하는 테스트를 먼저 더한 뒤 고칩니다 |

| `git commit`이 “Author identity unknown”으로 실패한다 | `git config --global user.name "이름"`과 `git config --global user.email "메일 주소"`를 먼저 실행합니다 |
| 8000번 포트가 사용 중이다 | 8001처럼 비어 있는 포트를 씁니다. 보존을 확인하는 동안에는 주소를 바꾸지 않습니다 |
