# 결과 예제와 앱 실행·확인 — 요구사항에서 명세로

## 1. 자기 문서를 먼저 읽기

GUIDE 1~3단계에서 만든 `spec.md`, `design.md`, `tasks.md`를 연다. 다음 연결을 파일에서 직접 찾아본다.

- W-03·W-04의 ‘지정한 한 항목’을 어떻게 구별하는가?
- W-06의 남은 개수는 어느 목록에서 계산하는가?
- W-08의 저장 실패 후 어떤 상태를 유지하며, 어느 시험으로 확인하는가?

아래 내용은 **비교를 위해 작성한 결과 예제**다. 실제 Claude Code 출력이나 새 웹 앱의 실행 기록은 아니다. 자기 결과를 관찰한 뒤 차이의 이유를 비교한다.

## 2. 명세 예제 — 사용자 동작을 데이터·규칙으로 풀기

입력은 [준비된 03 결과](../../03-requirements/M01-ai-requirements/requirements.md)다. 다음은 `spec.md`의 핵심 부분에 해당한다.

### 모델과 화면 상태

```text
Todo: { id: string, text: string, completed: boolean }
전체 목록: Todo[] (추가 순서)
현재 필터: all | active | completed (초기값 all)
저장 가능 상태: 정상 | 읽기 오류로 변경 중단
남은 개수: 전체 목록에서 completed=false인 항목 수
표시 목록: 현재 필터를 전체 목록에 적용한 결과
```

- `id`는 항목마다 고유하고 저장·복원해도 유지된다. 제목이 같아도 다른 ID다. W-03·W-04의 한 항목 처리를 위한 설계 선택이다.
- 화면의 ‘진행 중’은 `active`, 즉 `completed=false`다. 기존 공통 함수 샘플의 ‘진행’ 상태를 가져오지 않는다.
- 저장 대상은 전체 목록의 ID·제목·완료 여부·순서다. 필터와 남은 개수는 저장하지 않는다. 다시 열 때 필터는 전체다(D-04).

### 동작 계약

| 동작 | 입력·조건 | 결과·지켜야 할 조건 |
|---|---|---|
| 추가 | 제목 문자열 | 앞뒤 공백 제거 후 length 1~200이면 새 ID·미완료 항목 생성. 잘못된 길이면 기존 목록 유지·한국어 안내(W-01·W-02). |
| 완료 전환 | 존재하는 ID | 해당 항목만 반전, 나머지 데이터와 순서 유지(W-03). |
| 삭제 | 존재하는 ID | 해당 항목만 제거(W-04). |
| 필터 | all/active/completed | 표시 목록만 변경. 전체 목록과 남은 개수는 변하지 않음(W-05·W-06). |
| 저장 변경 | 계산한 다음 전체 목록 | 저장 성공 뒤에만 현재 상태로 교체. 실패하면 변경 전 전체 목록·개수·완료 상태 유지, 한국어 안내(W-08). |
| 초기 읽기 | 저장 키의 데이터 | 키가 없으면 빈 목록. 정상 배열이면 복원. 읽기 거부·JSON 오류·잘못된 항목 구조면 기존 저장값을 덮어쓰지 않고 변경 중단·안내(W-07·W-08). |

제목 최대 길이, 중복 허용과 초기 손상 데이터 처리의 근거는 03의 D-01·D-05다. 명세 작성 단계에서 AI가 새로 정한 사실로 바꾸지 않는다. 필터의 허용 값처럼 내부 상태를 구체화한 선택은 구현과 테스트가 같은 뜻으로 사용해야 한다.

## 3. 설계 예제 — 어떤 책임으로 나눌까

다음은 `design.md`에서 책임을 설명하는 한 가지 구성이다. 파일명은 다를 수 있지만 W-08의 순서와 책임은 읽을 수 있어야 한다.

| 파일 | 책임 | 확인할 요구 |
|---|---|---|
| `index.html`, `src/style.css` | 한국어 입력·버튼·필터·목록·안내와 보이는 초점 | Q-01·Q-02 |
| `src/todo.js` | 목록 변환·제목 검사·필터·집계. DOM과 저장소를 사용하지 않는 함수 | W-01~W-06 |
| `src/storage.js` | `my-todo:todos` 키 읽기·쓰기와 데이터 구조 검사. 저장 매체를 인자로 받아 시험 가능하게 구성 | W-07·W-08·C-01 |
| `src/app.js` | 사용자 입력 연결, 다음 목록 계산, 저장 시도, 성공한 상태의 화면 표시와 실패 안내 | W-01~W-08·Q-01·Q-02 |
| `tests/*.test.js` | 정상·경계·거부·저장 실패 자동 시험 | 각 해당 W 요구 |

호출 순서는 다음처럼 읽는다. 줄 하나가 한 책임에서 다음 책임으로 넘기는 동작이며, 도구가 자동 생성하는 흐름을 보증하는 표기가 아니다.

```text
사용자 추가 → app: 입력 읽기 → todo: 다음 목록 계산
                             → storage: 다음 목록 저장 시도
                                  성공 → app: 현재 목록 교체·표시
                                  실패 → app: 기존 목록 유지·안내
```

왜 `completed`와 별도로 ‘남은 개수’를 저장하지 않을까? 두 값을 따로 수정하면 완료 표시와 개수가 어긋날 수 있다. 목록만 바꾸고 개수를 계산하면 W-06의 불변조건을 유지하기 쉽다. 반면 큰 데이터의 집계 성능이 문제가 되는 시스템은 다른 선택을 검토할 수 있다. 이 예제의 작은 앱 조건에서 선택한 이유다.

## 4. 작업 분해 예제 — 구현 완료를 무엇으로 볼까

다음은 `tasks.md`의 예다. 작업 순번은 실행 순서를 나타내며 요구 ID와 다르다.

| 묶음 | 시험과 구현 대상 | 선행 | 완료 근거 |
|---|---|---|---|
| T1 추가·거부 | todo 로직의 유효 제목·공백·200/201 경계 시험 → 로직 → 입력 화면 연결 | 명세·설계 검토 | W-01·W-02 시험과 브라우저 추가·거부 확인 |
| T2 완료·삭제·조회 | 같은 제목 두 항목, 토글 왕복, 한 항목 삭제, 필터·전체 개수 시험 → 로직·화면 | T1 | W-03~W-06의 정상·빈 표시 목록 확인 |
| T3 보존·실패 | 저장 왕복·읽기 손상·쓰기 실패 시험 → 저장 담당 → 화면의 성공 전 교체 방지 | T2 | W-07·W-08 자동 시험과 재실행·실패 주입 확인 |
| T4 통합 품질 | 키보드 이동·안내·외부 전송 확인과 발견 사항 수정 | T3 | Q-01·Q-02·C-01 관찰 기록과 기존 기능 회귀 |

예를 들어 T3가 완료 표시여도 ‘저장 함수가 오류를 던진다’만 시험했다면 충분하지 않다. app이 오류를 잡고 기존 화면·개수를 유지하는지까지 자동 시험 또는 브라우저에서 확인해야 한다.

## 5. 완성한 앱 실행하기

**시작 조건:** GUIDE 4단계에서 자기 프로젝트의 구현이 끝난 상태. 아래 명령은 위 설계 예의 파일 구성을 따른다. 자기 설계가 다르면 실제 `design.md`의 명령·파일에 맞춘다. 파일이 없다면 생성이 완료되지 않은 것이므로 먼저 작업 결과를 확인한다.

1. `my-todo-sdd` 폴더에서 편집기로 `index.html`, `src/app.js`, `src/todo.js`, `src/storage.js`, `tests/`를 확인한다. `package.json`에는 ES 모듈용 `"type": "module"`이 있어야 한다. 자동 실행 스크립트와 외부 의존성이 추가되지 않았는지도 읽는다.
2. 터미널에서 실행한다.

```bash
node --test
```

`package.json`에 test 스크립트가 있으면 `npm test`로 실행한다. `node --test`는 테스트 폴더의 도우미 파일까지 테스트로 세어 수가 달라질 수 있다. 실패 0뿐 아니라 실제로 수집된 테스트가 있는지, 요구의 정상·경계·실패를 시험하는지도 읽는다. 시험 개수는 AI 출력마다 달라지므로 정해진 개수와 맞추지 않는다. 테스트 0개는 성공 증거가 아니다.

3. 같은 폴더에서 로컬 서버를 연다.

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

브라우저에서 `http://127.0.0.1:8000`을 연다. 포트가 이미 사용 중이면 8001처럼 비어 있는 포트를 선택하고 이후에도 같은 주소를 사용한다. `localhost`와 `127.0.0.1`, 서로 다른 포트는 저장 영역이 달라질 수 있으므로 보존 확인 중 주소를 바꾸지 않는다. 서버를 종료할 때는 터미널에서 Ctrl+C를 누른다.

## 6. 브라우저에서 실제 결과 확인하기

다른 데이터가 없는 실습 전용 주소에서 시작한다. 아래는 **기대 결과**이며 자기 앱에서 관찰한 결과는 별도로 적는다.

| 순서 | 할 행동 | 기대 결과·요구 |
|---|---|---|
| 1 | 공백만 입력해 추가 | 목록 변화 없이 한국어 거부 안내(W-02) |
| 2 | ‘보고서 작성’을 두 번 추가 | 같은 제목 두 항목이 미완료로 보이고 남은 개수 2(W-01) |
| 3 | 첫 항목만 완료 | 첫 항목만 완료, 남은 개수 1(W-03·W-06) |
| 4 | 전체·진행 중·완료 필터 변경 | 각각 두 개·두 번째·첫 번째 표시. 남은 개수는 모두 1(W-05·W-06) |
| 5 | 완료 필터에서 ‘전화하기’ 추가 | 완료 목록은 그대로, 전체 남은 개수 2. 전체 필터에 새 항목이 존재(W-01·W-05) |
| 6 | 첫 항목을 미완료로 되돌리고 두 번째 항목 삭제 | 첫 항목과 전화하기만 남고 남은 개수 2(W-03·W-04) |
| 7 | 전화하기를 완료하고 완료 필터를 고른 뒤 새로 고침, 브라우저를 닫았다 같은 주소로 재실행 | 제목·순서와 전화하기의 완료가 유지되고 필터는 전체(W-07) |
| 8 | 마우스를 놓고 Tab·Enter·Space로 전 기능 사용 | 초점이 보이고 완료·삭제 후에도 조작을 이어 갈 수 있음(Q-01) |
| 9 | 개발자도구 Network 기록을 켜고 추가·완료·삭제 | 할 일 내용의 외부 전송 없음. 초기 로컬 파일 요청과 구별(C-01) |

최대 길이 시험은 ‘가’를 200번, 201번 반복한 입력으로 경계를 비교한다. 긴 입력은 개발자 도구 Console에서 `copy('가'.repeat(200))`을 실행해 복사한 뒤 붙여 넣으면 된다. 입력칸이 201 입력을 막는다면 직접 호출하는 로직 시험에서도 거부되는지 확인한다. 화면 입력 제한만으로 데이터 처리 규칙을 검증했다고 보지 않는다.

## 7. 실패 처리 확인하기

정상 경로만 확인해서는 W-08을 충족했는지 알 수 없다. 실습 전용 주소와 데이터에서만 다음을 수행한다.

### 쓰기 실패

먼저 저장 담당 자동 시험에서 쓰기 메서드가 오류를 던지는 가짜 저장소를 입력한다. 이는 외부 서비스 응답을 꾸미는 것이 아니라 실패 조건을 통제하는 테스트 방법이다. 목록 처리 결과가 실제 화면 상태로 확정되지 않는지도 시험한다.

브라우저 통합 확인이 필요하면 DevTools Console에서 아래를 실행한 뒤 항목 하나를 추가한다. 이 변경은 현재 페이지의 저장 메서드만 실패시키고, 새로 고치면 원래 메서드로 돌아간다.

```javascript
Storage.prototype.setItem = function () {
  throw new Error('실습용 저장 실패');
};
```

기존 목록·개수 유지와 한국어 오류를 관찰한 뒤 새로 고친다. 방금 추가한 항목이 저장되지 않았는지 확인한다. 이 방법으로 실패가 일어나지 않는 구현이면 저장 담당의 실제 호출 경로를 먼저 확인한다. 실패를 관찰하지 않았는데 W-08 통과로 적지 않는다.

### 손상된 초기 데이터

정상 실습 데이터를 별도로 보관하고, DevTools의 해당 주소 localStorage에서 **자기 앱의 저장 키 하나만** 읽을 수 없는 JSON(예: `{`)으로 바꾼 뒤 새로 고친다. 위 설계 예는 키가 `my-todo:todos`다. 다른 구현이면 `storage.js`에서 실제 키를 확인한다.

오류 안내가 나오는지, 변경 기능이 멈추는지, 손상된 값을 덮어쓰지 않는지 확인한다. 마친 뒤 그 키만 원래 값으로 복원하고 다시 연다. 브라우저 전체 데이터 삭제나 `localStorage.clear()`로 다른 앱의 데이터를 지우지 않는다. 시험을 하지 못했다면 초기 손상 처리는 미확인으로 남긴다.

## 8. 결과 기록과 수정

`verification.md`에는 4단계에서 Claude가 적은 기록이 이미 있다. 그 끝에 아래 양식을 덧붙이고 자기 실행의 사실을 채운다. 아래는 빈 기록 양식이며 성공 출력 예문이 아니다.

```markdown
# 구현 확인
- 사용한 요구·명세 판본:
- 실행 환경과 명령:
- 자동 테스트에서 실제 수집·통과·실패한 시험:
- 브라우저에서 확인한 시나리오와 관찰:
- 실패 또는 미확인 조건:
- 수정한 파일·이유와 같은 조건의 재시험 결과:
```

예를 들어 완료 필터에서 남은 개수가 0으로 바뀌면 W-06, `spec.md`의 집계 입력, `design.md`의 상태 분리, `app.js`의 전달 목록과 관련 시험을 함께 읽는다. 사용자 요구가 그대로라면 요구를 코드의 오류에 맞춰 바꾸지 않는다. 반대로 사용자가 필터 기준 개수를 원하기로 결정했다면 요구에서 시작해 연결된 명세·시험도 바꾼다.

## 9. 기존 실행 샘플에서 추적성 확인하기

새 웹 앱 구현 전후에 기존 [공통 생성 샘플](../../../samples/web-task-system/README.md)을 사용해 작은 연결을 직접 확인할 수 있다. 저장소 루트에서 다음을 실행한다. 의존성은 샘플 폴더 안에서 설치한다.

```bash
cd samples/web-task-system
pnpm install
pnpm test
```
