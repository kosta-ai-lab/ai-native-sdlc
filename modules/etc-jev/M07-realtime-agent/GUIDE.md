# 개념

이 모듈에서는 **실시간으로 움직이는 2D 드론 게임**에서, 답하는 데 시간이 걸리는 두뇌(Jev)로 드론을 안전하게 조종합니다. 아래 네 가지만 알면 바로 시작할 수 있습니다. 자세한 개념과 드론 시뮬레이터 대응표는 [README.md](README.md)를 참고하세요.

| 용어 | 한 줄 설명 |
|---|---|
| 세 가지 주기 | 물리 60Hz, 화면 60FPS, **판단 5Hz**. 판단은 느리고 비싸니 따로 돈다 |
| 비동기 호출 | 두뇌가 생각하는 동안에도 세계·화면·안전 감시는 계속 돈다 |
| 예산·유지 | 너무 늦은 답은 버리고(budget), 새 답이 없으면 이전 명령을 유지하되 너무 오래면 멈춘다(hold) |
| 안전 행동 | 자신 없거나(낮은 확률) 오래 답이 없으면 `HOVER`(제자리 비행) |

세계는 실제 드론처럼 **미터와 초** 단위입니다.

```
  y (북, N)
  ↑            경기장 20m × 15m, 왼쪽 아래가 (0, 0)
  │   NW  N  NE     명령 9개: 8방향 + HOVER
  │     ╲ │ ╱       드론 속도 2m/s, 최대 가속도 4m/s² (관성 있음)
  │   W ─ ● ─ E     거리 센서 8방향, 최대 5m
  │     ╱ │ ╲
  │   SW  S  SE
  └──────────────→ x (동, E)
```

> 이 가이드의 규칙 두뇌·지연 흉내 결과는 **실제 실행 결과**입니다. Jev 결과는 실행할 때마다, 네트워크 상태마다 달라집니다.

# 2 단계: 규칙 두뇌와 세 가지 주기

이제 사람 대신 **규칙 두뇌**(`RuleBrain`)가 조종합니다. "목표 쪽으로 가되, 센서 거리가 짧은 방향은 피한다"는 규칙입니다.

`sim.py`의 루프가 세 주기를 어떻게 나누는지 봅니다.

```python
# 매 물리 주기 (1/60초)
blocked = decider.tick(world)          # 판단 주기(1/5초)가 됐을 때만 두뇌에게 요청
command = decider.command(world.t)     # 지금 실행할 명령 (도착한 답 반영)
command = safety.filter(world, command)  # 안전 감시는 매번 (60Hz)
world.step(DT, command)                # 세계 진행
# 화면은 프레임마다 renderer.draw()
```

실행합니다.

```powershell
python 01_rule_brain.py
```

판단 주기를 바꿔 봅니다.

```powershell
python 01_rule_brain.py --decision-hz 1
```

```powershell
python 01_rule_brain.py --decision-hz 20
```

화면 없이 결과만 빠르게 볼 수도 있습니다.

```powershell
python 01_rule_brain.py --headless --decision-hz 5
```

실제 결과 (`moving` 레벨, 지연 없음):

| 판단 주기 | 완료 시간 | 충돌 | 판단 요청 수 |
|---|---|---|---|
| 1Hz | 21.9초 | 0 | 22 |
| 5Hz | 19.1초 | 0 | 96 |
| 20Hz | 18.9초 | 0 | 378 |

5Hz와 20Hz의 차이는 0.2초뿐인데 요청 수는 4배입니다. Jev는 **요청마다 시간과 비용**이 드니, 판단 주기는 "충분히 빠른 만큼만" 정합니다.

## 규칙
> 화면 FPS(오른쪽 `FPS`)는 판단 주기와 상관없이 60 근처여야 합니다. 세 주기가 분리되어 있기 때문입니다.

> 판단 주기는 `config.py`의 `DECISION_HZ`(기본 5)에서도 바꿀 수 있습니다.

# 3 단계: 두뇌가 느리면? 동기 vs 비동기 호출

Jev는 답하는 데 0.2~0.5초가 걸립니다. 키 없이 먼저 체험하기 위해, 규칙 두뇌에 **지연을 흉내 내는** `LatencyModel`(0.3±0.1초)을 붙입니다.

**동기(sync)** — 답이 올 때까지 프로그램 전체가 멈춥니다.

```powershell
python 02_latency_sync.py --mode sync
```

**비동기(async)** — 두뇌는 뒤에서 생각하고, 나머지는 계속 돕니다.

```powershell
python 02_latency_sync.py --mode async
```

실제 측정 (5초 실행):

| 방식 | 평균 FPS | 화면 |
|---|---|---|
| sync | **18** | 뚝뚝 끊기고, 드론이 순간이동하듯 점프함 |
| async | **61** | 부드러움. 오른쪽 `waiting`이 0.3초까지 올라갔다 내려감 |

sync에서 드론이 점프하는 이유: 프로그램이 멈춘 0.3초 동안에도 **실제 드론은 이전 명령으로 계속 날아갔기** 때문입니다. `sim.py`의 `advance_blind()`가 이것을 재현합니다. 그 사이에는 **안전 감시도 실행되지 못합니다.**

```powershell
python 02_latency_sync.py --mode sync --latency 0.8
```

## 규칙
> 동기 호출의 진짜 위험은 화면이 아니라 **기다리는 동안 안전 감시가 눈을 감는 것**입니다. 실시간 제어에서 네트워크 호출은 항상 비동기로 합니다.

> `decider.py`는 Jev를 쓸 때 `ThreadPoolExecutor`로 다른 스레드에서 호출합니다. 요청은 한 번에 하나만 보내고, 진행 중이면 그 판단 주기는 건너뜁니다.

## 산출물
- sync / async의 FPS와 화면 차이 메모

## 체크리스트
- [ ] sync에서 FPS가 크게 떨어지는 것을 확인한다.
- [ ] async에서 FPS가 60 근처로 유지되는 것을 확인한다.
- [ ] sync에서 드론이 점프하는 이유를 설명할 수 있는지 확인한다.

# 4 단계: 지연 시간 예산과 이전 행동 유지

진짜 네트워크는 **가끔 크게 늦습니다.** 이번 지연은 "보통 0.3±0.1초, 15% 확률로 1.5초 더"입니다. 다섯 가지 설정을 30판씩 비교합니다 (화면 없이 1분 안팎이면 끝남).

| 설정 | 늦게 온 답 | 새 답이 오래 없을 때 |
|---|---|---|
| `ideal` | (지연 없음, 기준) | |
| `sync` | 기다리는 동안 모두 멈춤 | |
| `async` | 그대로 적용 | 이전 명령 계속 |
| `budget` | **0.6초 넘으면 버림** | 이전 명령 계속 |
| `budget+hold` | 0.6초 넘으면 버림 | **0.8초 넘으면 HOVER** |

`decider.py`의 핵심 부분입니다.

```python
if self.budget is not None and age > self.budget:
    result = "LATE"                  # 예산 초과 → 버림 (이전 명령 계속)
...
if self.hold is not None and now - self.last_fresh_t > self.hold:
    self.current, self.status = SAFE_ACTION, "TIMEOUT"   # 너무 오래 → HOVER
```

```powershell
python 03_latency_policies.py
```

실제 결과 (`moving` 레벨, 30판 평균, 1분 안팎 걸림):

```
설정              수집    충돌     점수    시간s     안전정지    버림     시간초과
----------------------------------------------------------------
ideal          5.0   0.0    500   19.1      4.0   0.0      0.0
sync           4.9   2.2    382   35.8      3.5   0.0      0.0
async          4.8   1.4    408   35.1     15.7   0.0      0.0
budget         4.8   1.3    413   34.3      9.1   8.0      0.0
budget+hold    4.6   1.0    408   39.0      7.9   8.9      7.8
```

결과 읽기:
- **지연만으로 완료 시간이 거의 두 배**(19초 → 34~39초)가 됩니다. 늦은 판단으로 목표를 지나쳤다 돌아오기 때문입니다.
- **sync → async**: 충돌 2.2 → 1.4. 안전 감시가 계속 돌기 때문입니다. 대신 안전 감시가 15.7번이나 개입해야 했습니다.
- **budget만**: 충돌은 거의 그대로(1.3)이고 안전 감시 개입이 줄어듭니다(9.1). 늦은 답을 버려도 **그동안은 이전 명령으로 계속 날기** 때문에 효과가 작습니다.
- **budget+hold**: 충돌이 가장 적고(1.0), 안전 감시 개입도 절반(7.9)입니다. 대신 멈춰 기다리는 시간만큼 느려집니다(39초). **안전과 속도를 맞바꾼 것**입니다.

같은 비교를 `open` 레벨(멈춘 장애물만)에서도 해 봅니다.

```powershell
python 03_latency_policies.py --level open
```

실제 결과 (30판 평균): 충돌 sync 1.4 → async 0.2 → budget 0.3 → budget+hold 0.2, 점수는 budget+hold가 478로 가장 높습니다.

한 설정을 화면으로 봅니다. 오른쪽 `status`가 `FRESH`(초록) → `HOLD`(노랑) → `LATE`(주황) → `TIMEOUT`(빨강)으로 바뀌는 것을 확인합니다.

```powershell
python 03_latency_policies.py --watch budget+hold
```

## 규칙
> **예산과 유지 한도는 함께** 씁니다. 예산만 쓰면 늦은 답을 버려도 그동안 이전 명령으로 계속 날기 때문에 효과가 작습니다.

> 무작위 지연이 섞인 실험은 판마다 결과가 크게 다릅니다. 기본 30판 평균을 보고, `--runs`를 줄이면 숫자가 흔들린다는 것을 기억합니다.

> 예산은 "평소 지연보다 넉넉하게, 그 사이 드론이 움직이는 거리가 감당할 만큼"으로 정합니다. 0.6초 × 2m/s = 1.2m입니다.

## 산출물

- `--watch`로 상태 변화를 본 메모

## 체크리스트

- [ ] budget만으로는 효과가 작은 이유와, hold를 더하면 무엇을 얻고 잃는지 설명할 수 있는지 확인한다.

# 5 단계: Jev 두뇌 연결하기

이제 흉내가 아니라 **진짜 Jev**를 꽂습니다. 1~4단계의 코드는 그대로이고, 두뇌만 `JevBrain`으로 바뀝니다.

`brains.py`의 `JevBrain`이 Jev에게 보내는 state입니다.

```python
{
  "units": "meters and seconds; x grows to the east, y grows to the north",
  "drone_velocity": {"vx": 1.41, "vy": 1.41},
  "target_item": {"dx": 2.0, "dy": 5.0, "distance": 5.39},        # 가장 가까운 목표까지
  "range_sensors_m": {"N": 5.0, "NE": 3.2, "E": 5.0, ...},       # 8방향 거리 센서
  "obstacles_nearby": [{"dx": 3.1, "dy": 0.5, "radius": 0.8, "vx": 0.0, "vy": 1.2, "gap": 2.1}],
  "items_left": 5,
  "decision_period_s": 0.2
}
```

# 6 단계: 신뢰도가 낮으면 안전 행동

Jev는 답과 함께 확률을 줍니다. **고른 명령의 확률이 기준(min_prob)보다 낮으면 HOVER**하게 합니다.

```python
elif self.min_prob is not None and decision.prob < self.min_prob:
    result = "LOW_CONF"              # 자신 없음 → 안전 행동
    self.current = SAFE_ACTION
```

먼저 키 없이 효과를 확인합니다. `NoisyBrain`은 25% 확률로 엉뚱한 방향을 고르지만, 그때는 확률을 낮게(0.2~0.5) 말하는 **"확률을 정직하게 말하는 모델" 흉내**입니다.

```powershell
python 05_low_confidence.py
```

실제 결과 (`moving` 레벨, 지연 0.3초, budget 0.6 / hold 0.8, 30판 평균):

```
min_prob     수집    충돌     점수    시간s     안전정지     자신없음
------------------------------------------------------
끔           4.6   1.0    410   36.3     13.0      0.0
0.4         4.8   0.9    437   33.6     10.8     15.0
0.55        5.0   0.8    460   31.6      5.4     20.7
0.7         4.8   0.9    433   39.5      8.3     43.7
0.9         1.3   0.1    125   45.0      0.2     98.9
```

- **0.55**: 엉뚱한 답(확률 0.5 이하)만 걸러서 수집·충돌·시간·점수가 모두 가장 좋습니다. 안전 감시 개입도 13.0 → 5.4로 줄어듭니다.
- **0.7**: 맞는 답(확률 0.6~0.7)까지 버리기 시작해서 오히려 느려집니다 (39.5초).
- **0.9**: 거의 모든 답을 버려 **드론이 얼어붙습니다** (수집 1.3개). 충돌은 거의 없지만 아무것도 못 합니다.

이제 Jev로 같은 실험을 합니다.

```powershell
python 04_jev_brain.py --min-prob 0.5
```

```powershell
python 04_jev_brain.py --min-prob 0.7
```

```powershell
python 04_jev_brain.py --level dense --min-prob 0.5
```

|---|---|---|---|---|---|---|---|
| D | moving | 끔 (5단계 A) | | | | - | |
| E | moving | 0.5 | | | | | |
| F | moving | 0.7 | | | | | |
| G | dense | 0.5 | | | | | |

**직접 해 보기**
1. 로그에서 `result`가 `LOW_CONF`인 줄의 `state`를 봅니다. Jev가 자신 없어 한 상황은 어떤 상황인가요? (예: 움직이는 장애물이 가까울 때, 목표가 장애물 뒤에 있을 때)
2. HOVER가 항상 안전할까요? `moving` 레벨에서 움직이는 장애물이 다가올 때 HOVER하면 어떻게 되는지 화면으로 확인합니다.

## 규칙
> 기준은 **"엉뚱한 답만 거를 만큼"**만 높입니다. 너무 높으면 안전하지만 임무를 못 합니다. 내 데이터(로그의 확률 분포)를 보고 정합니다.

> HOVER는 "가장 덜 위험한 행동"이지 "항상 안전한 행동"이 아닙니다. 다가오는 장애물 앞에서는 멈추는 것도 위험할 수 있습니다. 이 문제는 드론 시뮬레이터 모듈에서 "회피 기동"으로 다룹니다.
