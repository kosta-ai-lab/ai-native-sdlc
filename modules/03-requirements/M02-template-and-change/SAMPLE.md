# 완성 예제 — 원요청에서 ‘할 일 생성’ 요구사항까지

> 실습을 위해 만든 자체 교육 예제입니다. 아래 원요청·답변·결정은 설명용 시나리오이며 실제 고객 발화나 사람 승인 이력이 아닙니다. 기존 [요구사항 정본](../../../samples/web-task-system/docs/03-requirements.md)의 UC-01, R-01~R-03을 바꾸지 않고 그 앞의 분석 과정을 설명합니다.

## 1. 원요청과 목적

- 원문(교육용): “팀원이 처리할 업무를 할 일로 등록할 수 있게 해 주세요.”
- 원문 위치/제공자: 이 문서의 자체 교육 시나리오. 외부 제공자는 없습니다.
- 분석자의 재서술: 팀원이 업무 제목으로 할 일을 만들고, 만든 할 일의 시작 상태를 알 수 있어야 합니다.
- 관련 용어: ‘할 일’은 생성 직후 상태이며 ‘진행’·‘완료’와 구별합니다. 상태 변경은 이번 기능에 포함하지 않습니다.

원문만으로는 초기 상태나 오류 문구를 알 수 없습니다. 아래 예제 조건을 원문에 있었던 사실로 소급하지 않는 것이 핵심입니다.

## 2. 질문·가정·결정

| 질문 ID | 질문/선택지 | 관련 요구·영향 | 예제 답변·근거 | 상태 | 다음 단계 차단 여부·이유 |
|---|---|---|---|---|---|
| Q-01 | 등록할 정보는 제목뿐인가? | R-01, 필드 범위 | 예제 조건: 제목만 사용. D-01 | 예제에서 해소 | 아니오. 학습 경계 고정 |
| Q-02 | 생성 직후 상태는? | R-02, 결과 확인 | 예제 조건: ‘할 일’. D-02 | 예제에서 해소 | 아니오. 초기값 고정 |
| Q-03 | 빈 제목은 무엇이며 어떻게 알릴까? | R-03, 거부 기준 | 예제 조건: 빈 문자열 `""` 거부, ‘제목은 필수’ 오류. D-03 | 예제에서 해소 | 아니오. 이 경계만 구현 |
| Q-04 | 공백만 있는 제목·앞뒤 공백은? | R-03 변경 가능 | 원요청에 없음. 현재 코드도 공백 제거 안 함 | 미결 | 이번 기준에서는 보류. 거부 요구로 확장하면 차단 질문으로 전환 |
| Q-05 | 저장·로그인·웹 화면도 필요한가? | 서비스 범위 | 예제 조건: 이번 함수 실습에서는 제외. D-01 | 예제에서 해소 | 아니오. 실제 서비스라면 재검토 |

| A-01 | 호출자가 문자열 title을 전달함 | 함수 경계를 좁힘. 외부 입력이면 실행 시 검증 필요 | 04 타입 계약과 호출자 검토 | 예제의 입력 제약으로 한정, 외부 입력 안전성은 미검증 |

|---|---|---|---|---|---|

Q-04는 ‘공백 제목을 허용해야 한다’는 확정 요구가 아닙니다. 현재 기준이 정하지 않은 경계입니다. 지금 코드는 공백만 있는 제목도 거부하지 않고 그대로 담아 돌려주므로, 운영에 쓰기 전에는 별도 판단이 필요합니다.

## 3. 범위와 비기능 조건

- 포함: 문자열 제목으로 생성, 초기 상태 반환, 빈 문자열 거부.
- 제외: 목록·수정·삭제·상태 변경, ID·담당자·마감일, 저장, 웹/API, 인증·인가. 이 기능의 교육 범위 밖이며 불필요하다고 결정한 것이 아닙니다.
- 외부 의존/제약: TypeScript 함수 입력과 반환값만 다룹니다. 기존 샘플 테스트 환경은 Node.js·pnpm입니다.

| 비기능 항목 | 필요한 조건 | 측정 대상·기준·방법 | 근거/결정 | 상태·진행 영향 |
|---|---|---|---|---|
| 성능 | 원요청에 목표 없음 | 부하·응답 시간 목표는 미결. 임의 수치 없음 | 추가 질문 필요 | 함수 예제에서는 보류, 성능 검증 완료 아님 |
| 보안·저장 내구성 | 운영 서비스에는 검토 필요 | 인증·개인정보·저장 보장 기준은 미결 | D-01 범위 밖 | 실습에서는 제외, 운영 투입의 근거로 사용 불가 |

| R-02 | 새 할 일의 초기 상태는 ‘할 일’이다 | 기능 | D-02 | 정상 생성 결과의 상태가 ‘할 일’ | 예제 기준 |

## 5. 유즈케이스

### UC-01: 할 일 생성

- 행위자/목적: 팀원이 처리할 업무를 등록합니다.
- 관련 요구 ID: R-01, R-02, R-03.
- 사전 조건: 최초 기능이라 업무상 선행 조건은 없습니다. 함수 입력은 문자열이라는 A-01 제약을 적용합니다. 인증 면제를 뜻하지 않습니다.
- 정상 흐름: ① 팀원이 ‘보고서 작성’을 입력 → ② 시스템이 생성 → ③ 같은 제목과 ‘할 일’ 상태를 결과로 제공.
- 사후 조건: 제목과 초기 상태가 있는 결과를 얻습니다. DB 저장이나 화면 표시는 보장하지 않습니다.
- 오류/대안 흐름: ①에서 제목이 `""`이면 생성 결과 대신 ‘제목은 필수’ 오류를 돌려줍니다. 예제는 데이터를 저장하지 않으므로 저장 취소(롤백)도 다루지 않습니다.

## 6. 인계와 변경

04에는 [요구사항 정본](../../../samples/web-task-system/docs/03-requirements.md)과 이 분석표를 함께 넘깁니다. 차단 미결은 이 교육 기준에서는 없으며 Q-04와 비기능 목표는 보류합니다. 실제 프로젝트의 검토·승인 근거는 없고, 수강생은 자기 답변으로 검토 상태를 정해야 합니다.

| 변경 대상 ID | 이전→변경 제안 | 이유·근거 | 영향받는 산출물 | 검토 상태 |
|---|---|---|---|---|
| R-03 | `""` 거부 → 공백만 있는 제목도 거부 | Q-04를 확장하는 연습 제안 | UC-01 오류 흐름, 명세 입력 규칙, 인수조건, 테스트, 구현 | 제안만 있음. 반영하지 않음 |

## 7. 작성 완료 점검과 해설

- 원문에 없던 초기값·오류 기준은 D-02·D-03으로 분리했습니다.
- 요구 확인 기준을 관찰 가능한 결과로 썼고, 기술 계약은 04로 넘겼습니다.
- 미결·비기능 한계를 숨기지 않았습니다. ‘미결 없음’과 ‘이번 단계 차단 미결 없음’은 다릅니다.
- 문서가 채워진 것과 실제 사람 승인은 다릅니다. 승인 칸이 필요하면 [빈 양식](TEMPLATE.md)에서 실제 근거를 입력합니다.
