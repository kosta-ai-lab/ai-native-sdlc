# 양식으로 요구사항을 쓰고 변경 영향 찾기 가이드

> 검증 기준: Claude Code 2.1.330(모델 Sonnet 5.5), 2026-11-24. 3장의 요청문은 이 환경에서 실제로 실행했고, 1·2·4단계의 ‘검증 실행에서 본 것’은 그 결과에서 옮겼습니다. AI의 응답은 실행마다 달라집니다.

## 이 단원이 말하려는 것

원요청은 “팀원이 처리할 업무를 할 일로 등록할 수 있게 해 주세요” 한 문장입니다. 이 문장을 주고 AI에게 양식을 채우게 하면 원문에 없는 질문과 요구까지 함께 나옵니다. 이 단원은 두 가지를 묻습니다. AI가 내놓은 것 가운데 **무엇이 정해진 요구인가**. 요구를 바꿔 달라는 요청이 오면 **무엇부터 하는가**.

AI가 쓴 초안은 승인 전까지 제안입니다. 그래서 누가 결정했는지를 양식에 적고, 내가 정하지 않은 것에는 ‘승인’이라고 쓰지 않습니다. 요구는 뒤 단계의 기준이므로, 고치기 전에 영향받는 곳부터 찾습니다.

이 답은 이 과정의 네 가지 원칙에서 나옵니다. 1~5단계는 넷 가운데 하나 이상을 연습합니다.

| 원칙 | 이 단원(양식과 변경 영향)에서는 |
|---|---|
| ① AI는 제안하고, 결정은 사람이 한다 | AI가 채운 양식은 승인 전까지 제안입니다. 사람이 답한 것만 결정 주체와 함께 결정으로 적고, 승인 근거가 없으면 ‘승인’이라고 쓰지 않습니다 |
| ② 말이 아니라 실행 결과로 확인한다 | AI가 점검 항목을 모두 `[x]`로 표시해도 사람이 확인한 것이 아닙니다. 그 표시는 지우고 직접 확인한 항목만 다시 표시합니다. 어떤 파일이 바뀌었는지는 `git status --short`와 `git diff --stat`의 출력으로 봅니다 |
| ③ 맡길수록 절차가 필요하다 | 한 문장짜리 요청을 맡기면 AI는 원문에 없는 범위까지 제안합니다. 그래서 빈 양식을 먼저 주고 원문, 가정, 미결 질문, 결정 제안을 나누어 적게 합니다 |
| ④ 앞 단계가 뒤 단계의 기준이다 | 요구는 명세, 인수조건, 테스트, 구현의 기준입니다. 그래서 변경 요청이 오면 요구를 고치기 전에 영향받는 곳부터 목록으로 만듭니다 |

그래서 이 단원의 단계는 네 마디로 나누어 적었습니다. 단계마다 해당하는 마디만 적었습니다.

- **맡긴다**: AI에게 하는 요청입니다. AI가 내놓는 것은 제안입니다.
- **확인한다**: 채워진 문서와 AI의 응답을 직접 읽는 일입니다.
- **정한다**: 읽은 것을 두고 사람이 내리는 판단입니다. 무엇을 결정으로 적을지, 무엇을 범위에서 뺄지, 변경을 받아들일지를 정합니다.
- **넘긴다 (산출물)**: 다음 단계의 기준이 되는 산출물입니다. 바뀐 파일을 보고 커밋하는 명령도 여기에 있습니다.

마디는 일하는 순서대로 놓았습니다. 2단계는 답을 정해 반영을 맡긴 다음 범위를 정해 표시를 맡기므로 ‘정한다’와 ‘맡긴다’가 두 번씩 나옵니다. AI에게 맡길 일이 없는 단계(0, 3, 5단계)에는 ‘맡긴다’가 없습니다. 0단계에는 직접 하는 준비를 ‘한다’에 적었습니다. 단계 제목 아래에는 그 단계에서 주로 연습하는 원칙을 적었습니다.

## 1. 질문을 먼저 하는 이유

원요청 “팀원이 처리할 업무를 할 일로 등록할 수 있게 해 주세요”에는 사용자 목적은 있지만 입력 규칙이나 완료 기준은 없습니다. AI에게 바로 구현을 시키면 로그인·DB·마감일 같은 기능까지 임의로 정할 수 있습니다. 요구사항 분석은 문장을 길게 만드는 작업이 아니라 **지금 결정해야 할 경계와 아직 모르는 것을 드러내는 작업**입니다.

유즈케이스(UC)는 행위자가 목표를 달성하는 상호작용을 순서대로 설명합니다. 요구사항(R)은 시스템이 지켜야 할 개별 조건입니다. [완성 예제](SAMPLE.md)처럼 UC-01의 생성 결과를 R-01(제목), R-02(초기 상태), R-03(빈 제목 거부)으로 나누면 하나의 흐름 안에서도 누락된 규칙을 확인할 수 있습니다.

| 구분 | 무엇을 기록하나 | 할 일 생성에서의 예 |
|---|---|---|
| 원문 사실 | 제공된 자료가 실제로 말한 내용 | “팀원이 처리할 업무를 할 일로 등록할 수 있게 해 주세요” |
| 가정 | 분석을 진행하기 위한 잠정 전제. 확인 전에는 확정 요구가 아님 | 제목은 문자열로 받는다고 가정 |
| 결정 | 선택한 안과 이유·결정 주체·근거·적용 범위 | 이번 실습은 함수 단위 생성만 다룸 |
| 미결 | 답이 없어 아직 선택할 수 없는 질문 | 공백만 있는 제목도 거부할까? |

AI가 “보통 그렇게 한다”고 답한 것은 사람의 결정 근거가 아닙니다. 미결은 숨기지 말고 **이번 구현을 막는지** 표시합니다. 보류한 항목이라도 영향이 크면 다음 단계로 넘기지 않습니다.

미결과 가정을 숨기지 않고 표시하는 방식은 NASA Systems Engineering Handbook 부록 C의 점검 항목과 취지가 같습니다. 부록 C.3은 정해지지 않은 값(TBD)을 줄이고, 최선의 추정값을 적어 ‘해소 필요(TBR)’로 표시하면서 이유, 해소할 방법, 책임자, 기한을 함께 적으라고 합니다. 가정은 기준선을 확정하기 전에 확인하라고 적습니다. 이 단원의 양식은 추정값을 적지 않고 ‘미결’로 남긴다는 점이 다릅니다.

## 2. 변경이 들어왔을 때

예: “공백만 있는 제목도 거부해 주세요.” 기존 ‘빈 제목’ 정의와 다른지 먼저 확인합니다. R-03 변경 제안 → 질문/결정 기록 → UC-01 오류 흐름 → 명세(모듈 04)의 입력 규칙·오류 계약 → 새 인수조건(모듈 05) → 실패하는 새 테스트와 구현(모듈 06) 순서로 영향 목록을 만듭니다. 문서만 고쳐 놓고 구현까지 바뀐 것처럼 표시하지 않습니다. 기존 ID는 유지하고 개정 이유와 검토 상태를 기록합니다.

## 3. 단계별 실습

작업 위치는 자기 실습 폴더입니다. 요청은 Claude Code에 그대로 입력합니다. 1·2·4단계의 ‘검증 실행에서 본 것’은 같은 요청을 두 번씩 실행해 얻은 결과입니다. 자기 결과는 문장도 항목 수도 다를 수 있습니다.

### 0단계 — 실습 폴더 준비하기

**목적:** 원요청과 빈 양식이 있는 실습 폴더를 만듭니다.

**한다**

강의 자료 저장소의 루트 폴더에서 아래 명령을 실행합니다. 저장소 안에서 실습하면 강의 자료가 바뀌므로 저장소 밖에 폴더를 만듭니다.

```bash
mkdir -p ~/work/task-create-requirements
cp modules/03-requirements/M02-template-and-change/INPUT.md ~/work/task-create-requirements/request.md
cp modules/03-requirements/M02-template-and-change/TEMPLATE.md ~/work/task-create-requirements/requirements.md
cd ~/work/task-create-requirements
git init
git add -A && git commit -m "chore: 원요청과 빈 양식"
claude
```

`claude`를 실행한 창은 그대로 두고, 터미널 창을 하나 더 열어 `cd ~/work/task-create-requirements`로 이동한 뒤 그 창에서 git 명령을 실행합니다. Claude Code가 파일을 만들거나 고쳐도 되는지 물으면 허용합니다.

**넘긴다 (산출물)**

`request.md`(원요청)와 `requirements.md`(빈 양식)가 있는 git 저장소.

**검토**

- [ ] `git status --short`가 아무것도 출력하지 않는다.
- [ ] `requirements.md`에 대괄호로 된 작성 안내가 그대로 있다.

### 1단계 — 양식 채우기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다. ③ 맡길수록 절차가 필요하다.

**목적:** 한 문장짜리 원요청에서 질문, 가정, 결정 제안, 요구 초안을 뽑아 양식에 채웁니다.

**입력:** `request.md`, 빈 양식 `requirements.md`.

**맡긴다**

```text
request.md를 분석해서 requirements.md의 빈 양식을 채워 줘. 양식의 구성과 표의 열은 바꾸지 마.
목적은 구현 전에 필요한 동작과 범위를 검토하는 것이다.
원문, 가정, 미결 질문, 결정 제안을 구분하고 요구 ID와 UC를 연결해 줘.
질문에는 답이 없을 때 어떤 요구의 확정이 막히는지도 적어 줘.
내가 제공하지 않은 답변·결정·승인 근거는 만들지 말고 제안으로 남겨 줘.
정상/오류 흐름, 확인 기준, 범위 제외, 비기능 조건도 빠뜨리지 말아 줘.
코드·다른 문서는 수정하지 말고, 마지막에 내가 판단해야 할 질문을 알려 줘.
```

**확인한다**

채워진 `requirements.md`를 읽습니다. 원문에 없는 내용이 어디에 어떤 표시로 들어왔는지 찾습니다.

**정한다**

아직 답하지 않습니다.

**넘긴다 (산출물)**

질문, 가정, 결정 제안, 요구 초안, 유즈케이스가 채워진 `requirements.md`.

```bash
git status --short        #  M requirements.md 한 줄만 나온다
git add -A && git commit -m "docs: 요구사항 초안"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `requirements.md`만 고쳤고 `request.md`는 그대로였습니다. 양식의 일곱 절과 표의 열을 유지했습니다.
- 한 문장짜리 원요청에서 질문이 10개와 9개, 요구가 14개와 9개 나왔습니다. 담당자 지정, 등록 권한, 중복 등록, 알림처럼 원문에 없는 내용이 질문이나 요구로 들어왔습니다. 대부분 ‘분석자 제안’ 또는 ‘제안’이라고 표시됐습니다. 다만 담당자 지정은 두 번 모두 원문의 ‘팀원이 처리할’을 근거로 적고, 필수 여부 같은 세부만 ‘제안’으로 표시했습니다.
- 결정은 두 번 모두 5개였습니다. 상태는 전부 ‘제안’이고 결정 주체와 근거 위치는 ‘[미제공]’이었습니다. 문서의 검토 상태는 ‘초안’, 사람 검토 근거는 ‘[미제공]’으로 남았습니다.
- 성능 같은 비기능 항목에는 수치를 만들지 않고 ‘[미제공]’이나 ‘미결’로 두었습니다.
- 한 번은 INPUT의 안내 문장(‘실제 업무 자료가 아니라…’)까지 원문으로 옮겨 적고, 이를 근거로 제약을 하나 붙였습니다.
- 양식의 ‘04’는 명세 단계(모듈 04)를 뜻합니다. 한 번은 Claude가 ‘04 단계’의 파일 이름을 알려 달라고 되물었습니다.
- 두 번 모두 6절(인계와 변경)까지 채웠고, 7절의 점검 항목 네 개를 모두 `[x]`로 표시했습니다. 이 표시는 사람이 확인한 것이 아닙니다. 5단계에서 다시 봅니다.

**검토**

- [ ] `git diff HEAD~1 -- request.md`가 아무것도 출력하지 않는다. 원문이 바뀌지 않았다.
- [ ] 결정의 상태가 모두 ‘제안’이고, 결정 주체나 승인 근거가 지어져 있지 않다.
- [ ] 원문에 없는 요구에는 그 사실이 표시되어 있다.
- [ ] 응답 시간 같은 수치가 근거 없이 적혀 있지 않다.

### 2단계 — 답을 반영하고 범위 좁히기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 사람이 답한 것만 결정으로 기록하고, 이번에 다룰 범위를 좁힙니다.

**입력:** 1단계의 `requirements.md`.

**정한다**

질문을 읽고 자기 답과 이유를 정합니다. 정하지 못한 것은 답하지 않고 둡니다.

**맡긴다**

아래는 검증 실행에서 쓴 답입니다. [SAMPLE](SAMPLE.md)의 예제 조건과 같은 선택입니다. 첫 줄은 그대로 두고 항목은 자기 답으로 바꿔 씁니다. 예제와 나란히 비교하려면 그대로 써도 됩니다.

```text
질문에 대한 내 답은 다음과 같아. 이 답의 범위만 requirements.md에 반영해 줘. 결정 주체는 "실습자 본인"으로 적고, 내가 답하지 않은 질문은 미결로 남겨 줘. 내가 말하지 않은 승인 기록은 만들지 마.
- 등록할 정보는 제목뿐이다. 이번에는 함수 하나로 생성만 다루는 작은 예제이기 때문이다.
- 생성 직후 상태는 "할 일"이다. 시작 상태를 하나로 정해 두어야 결과를 확인할 수 있기 때문이다.
- 빈 문자열 제목은 거부하고 "제목은 필수" 오류를 돌려준다.
- 저장, 로그인, 웹 화면은 이번 범위에서 뺀다.
- 공백만 있는 제목을 어떻게 할지는 아직 정하지 않았다.
```

**정한다**

반영된 문서를 읽고, 남아 있는 AI의 제안을 하나씩 정리합니다. 이번 범위에 넣지 않을 요구는 지우거나 ‘범위 밖’으로 표시하게 합니다. AI가 “보통 그렇게 한다”고 답한 것은 결정의 근거가 아닙니다.

**맡긴다**

아래는 검증 실행에서 쓴 요청입니다. 요구 번호는 자기 문서에 맞게 바꿉니다.

```text
R-04, R-06, R-07은 이번 범위에 넣지 않을게. 지우지 말고 상태 칸에 "범위 밖"이라고 표시해 줘. 다른 곳은 고치지 마.
```

**넘긴다 (산출물)**

내 답이 결정으로 기록되고, 답하지 않은 것은 미결로 남은 `requirements.md`.

```bash
git diff --stat           # requirements.md만 바뀌었는지 본다
git add -A && git commit -m "docs: 답 반영"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `requirements.md`만 고쳤습니다. 내 답은 결정 표에 결정 주체 ‘실습자 본인’으로 기록됐고, 문서의 검토 상태는 ‘초안’ 그대로였습니다. 한 번은 결정의 상태 칸에 ‘답변 반영. 별도 승인 기록 없음’이라고 적었습니다.
- ‘공백만 있는 제목’은 두 번 모두 미결로 기록됐습니다. 1단계 초안에는 두 번 모두 ‘공백뿐인 제목도 거부한다’가 요구에 들어 있었는데, 내 답에 따라 미결로 바뀌었습니다.
- 이유를 말하지 않은 두 답(빈 문자열 거부, 범위 제외)은 이유 없이 기록됐습니다. 이유를 남기려면 답할 때 함께 말합니다.
- 내가 답하지 않은 AI의 제안(담당자 지정, 중복 등록 등)은 ‘제안’으로 남았습니다. 내 답과 부딪히는 곳에는 ‘충돌 여지’, ‘재검토’ 같은 표시가 붙었습니다.
- 요구는 여전히 14개와 9개였습니다. 범위에서 뺀 내용과 관련된 요구도 지워지지 않고 표시만 붙은 채 남았습니다. 예제는 요구가 3개입니다. 범위를 좁히는 일은 사람이 해야 합니다.
- 범위를 좁히는 요청은 한 번 실행했습니다. 요구 세 개의 상태 칸만 ‘범위 밖’으로 바뀌었습니다(3줄 변경). Claude는 그 요구들이 유즈케이스의 관련 요구 ID와 오류 흐름, 6절, 질문 설명에 아직 남아 있어 요구 표와 맞지 않을 수 있다고 알렸습니다. 한 곳만 고치면 문서 안에서 어긋나는 곳이 생깁니다.

**검토**

- [ ] 결정 주체가 ‘실습자 본인’인 결정은 내가 답한 것뿐이다.
- [ ] 문서의 검토 상태가 ‘승인’으로 바뀌어 있지 않다.
- [ ] 미결로 남은 질문마다 어떤 요구의 확정이 막히는지 적혀 있다.
- [ ] 이번 범위에 넣지 않을 요구를 지우거나 표시했다.

### 3단계 — 예제와 비교하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 문구가 아니라 판단 근거와 빠진 것을 기준으로 자기 문서를 점검합니다.

**입력:** 자기 `requirements.md`, [SAMPLE](SAMPLE.md).

**확인한다**

아래 표의 순서로 두 문서를 나란히 읽습니다. 예제는 표 제목의 괄호 안내를 빼고 6절과 7절을 문단으로 풀어 썼습니다. 이런 형식 차이는 비교 대상이 아닙니다.

| 볼 곳 | 예제의 선택 | 내 문서에서 확인할 것 |
|---|---|---|
| 범위 | D-01: 제목으로 생성하는 함수만 다룬다 | 범위 밖의 요구가 확정된 것처럼 남아 있지 않은가 |
| 초기 상태 | D-02 → R-02: 새 할 일의 상태는 ‘할 일’ | 정상 흐름의 결과에 초기 상태가 있는가 |
| 빈 제목 | D-03 → R-03, UC-01 오류 흐름: `""`이면 ‘제목은 필수’ 오류 | 오류 흐름이 어느 단계에서 갈라지는지 적혀 있는가 |
| 공백 제목 | Q-04: 미결로 둔다 | 정하지 않은 것을 정한 것처럼 쓰지 않았는가 |
| 확인 기준 | 요구마다 입력과 관찰할 결과 | 요구마다 확인 기준이 있는가. 함수 이름 같은 구현 계약이 섞여 있지 않은가 |
| 승인 | ‘예제 기준, 실제 프로젝트 승인 아님’ | 승인 근거 없이 ‘승인’이라고 적혀 있지 않은가 |

**정한다**

예제에 없는 요구를 냈다고 해서 틀린 것은 아닙니다. 지우기 전에 목적, 범위, 근거를 먼저 확인합니다.

**넘긴다 (산출물)**

예제와 다른 곳과 그 이유를 적은 메모(실습 폴더 밖에 둡니다). `requirements.md`를 고쳤으면 `git add -A && git commit -m "docs: 예제와 비교해 수정"`으로 커밋합니다.

**검토**

- [ ] 예제와 다른 요구마다 남긴 이유나 지운 이유를 말할 수 있다.
- [ ] 요구 하나가 테스트 하나와 꼭 대응하지는 않는다는 것을 확인했다. 작은 사례의 [인수조건](../../../samples/web-task-system/docs/05-acceptance.feature)에서 ‘제목이 있는 할 일을 만든다’ 시나리오 하나가 R-01과 R-02를 함께 확인한다.

### 4단계 — 변경 영향 찾기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 변경 요청을 바로 반영하지 않고, 무엇이 바뀌는지 먼저 목록으로 만듭니다.

**입력:** 자기 `requirements.md`.

**맡긴다**

```text
"공백만 있는 제목도 거부해 주세요"라는 변경 요청이 들어왔어. 아직 승인된 변경이 아니야.
requirements.md를 읽고 이 변경이 영향을 주는 요구 ID와 유즈케이스 흐름, 그리고 뒤 단계의 명세·인수조건·테스트·구현에서 바뀔 곳을 목록으로 만들어 줘.
requirements.md의 변경 표에 제안으로만 기록하고, 요구와 유즈케이스의 본문은 고치지 마.
```

**확인한다**

영향 목록을 읽고 빠진 곳이 없는지 봅니다.

**정한다**

변경을 받아들일지는 사람이 정합니다. 받아들인다면 결정을 먼저 기록하고, 그다음에 요구와 유즈케이스를 고칩니다. 기존 ID는 유지합니다.

**넘긴다 (산출물)**

변경 표에 제안 한 줄이 더해진 `requirements.md`와, Claude Code의 응답에 나온 영향 목록. 영향 목록은 파일에 저장되지 않으므로 남기려면 복사해 둡니다.

```bash
git diff --stat           # requirements.md 한 파일, 한 줄 추가
git add -A && git commit -m "docs: 변경 제안 기록"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 변경 표에 한 줄만 더했고 상태는 ‘제안(미승인)’이었습니다. 요구와 유즈케이스의 본문은 고치지 않았습니다.
- 두 번 모두 직접 영향을 받는 곳으로 R-03과 UC-01의 오류 흐름을 들었습니다. 뒤 단계의 명세, 인수조건, 테스트, 구현에서 바뀔 곳도 함께 적었고, 승인되면 새 결정이 필요하다고 했습니다.
- 두 번 모두 제목의 공백을 다듬는 문제를 짚었습니다. 한 번은 앞뒤 공백을 다듬어 돌려주면 ‘입력한 제목이 그대로 나타난다’는 요구와 부딪힌다고 적었습니다. 공백만 있는 제목을 거부하는 변경이 유효한 제목의 처리 방식까지 건드린다는 뜻입니다.

이 변경을 실제로 구현하는 과정은 [모듈 06 단원 M02](../../06-coding-tdd/M02-tdd-rules/README.md)에 있습니다. 그 단원의 실습 출발점에는 ‘제목 앞뒤 공백은 제거한다’와 ‘공백만 있는 제목은 거부한다’ 시나리오가 인수조건에 더해져 있습니다.

**검토**

- [ ] 변경 표의 상태가 ‘제안’이고, 요구 본문은 바뀌지 않았다.
- [ ] 영향 목록에 요구, 유즈케이스, 명세, 인수조건, 테스트, 구현이 모두 있다.
- [ ] 문서만 고쳐 놓고 구현까지 바뀐 것처럼 표시하지 않았다.

### 5단계 — 다음 단계로 넘기기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ② 말이 아니라 실행 결과로 확인한다. AI가 한 `[x]` 표시는 사람이 확인한 결과가 아닙니다.

**목적:** 요구, 가정, 미결, 검토 상태를 함께 넘겨 다음 단계가 빈칸을 추측하지 않게 합니다.

**확인한다**

양식 6절(인계와 변경)과 7절(작성 완료 점검)을 직접 다시 확인합니다. AI가 한 `[x]` 표시는 지우고, 직접 확인한 항목만 다시 표시합니다.

**정한다**

명세의 확정을 막는 미결이 있으면 그 요구는 넘기지 않고 보류합니다. 초안을 검토해 달라고 요청할 수는 있지만, 사람의 승인 근거가 없으면 ‘승인’이라고 쓰지 않습니다.

**검토**

- [ ] 원요청과 재서술을 구분했고, 원문 위치를 찾을 수 있다.
- [ ] 가정, 미결, 사람의 결정이 구별되고, 승인 근거가 없는 것은 ‘제안’이나 ‘검토 대기’로 남아 있다.
- [ ] 포함과 제외, 비기능 조건이 있고, 모르는 목표값은 확정하지 않았다.
- [ ] 요구 ID마다 확인 기준이 있고 UC의 정상 흐름과 오류 흐름에 연결된다.
- [ ] 명세의 확정을 막는 질문과 범위 밖의 질문을 구별했다.

같은 요구가 뒤 단계로 이어진 모습은 저장소의 작은 사례에서 볼 수 있습니다. [요구사항](../../../samples/web-task-system/docs/03-requirements.md), [명세](../../../samples/web-task-system/docs/04-spec.md), [인수조건](../../../samples/web-task-system/docs/05-acceptance.feature), [테스트](../../../samples/web-task-system/test/todo.test.ts), [구현](../../../samples/web-task-system/src/todo.ts)입니다. 테스트와 구현을 직접 만드는 실습은 [모듈 06 단원 M01](../../06-coding-tdd/M01-red-green-refactor/README.md)에 있습니다.

## 4. 양식의 절마다 판단할 것

3장의 단계에서 문서를 읽고 고칠 때 아래 기준을 씁니다.

**입력으로 쓸 수 있는 것:** 원요청 원문, 업무 흐름·용어 자료(있을 때), 기존 요구사항·코드(있을 때), 제약과 사람의 답변. 없는 문서나 답변은 ‘미제공’으로 둡니다. 기존 코드가 있으면 현재 동작의 근거로 읽되, 사용자가 원한 동작의 증거로 삼지는 않습니다.

### 원요청과 목적 (1절)

원문과 분석자의 재서술을 나란히 둡니다. 원문은 고치지 않습니다. 사용자의 목표, 행위자, 기대 결과를 한 문장씩 적고 뜻이 분명하지 않은 낱말을 표시합니다. ‘빈 제목’처럼 경계가 중요한 낱말부터 질문합니다.

### 질문·가정·결정 (2절)

질문마다 관련 요구, 선택지, 영향, 답변 상태를 적습니다. AI는 선택지와 장단점을 제안할 수 있지만 답변자 이름, 승인 시각, 결정 근거를 만들어서는 안 됩니다. 실제 답변을 받으면 그 답변을 근거로 결정 행을 고칩니다. 답변을 받지 못하면 가정이나 미결로 둡니다. [예제](SAMPLE.md)에서 저자가 정한 조건은 승인 절차를 설명하려고 만든 것입니다. 자기 문서의 승인 기록으로 옮겨 적지 않습니다.

### 범위와 비기능 조건 (3절)

기능 요구는 무엇을 할 수 있어야 하는지를 나타냅니다. 비기능 요구는 성능, 보안, 신뢰성 같은 품질을 어떤 조건에서 어느 수준으로 갖춰야 하는지를 나타냅니다. ‘빨라야 한다’ 대신 측정 대상, 부하, 상한, 측정 방법을 확인합니다. 숫자를 모르면 AI가 응답 시간 목표를 지어내지 않게 합니다.

이 단원의 함수 예제는 UI, 저장, 인증, 상태 변경을 구현하지 않습니다. 운영 시스템에 필요 없다는 판단이 아니라 이번 학습 범위 밖이라는 뜻입니다. 실제 프로젝트에 개인정보나 인증 문제가 있으면 ‘제외’라고만 적고 넘어가지 않습니다. 담당자의 판단과 그 문제가 진행을 막는지를 함께 기록합니다.

### 요구사항 (4절)

한 행에 판단 단위 하나를 쓰고 ID를 붙입니다. 이미 쓰고 있는 ID는 번호를 다시 매기지 않습니다. 관찰할 수 있는 결과로 적되, 이 단계에서 함수 이름이나 DB 종류를 필요 없이 고정하지 않습니다. ‘제목이 있는 할 일을 생성할 수 있다’는 요구이고, `createTodo({ title })`라는 함수 계약은 모듈 04에서 구체화할 명세입니다.

확인 기준에는 정상 입력, 초기 상태, 거부 입력과 기대 결과를 적습니다. 요구 하나가 반드시 테스트 하나인 것은 아닙니다.

### 유즈케이스 (5절)

행위자·목표·사전 조건, 정상 흐름, 사후 조건, 오류 흐름의 순서로 읽습니다. 정상 흐름은 성공할 때의 순서입니다. 오류 흐름에는 어느 단계에서 어떤 조건으로 갈라지는지를 적습니다. 인증을 다루지 않는 함수 예제의 ‘사전 조건 없음’을 운영 서비스에 접근 통제가 필요 없다는 뜻으로 읽지 않습니다.

### 인계와 변경 (6절)

원문에서 결정, 요구, 유즈케이스로 이어지는 연결을 읽으며 원문에 없는 선택에 근거가 있는지 확인합니다. 진행을 막는 미결이 있으면 그 미결에 걸린 요구는 다음 단계로 넘기지 않고 보류합니다. 초안을 검토해 달라고 요청할 수는 있지만, 사람이 승인한 근거가 없으면 ‘승인’이라고 쓰지 않습니다. 요구, 가정, 미결, 승인 상태를 함께 넘겨야 다음 단계가 빈칸을 추측하지 않습니다.

## 5. 자주 막히는 곳

| 증상 | 확인하고 고칠 것 |
|---|---|
| 한 문장 요청인데 요구가 10개가 넘는다 | AI가 원문에 없는 범위까지 제안한 것입니다. 2단계에서 이번에 다룰 범위를 답하고, 넣지 않을 요구를 지우거나 표시합니다 |
| 양식의 절이나 표의 열이 바뀌었다 | `git diff`로 확인합니다. `git checkout -- requirements.md`로 되돌린 뒤 “양식의 구성과 표의 열은 바꾸지 마”를 넣어 다시 요청합니다. 마지막 커밋 뒤에 고친 내용이 모두 사라지므로 남길 변경은 먼저 따로 적어 둡니다 |
| 결정 주체나 승인자가 채워져 있다 | 내가 말하지 않은 사람이나 승인은 지웁니다. 상태를 ‘제안’으로 되돌립니다 |
| 변경 요청을 했더니 요구 본문이 바뀌었다 | 승인 전에 반영된 것입니다. `git checkout -- requirements.md`로 되돌리고, 변경 표에만 제안으로 기록하게 합니다. 마지막 커밋 뒤에 고친 내용이 모두 사라지므로 남길 변경은 먼저 따로 적어 둡니다 |
| Claude Code가 스크립트(python 등)를 실행해도 되는지 묻는다 | 검증 실행의 2단계에서 두 번 모두 먼저 스크립트로 한꺼번에 고치려 했고, 실행되지 않자 편집 도구로 `requirements.md`를 직접 고쳤습니다. 거절하고 파일을 직접 고쳐 달라고 해도 됩니다. 허용했다면 `git status --short`로 다른 파일이 생기지 않았는지 봅니다 |
| `git commit`이 “Author identity unknown”으로 실패한다 | `git config --global user.name "이름"`과 `git config --global user.email "메일 주소"`를 먼저 실행합니다 |
