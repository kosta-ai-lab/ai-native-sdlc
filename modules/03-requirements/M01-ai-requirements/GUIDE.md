# AI 요구사항 분석 가이드

> 검증 기준: Claude Code 2.1.330(모델 Sonnet 5.5), 2026-11-24. 3장의 요청문은 이 환경에서 실제로 실행했고, 1~4단계의 ‘검증 실행에서 본 것’은 그 결과에서 옮겼습니다. AI의 응답은 실행마다 달라집니다.

## 이 단원이 말하려는 것

“할 일을 적고 완료 표시도 하고 싶다”는 말을 AI에게 전하면 앱은 나올 수 있습니다. 말로 시켜서 바로 만들어 보는 것은 좋은 출발점입니다. 이 단원은 그다음 걸음을 다룹니다. 물음은 하나입니다. 요구사항을 정리할 때 **무엇을 AI에게 맡기고 무엇을 사람이 정하는가**.

AI는 요청에서 빠진 것을 찾아 질문으로 내놓는 일을 잘합니다. 초안까지 맡겨도 됩니다. 질문에 답하고 범위를 정하는 일, 초안을 읽고 받아들일지 정하는 일은 사람이 합니다. 사람이 정한 것만 요구사항입니다.

이 답은 이 과정의 네 가지 원칙에서 나옵니다. 1~5단계에서는 단계마다 넷 가운데 하나 이상을 연습합니다.

| 원칙 | 이 단원에서는 |
|---|---|
| ① AI는 제안하고, 결정은 사람이 한다 | 질문과 추천, 요구사항 초안, 초안을 검토한 지적은 AI가 냅니다. 어느 답을 고를지, 어느 지적을 받아들일지는 사람이 정합니다. 답하지 않은 질문은 미정으로 남깁니다 |
| ② 말이 아니라 실행 결과로 확인한다 | AI가 “됐습니다”라고 해도 질문과 답을 적는 `questions.md`와 요구사항을 적는 `requirements.md`를 직접 열어 읽습니다. 어떤 파일이 바뀌었는지는 `git status --short`와 `git diff --stat`의 출력으로 봅니다 |
| ③ 맡길수록 절차가 필요하다 | 질문 정리, 답 기록, 초안 작성, 검토, 반영을 한 번에 하나씩 맡깁니다. 요청마다 “질문 정리까지만”, “수정은 아직 적용하지 마”처럼 범위를 정합니다. 초안을 맡기기 전에 사람의 답을 먼저 `questions.md`에 남깁니다 |
| ④ 앞 단계가 뒤 단계의 기준이다 | 원요청과 사람의 답이 요구사항의 기준이 됩니다. 요구사항은 모듈 04에서 명세를 쓸 때의 근거가 됩니다 |

그래서 이 단원의 단계는 네 마디로 나누어 적었습니다. 해당하는 일이 없는 마디는 뺐습니다.

- **맡긴다**: AI에게 하는 요청입니다. AI가 내놓는 것은 제안입니다.
- **확인한다**: AI가 만든 파일을 직접 열어 읽고, 명령을 직접 실행해 출력을 보는 일입니다.
- **정한다**: 확인한 것을 보고 사람이 내리는 판단입니다. 어느 답을 고를지, 무엇을 미정으로 둘지, 어느 지적을 받아들일지를 정합니다.
- **넘긴다 (산출물)**: 다음 단계의 기준이 되는 산출물입니다. 바뀐 파일을 보고 커밋하는 명령도 여기에 있습니다.

마디는 일하는 순서대로 놓았습니다. 2단계에서는 사람이 답을 먼저 정한 뒤에 기록을 맡기므로 ‘정한다’가 앞에 옵니다. 4단계에서는 검토와 반영을 따로 맡기므로 ‘맡긴다’가 두 번 나오고, 그 사이에 ‘확인한다’와 ‘정한다’가 있습니다. AI에게 맡길 일이 없는 단계(0, 5단계)에는 ‘맡긴다’ 대신 직접 하는 일을 적은 ‘한다’가 있습니다. 단계 제목 아래에는 그 단계에서 주로 연습하는 원칙을 적었습니다.

## 1. 요구사항을 먼저 정리하는 이유

할 일을 추가하는 버튼이 있다는 사실만으로 사용자가 원하는 앱이라고 할 수는 없습니다. 사용자는 다시 접속해서 남은 일을 보고 싶었는데, 개발자는 화면에 잠깐 표시하는 기능만 만들었을 수 있습니다. 요구사항은 **사용자에게 필요한 능력과 시스템이 지켜야 할 조건을 함께 이해하기 위한 기준**입니다. 기술을 먼저 고르면 사용자의 필요를 그 기술에 맞춰 해석하기 쉽습니다.

### 요구사항의 종류와 좋은 요구사항의 조건

IREB의 [CPRE 용어집](https://cpre.ireb.org/en/downloads-and-resources/glossary)은 시스템의 결과·행동을 다루는 기능 요구, 품질에 관한 요구, 가능한 해결 방법을 제한하는 제약을 구별합니다. 예를 들어 ‘할 일을 삭제한다’는 기능 요구이고, ‘키보드만으로 추가·완료·삭제할 수 있다’는 접근성에 관한 품질 요구입니다. ‘서버로 데이터를 전송하지 않는다’는 이 예제의 해결 범위를 제한합니다. 반면 ‘localStorage를 사용한다’는 아직 선택하지 않아도 되는 구현 방법입니다. 요구의 목적과 기술 선택을 분리하면 같은 요구를 두고 여러 설계를 비교할 수 있습니다.

**요구사항의 종류와 요구사항 문장의 품질은 다른 문제**입니다. 기능 요구라도 ‘편리하게 관리한다’라고 쓰면 사람마다 다르게 구현합니다. NASA Systems Engineering Handbook [Appendix C, C.2~C.4](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)는 한 문장의 단일한 의미, 가정의 명시, 일관성, 필요성·추적성, 시험·시연·검사 등으로 확인할 수 있는지를 점검합니다. 우주 시스템용 점검표 전체를 이 작은 앱에 적용하는 것은 아닙니다. 여기서는 다음처럼 읽는 사람에 따라 구현과 합격 판단이 달라지는 문장을 고치는 데 사용합니다.

| 초안 | 부족한 점 | 확인 가능하도록 고친 예 |
|---|---|---|
| 데이터를 안전하게 보관한다 | 언제, 무엇이 남는지 알 수 없습니다 | 같은 브라우저에서 페이지를 새로 고치면 제목·완료 상태·목록 순서가 유지된다. |
| 남은 개수를 보여 준다 | 필터 기준인지 전체 기준인지 알 수 없습니다 | 필터와 관계없이 전체 목록의 미완료 항목 수를 표시한다. |
| 빠르게 추가한다 | 조건과 측정 기준이 없습니다 | 속도 요구가 실제로 필요한지 먼저 질문합니다. 근거 없이 응답 시간 수치를 만들지 않습니다. |

이 문장들은 이 수업에서 만든 적용 예입니다. NASA가 할 일 앱의 저장 방식이나 개수 기준을 정한 것은 아닙니다.

### 사용자 스토리·유즈케이스·인수조건의 차이

IREB 용어집의 User story는 사용자의 필요와 기대 이익을 짧게 표현하고, Use case는 외부 행위자와 시스템 사이에서 이익을 제공하는 가능한 상호작용을 다룹니다. 인수조건은 결과를 받아들일지 판단할 조건입니다. 서로 대체하는 양식이 아니라 **목적 → 상호작용 → 합격 판단**을 다른 깊이에서 표현합니다.

- **사용자 스토리:** ‘개인 사용자로서 남은 일을 잊지 않도록 할 일을 등록하고 싶다.’ 왜 필요한지 말하지만 빈 입력을 어떻게 처리할지는 아직 모릅니다.
- **유즈케이스:** 사용자가 제목을 입력하고 추가하면 시스템이 검사·등록·표시합니다. 공백뿐이면 등록 대신 오류 안내로 갈라집니다. 정상과 예외의 흐름을 읽습니다.
- **인수조건:** ‘목록이 비어 있을 때 “보고서 작성”을 추가하면 미완료 항목 한 개와 남은 개수 1이 보인다.’ 실제로 무엇을 보고 합격시킬지 정합니다.

Given(사전 상태)·When(행동)·Then(관찰 결과)은 인수조건을 적는 한 방법입니다. 위 예에서 사전 상태를 빼면 기존 항목 수를 몰라 남은 개수 1이 맞는지 판단할 수 없습니다. 모든 스토리와 모든 요구를 반드시 일대일로 만들 필요는 없습니다. 새 항목의 초기 상태처럼 여러 흐름에서 쓰는 규칙도 있습니다.

### 도출·분석·검증의 반복

**도출**은 원문·관찰·사용자 대화에서 필요를 찾아 모으는 일입니다. **분석**은 그 필요의 의미와 관계를 이해하고 범위·충돌·미정을 정리하는 일입니다. **검증**에서는 문장이 잘 쓰였는지와 실제 필요를 맞게 담았는지를 모두 살핍니다. 용어를 더 엄밀히 구분하면 전자는 verification, 후자는 validation입니다. IREB 용어집은 이 둘을 구별합니다. NASA의 소프트웨어 공학 요구사항 [NPR 7150.2D 4.1.7(SWE-055)](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter4)도 요구사항 validation의 목적을 ‘소프트웨어가 고객의 환경에서 의도한 대로 동작하도록 보장하는 것’으로 적습니다. 문장이 잘 쓰였는지만 보는 일이 아니라는 뜻입니다. 다만 NASA 자료는 문장 품질 점검까지 validation이라고 부릅니다. 용어의 경계는 자료마다 다릅니다.

이 실습에서는 문서를 읽으며 ‘완료 필터에서도 전체 미완료 수가 보이는가’를 따져 봅니다. 사용자가 그 표시를 혼동한다면 문장을 정확히 구현했더라도 요구를 다시 논의할 수 있습니다. 테스트 가능성과 사용자에게 적합함은 같은 판정이 아닙니다.

AI는 누락 질문·상충 조건·수정안을 빠르게 **제안**할 수 있습니다. 하지만 사용자 의도나 범위를 승인할 당사자는 아닙니다. AI의 ‘보통은 이렇게 합니다’를 원요청 사실로 바꾸지 말고, 이유를 읽은 사람이 결정하거나 확인할 질문으로 남깁니다.

## 2. 해설 예제 — ‘계속 남아 있어야 한다’에서 물을 것

원요청이 ‘브라우저를 닫았다 열어도 남아 있어야 한다’라면 서버 저장, 계정 동기화, 같은 브라우저 안의 저장 모두 후보가 될 수 있습니다. 여기서 곧바로 DB를 정하지 않습니다.

1. **필요 확인:** 다른 기기에서도 이어서 쓰려는가, 이 브라우저에서만 이어 쓰려는가?
2. **범위 결정:** 예제에서는 개인의 같은 브라우저·같은 주소에서 이어 쓰기로 정합니다. 로그인·동기화는 제외합니다.
3. **요구 작성:** 정상 저장된 목록은 새로 고침과 브라우저 재실행 뒤에도 제목·완료 상태·순서가 유지됩니다. 브라우저 데이터 삭제까지 복구하는 요구는 아닙니다.
4. **실패 질문:** 브라우저가 저장을 거부하면 성공으로 보이게 해도 되는가? 예제에서는 기존 표시를 유지하고 저장 실패를 알리기로 합니다.
5. **다음 단계:** 04에서는 이 요구를 어떤 데이터 모델·저장 경계·실패 처리로 지킬지 설계합니다.

위 결정은 비교용입니다. 자기 실습에서는 아래 0단계부터 따라 한 뒤 [SAMPLE](SAMPLE.md)과 비교합니다.

## 3. 단계별 실습

작업 위치는 자기 실습 폴더입니다. 요청은 Claude Code에 그대로 입력합니다. 요청마다 결과를 읽고 필요한 대화를 이어 가며, 다음 단계에는 수정한 자기 파일을 사용합니다. 1~4단계의 ‘검증 실행에서 본 것’은 같은 요청을 두 번씩(4단계의 반영 요청은 한 번) 실행해 얻은 결과입니다. 자기 결과는 문장도 항목 수도 다를 수 있습니다.

### 0단계 — 실습 폴더 준비하기

**목적:** AI가 만들고 고친 파일을 바로 확인할 수 있는 실습 폴더를 만듭니다.

**한다**

강의 자료 저장소의 루트 폴더에서 아래 명령을 실행합니다. 저장소 안에서 실습하면 강의 자료가 바뀌므로 저장소 밖에 폴더를 만듭니다.

```bash
mkdir -p ~/work/my-todo-requirements
cp modules/03-requirements/M01-ai-requirements/INPUT.md ~/work/my-todo-requirements/request.md
cd ~/work/my-todo-requirements
git init
git add -A && git commit -m "chore: 원요청"
claude
```

`git`은 AI가 어떤 파일을 만들고 고쳤는지 확인하는 데 씁니다. `claude`를 실행한 창은 그대로 두고, 터미널 창을 하나 더 열어 `cd ~/work/my-todo-requirements`로 이동한 뒤 그 창에서 git 명령을 실행합니다. 단계가 끝날 때마다 `git status --short`로 바뀐 파일을 보고 커밋합니다. Claude Code가 파일을 만들거나 고쳐도 되는지 물으면 허용합니다.

**넘긴다 (산출물)**

`request.md` 한 파일이 있는 git 저장소.

**검토**

- [ ] `git status --short`가 아무것도 출력하지 않는다.
- [ ] `request.md`의 내용이 [INPUT](INPUT.md)과 같다.

### 1단계 — 질문과 범위를 정리하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 원요청에서 이미 정해진 내용과 구현 전에 정해야 할 내용을 가릅니다.

**입력:** `request.md`.

**맡긴다**

```text
request.md를 읽고 개인용 할 일 웹 앱의 요구사항 분석을 시작해 줘.
원문에서 확인한 내용과 추가 확인이 필요한 내용을 구별하여 questions.md에 정리해 줘.
질문에는 답에 따라 달라지는 사용자 동작이나 범위를 설명하고, 선택지와 추천 이유를 제안해 줘.
이번에는 질문 정리까지만 해 줘.
```

**확인한다**

`questions.md`를 열어 읽습니다. 원문에 이미 답이 있는 내용을 다시 묻고 있지 않은지 확인합니다. 제목의 빈 값·길이·중복, 삭제 확인, 남은 개수의 기준, 저장 실패처럼 답에 따라 동작이 달라지는 질문이 들어 있는지 봅니다. 답은 아직 하지 않습니다. 2단계에서 정합니다.

**넘긴다 (산출물)**

원문에서 확인한 내용, 질문, 선택지, AI의 추천이 담긴 `questions.md`.

```bash
git status --short        # ?? questions.md 한 줄만 나온다
git add -A && git commit -m "docs: 질문 정리"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `questions.md` 하나만 만들었고 `request.md`는 고치지 않았습니다.
- 원문에서 확인한 내용은 16개와 13개, 질문은 15개와 12개였습니다. 질문마다 선택지와 추천이 붙었습니다.
- 원문이 미정이라고 밝힌 네 가지(입력 길이, 중복, 삭제 확인, 저장 실패) 말고도 질문이 더 나왔습니다. 데이터를 어디에 보관하는지, ‘외부 서버로 전송하지 않는다’의 범위가 어디까지인지, 어떤 기기와 브라우저에서 쓰는지, 원문에 없는 기능(항목 수정 등)을 범위에서 뺄지는 두 번 모두 물었습니다.
- 한 번은 ‘localStorage와 IndexedDB 가운데 무엇을 쓸까’처럼 구현 방법을 고르는 질문이 섞여 있었습니다. 이것은 요구가 아니라 설계 선택입니다. 여기서 답하지 않고 04로 넘깁니다.

**검토**

- [ ] 원문에 있는 사실과 AI의 추천이 구별되어 있다.
- [ ] ‘개인용’이 팀 공유로 바뀌는 것처럼 원문과 어긋나는 내용이 없다.
- [ ] 구현 방법을 고르는 질문을 찾아 표시해 두었다.

### 2단계 — 답을 정하고 기록하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다.

**목적:** 질문에 사람이 답하고, 그 답을 AI의 추천과 구별되게 남깁니다.

**입력:** `questions.md`.

**정한다**

질문을 읽고 자기 답을 정합니다. 모르면 결정한 척하지 않고 답하지 않은 채로 둡니다.

**맡긴다**

답은 Claude에게 말해 기록하게 합니다. 아래는 검증 실행에서 쓴 답입니다. 자기 답으로 바꿔 쓰고, 이유도 함께 적습니다.

```text
질문에 대한 내 답은 다음과 같아. questions.md의 해당 질문에 결정과 이유로 기록해 줘. 내가 답하지 않은 질문은 추천안을 채택하지 말고 미정으로 남겨 줘.
- 제목: 앞뒤 공백은 제거한다. 빈 제목과 공백만 있는 제목은 거부한다. 길이는 1~200자다. 같은 제목은 허용한다.
- 순서: 추가한 순서로 표시한다. 새 항목은 미완료다.
- 삭제: 확인 창과 되돌리기는 이번에 넣지 않는다.
- 남은 개수: 필터와 관계없이 전체 목록의 미완료 수다.
- 보존: 같은 브라우저, 같은 주소에서만 이어 쓴다. 다른 기기와의 동기화는 필요 없다.
- 저장 실패: 변경 전 목록을 그대로 두고 한국어로 실패를 알린다.
```

**넘긴다 (산출물)**

질문마다 결정과 이유, 또는 미정이 적힌 `questions.md`.

```bash
git diff --stat           # questions.md만 바뀌었는지 본다
git add -A && git commit -m "docs: 질문에 답을 기록"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `questions.md`만 고쳤습니다. 답하지 않은 질문은 추천안을 채택하지 않고 미정으로 남겼습니다. 한 번은 질문 12개 가운데 7개가 결정, 5개가 미정이 됐습니다.
- 답이 질문의 일부에만 해당하면 남은 부분을 미정으로 적었습니다. ‘길이는 1~200자’라는 답에는 ‘200자를 넘으면 입력을 막을지’가, ‘저장 실패’ 답에는 ‘저장된 내용이 손상됐을 때의 처리’가 미정으로 남았습니다.
- 두 번 모두 결정 옆에 답에 없는 풀이를 덧붙였습니다. 예를 들어 ‘저장 실패’ 답에 ‘실패한 변경은 화면에 남기지 않음’이라는 풀이가 붙었습니다. 내 답보다 넓게 적히지 않았는지 확인합니다.
- 위 답에는 이유가 없습니다. 그래서 이유 칸에 ‘별도 이유는 밝히지 않았다’, ‘별도 이유는 제시되지 않았다’처럼 기록됐습니다. 이유를 남기려면 답할 때 함께 말해야 합니다.

**검토**

- [ ] 내가 답하지 않은 질문이 결정으로 바뀌어 있지 않다.
- [ ] 결정마다 내가 말한 이유가 적혀 있고, 내 답에 없는 풀이가 덧붙어 있지 않다.
- [ ] 미정으로 남은 질문이 다음 단계의 어느 동작에 영향을 주는지 알 수 있다.

### 3단계 — 요구사항과 흐름을 작성하기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다. ③ 맡길수록 절차가 필요하다.

**목적:** 흩어진 답을 같은 앱을 설명하는 하나의 문서로 만듭니다.

**입력:** `request.md`, 자기 답을 기록한 `questions.md`.

**맡긴다**

```text
request.md와 questions.md를 바탕으로 requirements.md를 작성해 줘.
사용자 목적과 범위, 기능·품질·제약, 유즈케이스의 정상·예외 흐름, 인수조건을 포함해 줘.
요구마다 참조할 ID를 붙이고, 원요청과 추가 결정의 근거를 구별해 줘.
아직 결정하지 않은 내용을 확정하지 말고, 기술 스택과 구현 코드는 이번에 만들지 마.
```

**확인한다**

먼저 자기 `requirements.md`에서 추가·완료·삭제·필터·개수·보존을 찾습니다.

**정한다**

유즈케이스는 주요 흐름을 선택하여 충분히 설명하고, 나머지 기능도 인수조건으로 확인 가능하게 합니다. [SAMPLE](SAMPLE.md)과의 비교는 4단계를 마친 뒤에 합니다.

**넘긴다 (산출물)**

04에 전달할 `requirements.md` 초안.

```bash
git status --short        # ?? requirements.md 한 줄만 나온다
git add -A && git commit -m "docs: 요구사항 초안"
```

**검증 실행에서 본 것 (2회)**

- 두 번 모두 `requirements.md` 하나만 만들었습니다. 분량은 약 12,000자였습니다.
- 두 번 모두 기능 요구, 품질 요구, 제약, 유즈케이스 6개(정상·예외 흐름), 인수조건(24개와 21개), 미결 사항(16개와 9개), 추적표가 들어 있었습니다. 요구마다 원요청에서 온 것인지 추가 결정에서 온 것인지 근거를 표시했습니다.
- 답하지 않은 질문은 대부분 요구로 확정하지 않고 미결 사항에 모았습니다. 기술 이름은 요구에 들어가지 않았습니다. 한 번은 미결 사항에 ‘저장 방식(localStorage / IndexedDB 등)’이라고만 적혔습니다.
- 두 번 모두 원문에도 답에도 없는 항목을 덧붙였습니다. 한 번은 ‘분석 보강’이라고 표시했습니다(한글 입력 중 Enter 처리, 초점 표시). 다른 한 번은 ‘[분석]’으로 표시하거나(삭제 실수 방지) 원요청을 근거로 적었습니다(초점 표시, 날짜·숫자 표기). 일부는 답하지 않은 질문의 추천안에서 온 내용입니다. 표시가 있어도 채택할지는 사람이 정합니다.
- [준비된 요구사항](requirements.md)보다 길고 ID 체계도 다릅니다. 준비된 예제는 수업용으로 정리한 문서이며 이 검증 실행의 출력이 아닙니다.

**검토**

- [ ] ‘완료를 해제할 수 있다’는 요구가 있다면 흐름도 완료 설정과 해제를 모두 설명한다.
- [ ] ‘남은 개수’의 뜻이 모든 절에서 같다.
- [ ] 기술 선택이 사용자 요구처럼 들어가 있지 않다.
- [ ] 내가 정하지 않은 내용이 확정된 요구로 적혀 있지 않다.
- [ ] 근거 표시 몇 개를 골라 원문이나 내 답과 실제로 맞는지 확인했다.

### 4단계 — 요구사항을 검토하고 수정하기

> 연습하는 원칙: ① AI는 제안하고, 결정은 사람이 한다. ② 말이 아니라 실행 결과로 확인한다. 이 단계의 실행 결과는 검토 요청 뒤의 `git status --short` 출력과 반영 요청 뒤의 `git diff --stat` 출력입니다.

**목적:** 문서가 그럴듯한지보다 같은 조건에서 같은 결과를 예상할 수 있는지 확인합니다.

**입력:** `request.md`, `questions.md`, `requirements.md`.

**맡긴다**

```text
세 문서를 대조해서 requirements.md의 누락·충돌·모호함과 사용자 목적에 맞지 않을 수 있는 부분을 찾아 줘.
정상 추가, 공백 입력 거부, 완료 후 필터 변경, 삭제, 새로 고침을 문서만 보고 따라가며 지적해 줘.
지적마다 관련 문장과 판단 이유를 보여 줘. 수정은 아직 적용하지 마.
```

**확인한다**

검토 요청이 끝나면 바뀐 파일이 없는지 봅니다.

```bash
git status --short        # 검토 요청 직후에는 아무것도 나오지 않는다
```

**정한다**

지적을 읽고 받아들일 것을 고릅니다. 잘못된 지적은 문서 근거로 설명합니다. 새로 정해야 할 것이 나오면 2단계처럼 `questions.md`에 결정을 먼저 남깁니다.

**맡긴다**

받아들일 지적은 범위를 정해서 반영을 요청합니다. 지적이 맞으면 영향받는 요구·흐름·인수조건을 함께 수정합니다. 예를 들어 필터를 바꿨을 뿐인데 남은 개수가 달라진다면, 기준을 명확히 하고 필터를 다루는 절과 개수를 다루는 절을 함께 맞춥니다. 아래는 검증 실행에서 쓴 요청입니다.

```text
다음 두 가지만 requirements.md에 반영해 줘. 관련된 요구, 유즈케이스, 인수조건을 함께 맞추고 그 밖의 내용은 고치지 마.
1. 완료 필터를 보는 중에 추가한 새 항목은 저장되지만 그 필터에는 보이지 않는다.
2. 보존 대상에 목록의 순서를 넣는다. 새로 고친 뒤에도 추가한 순서가 유지된다.
```

**넘긴다 (산출물)**

사람이 검토한 `requirements.md`와 결정 이유.

```bash
git diff --stat           # 반영 요청 뒤에는 requirements.md만 바뀐다
git add -A && git commit -m "docs: 요구사항 검토 반영"
```

**검증 실행에서 본 것 (검토 2회, 반영 1회)**

- 검토 요청에서는 두 번 모두 파일을 고치지 않고 지적만 했습니다. 지적은 21건과 28건이었고, 대부분의 지적에 관련 문장과 이유를 붙였습니다.
- 두 번 모두 나온 지적이 있습니다. 완료 필터를 보는 중에 추가하면 새 항목이 화면에 보이지 않는다는 것, 추가한 뒤 입력 칸과 초점이 어떻게 되는지 정해져 있지 않다는 것, 새로 고친 뒤에도 순서가 유지되는지 확인할 요구나 인수조건이 없다는 것입니다.
- 한 번만 나온 지적도 있습니다. 저장 실패 때 ‘변경 전 목록’이 화면을 되돌린다는 뜻인지 저장된 내용만 그대로라는 뜻인지 갈린다는 것입니다.
- 반영 요청에서는 `requirements.md`만 바뀌었습니다(8줄 추가, 5줄 삭제). 요구 2개를 고치고 1개를 더했고, 유즈케이스 2개와 인수조건 2개를 고치고 인수조건 1개를 더했습니다. 기존 ID는 바꾸지 않았습니다. 두 결정을 `questions.md`에 먼저 기록하지 않았기 때문에 근거가 질문 번호 없이 ‘[분석]’으로 표시됐습니다.
- 준비된 예제에도 같은 쟁점에 대한 결정이 있습니다. W-01은 ‘완료 필터에서 추가하면 저장은 되지만 새 항목은 그 필터에 보이지 않는다’를 확인할 조건에 적었고, W-07은 순서를 보존 대상에 넣었고, D-05는 저장에 실패하면 변경 전 목록과 개수를 유지한다고 정했습니다. 추가한 뒤의 입력 칸과 초점은 준비된 예제에서도 정하지 않았습니다.

**검토**

- [ ] 다른 사람이 공백 입력이 거부되는 장면과 두 항목 중 하나를 완료한 장면을 읽고 결과를 말할 수 있다.
- [ ] 받아들인 지적과 받아들이지 않은 지적의 이유를 설명할 수 있다.
- [ ] 해결하지 못한 조건을 구현자가 알 수 있다.

### 5단계 — 명세 단계에 전달하기

> 연습하는 원칙: ④ 앞 단계가 뒤 단계의 기준이다.

**목적:** 요구 문서를 다시 작성하는 대신 결정된 동작을 설계의 입력으로 사용합니다.

**한다**

`questions.md`에 남은 중요한 미정은 요구 문서에도 표시합니다. `requirements.md` 첫머리에 검토를 마쳤는지와 남은 미정이 어느 동작에 영향을 주는지를 두세 줄로 적습니다.

**넘긴다 (산출물)**

자기 `requirements.md`가 [모듈 04(SDD)](../../04-sdd/)에서 명세를 쓸 때의 근거입니다. 04의 도구 가이드 다섯 개(Kiro, OpenSpec, Spec Kit, GSD, BMAD)는 모두 같은 ‘할 일 관리 웹 앱’을 예제로 씁니다. 다만 그 가이드들은 각자 준비한 시작 요청으로 출발합니다. `requirements.md`를 넣는 절차는 아직 없고, 넣는 방법은 이 단원에서 확인하지 않았습니다.

**검토**

- [ ] 무엇을 보존해야 하는지와 실패했을 때 사용자가 무엇을 보아야 하는지가 정해져 있다. `localStorage` 같은 저장 방법은 여기서 고르지 않아도 된다.
- [ ] 미정으로 남은 항목과 그 영향이 `requirements.md`에 적혀 있다.

| ② 말이 아니라 실행 결과로 확인한다 | `git status --short`와 `git diff --stat`의 출력으로 검토 요청 직후에는 바뀐 파일이 없는지, 반영 요청 뒤에는 `requirements.md`만 바뀌었는지 봤습니다(4단계) |
| ③ 맡길수록 절차가 필요하다 | 초안 전체를 맡기는 요청에 조건 네 가지를 붙였습니다. 요구마다 ID 붙이기, 원요청과 추가 결정의 근거 구별하기, 결정하지 않은 내용 확정하지 않기, 기술 스택과 구현 코드 만들지 않기입니다(3단계) |
| ④ 앞 단계가 뒤 단계의 기준이다 | `request.md`와 답을 기록한 `questions.md`가 `requirements.md` 초안의 입력이 됐습니다(3단계). 그 `requirements.md`는 모듈 04에서 명세를 쓸 때의 근거가 됩니다(5단계) |

## 정리와 확인 질문

‘할 일을 추가할 수 있다’만으로는 왜 공백 거부와 초기 완료 상태를 구현할 수 없을까요? 사용자 스토리에는 목적이 있지만 모든 규칙은 없기 때문입니다. 유즈케이스에서 흐름을 펼치고 인수조건으로 확인할 결과를 정해야 합니다. AI가 제시한 문장을 늘리는 대신, 사용자의 필요를 바꾸는 결정이 어디에 있는지 설명해 봅니다.

## 자주 막히는 곳

| 증상 | 확인하고 고칠 것 |
|---|---|
| 질문이 10개가 넘어 어디서부터 답할지 모르겠다 | 답에 따라 사용자 동작이나 범위가 달라지는 질문부터 답합니다. 나머지는 미정으로 두어도 됩니다 |
| 구현 방법을 묻는 질문이 있다 | 요구가 아닙니다. 답하지 않고 04에서 정합니다. 무엇을 보존해야 하는지처럼 사용자에게 필요한 조건만 여기서 정합니다 |
| 답했는데 일부가 미정으로 남았다 | 답이 질문의 일부에만 해당한 것입니다. 남은 부분을 읽고 정하거나 미정으로 둡니다 |
| 이유 칸에 이유가 없다고 적혔다 | 답할 때 이유를 말하지 않았습니다. 이유를 말하고 다시 기록하게 합니다 |
| 검토 지적이 20건이 넘는다 | 모두 고칠 필요는 없습니다. 사용자 목적과 이번 범위에 영향을 주는 것부터 고르고, 받아들이지 않은 이유를 남깁니다 |
| 검토만 요청했는데 파일이 바뀌었다 | `git diff`로 바뀐 곳을 읽습니다. 바뀐 내용을 쓰지 않으려면 `git checkout -- requirements.md`로 마지막 커밋 상태로 되돌립니다. 파일 전체가 되돌아가므로 남길 변경은 먼저 따로 적어 둡니다. 3단계에서 커밋하지 않았다면 이 명령으로 되돌릴 수 없습니다 |
| `git commit`이 “Author identity unknown”으로 실패한다 | `git config --global user.name "이름"`과 `git config --global user.email "메일 주소"`를 먼저 실행합니다 |
