# 모듈 03 · 단원 M01 — AI와 함께 요구사항 도출·분석·검증하기

> 상태: 초안 · 담당: 윤성열 · 예제: 개인용 할 일 관리 웹 앱
> 검증 기준: Claude Code 2.1.330(모델 Sonnet 5.5) · 2026-11-24

## 목적

“할 일을 적고 완료 표시도 하고 싶다”는 말을 AI에 전달하면 앱은 나올 수 있습니다. 그러나 새로 고침 뒤 내용이 사라지거나, ‘남은 개수’가 필터마다 달라진다면 원한 앱인지 다시 물어야 합니다. 이 실습은 **원요청을 질문으로 구체화하고, 사람이 선택한 내용을 구현 전에 확인할 수 있는 요구사항으로 남기는 과정**입니다.

이 단원을 마치면 다음을 할 수 있습니다.

- 기능 요구·품질 요구·제약을 구별하고 모호한 문장을 관찰 가능한 조건으로 고친다.
- 사용자 스토리의 목적, 유즈케이스의 흐름, 인수조건의 합격 기준을 같은 기능에서 연결한다.
- AI가 제안한 가정과 사람이 결정한 범위를 구별하여 다음 명세 단계에 전달한다.

## 사전 준비물

- Claude Code. 설치와 로그인을 마친 상태여야 합니다. `claude --version`으로 확인합니다. 설치 방법은 Claude Code 공식 문서(https://code.claude.com/docs)를 따릅니다.
- git. AI가 만들고 고친 파일을 확인하는 데 씁니다.
- Markdown 파일을 읽고 고칠 편집기.

| `requirements.md` | 사용자 목적, 동작, 확인 기준 | [모듈 04(SDD)](../../04-sdd/)에서 명세를 쓸 때의 근거 |

## 검증 기록 (2026-11-24)

- 환경: macOS, Claude Code 2.1.330(모델 Sonnet 5.5), git 2.56.1
- GUIDE 1~3단계의 요청과 4단계의 검토 요청을 Claude Code 비대화형 모드(`claude -p`)로 두 번씩 실행했습니다. 4단계의 반영 요청은 한 번 실행했습니다. 단계마다 새 세션으로 실행했고, 단계 사이에는 파일만 이어졌습니다.
- 설정 파일은 프로젝트 것만 읽게 했습니다(`--setting-sources project,local`). 이 옵션으로는 사용자 전역 지침 파일(`~/.claude/CLAUDE.md`)이 빠지지 않아서, 실행 장비의 전역 지침 파일이 함께 읽혔습니다. 그 파일에는 장비 환경 안내만 있고 요구사항 작성에 관한 지침은 없습니다. 검토 실행 한 번의 지적 하나에 그 환경 정보가 섞였습니다.
- 확인한 것은 다음과 같습니다. 결과는 GUIDE 각 단계의 ‘검증 실행에서 본 것’에 적었습니다.
  - 단계마다 만들어지거나 바뀐 파일(`git status`)
  - 원요청이 바뀌지 않았는지
  - 답하지 않은 질문이 미정으로 남는지
  - 기술 선택이 요구로 들어가는지
  - 검토 단계에서 파일을 고치는지
- GUIDE가 인용한 정의와 점검 항목은 IREB의 CPRE 온라인 용어집, NASA Systems Engineering Handbook 부록 C, NPR 7150.2D 원문과 대조했습니다.
- 한계: 실행 횟수가 적고 모델과 버전이 하나입니다. 대화형 화면에서의 표시, 한 세션에서 이어서 진행하는 경우, 다른 AI 도구는 확인하지 않았습니다.
- 준비된 [requirements.md](requirements.md)는 수업용으로 정리한 예제이며 이 검증 실행의 출력이 아닙니다. 실제 고객의 요구나 승인 기록도 아닙니다.

## 다른 자료와의 관계

- 예제의 기능 범위는 [모듈 04](../../04-sdd/)의 도구 가이드(Kiro, OpenSpec, Spec Kit, GSD, BMAD)가 만드는 할 일 관리 웹 앱과 이어집니다. 도구 설치나 앱을 만드는 활동은 여기서 하지 않습니다.
- 작은 코드로 요구사항에서 테스트까지의 연결을 보고 싶다면 [할 일 생성 샘플](../../../samples/web-task-system/README.md)을 따로 읽습니다. 그 샘플은 팀원이 할 일을 생성하는 기능만 다루며, 이 단원의 개인용 웹 앱과 요구 ID가 다릅니다.
