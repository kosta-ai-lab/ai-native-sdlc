# 결과 예제 읽기와 확인 — 요구사항

## 1. 자기 결과를 먼저 확인하기

[GUIDE](GUIDE.md) 4단계까지 마쳤다면 자기 실습 폴더의 `requirements.md`를 엽니다. 다음 세 장면의 결과가 문서만으로 결정되는지 적어 봅니다.

1. 미완료 두 개 중 하나를 완료하고 완료 필터를 선택한다. 화면에 몇 개가 보이고 남은 개수는 얼마인가?
2. 같은 제목 두 개 중 하나를 삭제한다. 어느 항목이 남는지 구별할 기준이 있는가?
3. 새 항목을 입력했지만 브라우저가 저장을 거부한다. 화면과 저장 데이터는 각각 어떻게 되는가?

답이 여러 개라면 파일 생성은 끝났어도 요구 검토는 아직 끝나지 않았습니다. AI가 알아서 구현할 것이라 넘기지 말고 질문과 결정으로 돌아갑니다.

## 2. 준비된 결과의 구성

[requirements.md](requirements.md)는 이 실습의 준비된 예제입니다. 원요청 전체를 복잡한 시스템으로 확장하지 않고, 개인용 웹 앱의 범위를 유지했습니다.

| 읽을 부분 | 예제에서 확인할 점 |
|---|---|
| 목적·용어 | ‘진행 중’을 제3의 상태로 만들지 않고 미완료 필터로 정의했습니다 |
| D-01~D-05 | 원문에 없던 길이·중복·삭제·실패 정책을 추가 결정으로 분리했습니다 |
| W-01~W-08 | 정상 결과와 함께, 거부(W-02)와 저장 실패(W-08) 뒤에 유지할 상태도 적었습니다 |
| Q-01·Q-02·C-01 | 기능 목록과 별도로 접근성·한국어·전송 제한을 확인합니다 |
| UC-W01·UC-W02 | 저장 성공을 거친 뒤 표시하는 흐름과 필터에서 사라지는 상황을 설명합니다 |

### ‘남은 개수’를 필터 결과에서 세지 않는 이유

완료 필터에 완료 항목 하나만 보일 때, 표시 목록에서 미완료 수를 세면 0입니다. 그러나 사용자는 아직 남은 일이 전체에 하나 있다는 것을 알아야 합니다. 예제는 W-06을 ‘전체 목록의 미완료 수’로 결정했습니다. 따라서 W-06의 개수는 W-05가 만든 표시 목록이 아니라 전체 목록에서 세어야 합니다. 이 차이는 04에서 데이터 처리와 화면 표시를 분리할 이유가 됩니다.

### 중복 제목을 허용하면서도 항목을 구별하는 이유

‘전화하기’를 여러 번 적을 수 있어도 한 번의 완료·삭제가 모두에 적용되어서는 안 됩니다. D-01은 제목 중복을 허용하고 W-03·W-04는 지정한 한 항목을 바꾸도록 했습니다. 03에서는 항목 구별이 필요하다는 뜻을 확정하고, 04에서 고유 ID라는 방법을 선택합니다. 사용자 요구와 설계 결정을 같은 문장으로 섞지 않은 예입니다.

### 저장 실패에 두 정책이 있는 이유

W-08의 변경 저장 실패 때는 이미 읽은 정상 목록이 있으므로 이전 화면을 유지할 수 있습니다. 처음부터 저장 내용이 손상된 경우에는 무엇이 정상 목록인지 알 수 없습니다. 빈 목록으로 조용히 저장하면 원래 데이터를 잃습니다. D-05는 손상 내용을 보존하고 변경을 중단하도록 정했습니다. 두 경우를 ‘오류 처리’ 한 줄로 합치지 않습니다.

## 3. 문서로 흐름 따라가기

준비된 예제로 1장의 세 장면을 따라가면 결과는 다음과 같습니다. 이것은 앱 실행 로그가 아니라 요구 문장으로 계산한 기대 결과입니다.

| 장면 | 요구로부터 예상할 결과 | 근거 |
|---|---|---|
| 미완료 A·B 중 A 완료 후 완료 필터 | A 표시, 남은 개수 1 | W-03·W-05·W-06 |
| 같은 제목 A·B 중 A 삭제 | B 유지. 제목만으로 두 항목을 식별하면 안 됨 | D-01·W-04 |
| 정상 목록에서 추가 저장 실패 | 변경 전 목록·개수 유지, 한국어 실패 안내. 새 항목은 저장되지 않음 | D-05·W-08·Q-02·UC-W01 |

자기 문서의 결과가 다르더라도 이유와 범위가 일관되면 가능한 대안입니다. 다만 준비된 예제와 다른 결정을 했다면 그 차이를 이후의 명세와 설계에도 반영해야 합니다.

## 4. 짧은 독립 확인

‘같은 제목은 허용하지 않는다’로 조건을 바꿔 봅니다. 제목만 비교할지 앞뒤 공백 제거 후 비교할지, 거부 안내는 무엇인지 먼저 결정합니다. 그다음 D-01, W-01~W-04의 확인할 조건, UC-W01의 대안 A에서 바뀔 부분을 말해 봅니다. 고유 ID가 불필요해진다고 단정하지 않습니다. 제목 변경 같은 후속 기능을 고려하면 ID는 여전히 설계 대안입니다.

## 5. 04로 가져가기

[모듈 04(SDD)](../../04-sdd/)의 도구 가이드는 각자 준비한 시작 요청으로 명세를 만듭니다. `requirements.md`를 넣는 절차는 아직 없고, 넣는 방법은 이 단원에서 확인하지 않았습니다. 03에서 만든 질문표 전체를 04에서 다시 쓰지는 않습니다. 준비된 예제 파일을 복사해 쓴다면 이 예제의 선택을 채택한 것임을 알고 시작합니다.

[할 일 생성 샘플](../../../samples/web-task-system/docs/03-requirements.md)은 R-01~R-03과 ‘할 일/진행/완료’ 상태를 쓰는 별도의 작은 사례입니다. 이 단원의 W-01~W-08 ID나 미완료/완료 상태와 섞어 쓰지 않습니다.
