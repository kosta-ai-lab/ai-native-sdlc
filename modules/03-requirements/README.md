# 모듈 03 — 유즈케이스·요구사항

> 상태: 단원 1개 초안 (담당: 윤성열)
> 한 줄: **원요청을 질문과 사람의 결정을 거쳐, 구현 전에 확인할 수 있는 요구사항과 유즈케이스로 바꾼다.**

## 목적

“할 일을 등록하고 싶다”는 요청만으로는 구현을 시작하기 어렵습니다. 누가 무엇을 입력하는지, 잘못된 입력은 무엇인지, 이번에 어디까지 만드는지 먼저 정해야 합니다. 이 모듈에서는 원요청을 질문과 사람의 판단을 거쳐 **검증 가능한 요구사항과 유즈케이스**로 바꿉니다.

학습 후에는 다음을 할 수 있어야 합니다.

- 원문에 있는 사실과 AI의 가정, 사람의 결정, 아직 정하지 않은 질문을 구별한다.
- 기능 요구·품질 요구·제약을 나누고, 정상 흐름과 예외 흐름을 유즈케이스로 설명한다.
- 요구 ID와 확인 기준을 유지하여 모듈 04(SDD)에 넘긴다.

## 단원 구성

단원마다 README(목적과 준비물), GUIDE(단계별 따라 하기), SAMPLE(결과 예제 읽기)이 있습니다.

| 단원 | 내용 | 만드는 것 |
|---|---|---|
| [M01 — AI와 함께 요구사항 도출·분석·검증하기](M01-ai-requirements/) | 개인용 할 일 관리 웹 앱의 원요청에서 질문을 찾고, 답을 정해 기록하고, 요구사항·유즈케이스·인수조건으로 정리해 검토합니다 | `questions.md`, `requirements.md` |

## 입력

- 원요청 원문
- 업무 흐름이나 용어 자료가 있으면 함께 씁니다([모듈 02 시맨틱 모델](../02-semantic-model/)). 없는 자료를 AI가 있다고 꾸미지 않게 합니다.

## 산출물

- 질문과 결정 기록(`questions.md`)
- 요구사항 문서(`requirements.md`): 목적과 범위, 기능 요구·품질 요구·제약, 유즈케이스, 인수조건
- 모듈 04(SDD)로 넘길 요구 ID와 미정 목록

## 흐름

원요청 → 질문·결정 기록 → 요구사항·유즈케이스 → [04 명세](../04-sdd/) → [05 인수조건](../05-bdd/) → [06 테스트·구현](../06-coding-tdd/)

요구사항은 **사용자에게 필요한 동작과 이유**를, 명세는 **구현과 테스트가 따를 구체적인 계약**을 다룹니다. 둘을 따로 관리하지 않고 같은 요구 ID로 연결합니다.

단원 README에 검증 기록이 있습니다. 요청문은 Claude Code 2.1.330(모델 Sonnet 5.5)에서 실제로 실행했고(2026-11-24), 인용한 정의는 원문과 대조했습니다. AI의 응답은 실행마다 달라질 수 있습니다.
