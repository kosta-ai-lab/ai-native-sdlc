# 개념

**Research Assistant 하네스**는 Claude Code 안에서 **학술 연구 보조 전문가 5명이 팀으로 협업**하도록 미리 설정해 놓은 구성 파일 묶음입니다.

"문헌 리뷰 해줘"라고 한 마디만 하면, 아래 5명의 에이전트가 순서대로(일부는 동시에) 일합니다.

| 에이전트 | 하는 일 |
|---------|--------|
| 🔍 literature-searcher | 논문·서적·보고서를 웹에서 검색하고 관련성 평가 |
| 📝 note-taker | 문헌별로 구조화된 읽기 메모 작성 (핵심 논지, 방법론, 인용 구절) |
| 🧠 critic-synthesizer | 비판적 분석, 테마별 종합, 연구 갭(gap) 식별 |
| 📚 reference-manager | APA/MLA/Chicago 등 인용 형식 관리, BibTeX 생성 |
| ✅ research-coordinator | 전체 결과물 교차 검증 후 최종 보고서 작성 |

최종적으로 `_workspace/` 폴더에 **문헌 검색 결과 → 읽기 메모 → 비평·종합 → 참고문헌 → 최종 연구 보고서** 5개의 마크다운 파일이 만들어집니다.

> ⚠️ **범위 참고**: 실험 수행, 통계 분석 실행, 논문 최종 집필, 학술지 투고는 이 하네스의 범위가 아닙니다. "연구 준비 단계"를 도와주는 도구입니다.

# 1 단계: .claude 폴더 만들기 및 skills 폴더 만들기

연습용 프로젝트 폴더에 하네스의 뼈대가 될 폴더 구조를 만들자. 연습용 프로젝트 이름은 my-harness-demo로 만들고 그 안에 다음 폴더를 만들 수 있다.

```bash
# 하네스의 핵심: .claude 폴더와 하위 폴더 만들기
mkdir -p .claude/agents
mkdir -p .claude/skills/commit-message
```
## 규칙

핵심 규칙은 두 가지입니다. 에이전트는 .claude/agents/ 안에 마크다운 파일 하나로 정의하고, 스킬은 .claude/skills/스킬이름/ 폴더 안에 반드시 SKILL.md라는 이름의 파일로 정의합니다. 이 폴더들은 git으로 커밋되므로 팀원과 공유하면 모두가 같은 하네스를 쓰게 됩니다.

## 산출물

```bash
my-harness-demo/
└── .claude/
    ├── agents/                  ← 서브에이전트 정의 파일(.md)이 들어갈 곳
    └── skills/
        └── commit-message/       ← 스킬 하나당 폴더 하나
            └── SKILL.md         ← (다음 단계에서 만들 파일)
```

## 체크리스트
[ ] 상기 산출물 구조대로 만들었는지 확인한다.

# 2 단계: SKILL.md 스킬 파일 만들기

스킬은 '이 작업은 이렇게 하는 거야'라고 Claude에게 가르치는 문서입니다. 파일 하나면 충분합니다. 메모장이나 VS Code 등 아무 텍스트 편집기로 .claude/skills/commit-helper/SKILL.md 파일을 만들고 아래 내용을 그대로 붙여 넣으세요.

```bash
---
name: commit-helper
description: git 커밋 메시지를 작성할 때 사용. 사용자가 커밋, commit,
  변경사항 저장을 요청하면 이 규칙에 따라 커밋 메시지를 만든다.
---
 
# 커밋 메시지 작성 규칙
 
커밋 메시지를 작성할 때 다음 절차를 따른다.
 
1. 먼저 `git diff` 와 `git status` 로 변경 내용을 파악한다.
2. 커밋 메시지는 아래 형식을 지킨다.
 
   <타입>: <50자 이내 한글 요약>
 
   - 타입은 feat(기능), fix(버그수정), docs(문서),
     refactor(리팩터링), chore(기타) 중 하나
   - 제목은 명사형으로 끝낸다 (예: "로그인 버튼 추가")
3. 변경이 두 가지 이상의 성격을 가지면 커밋을 나누자고 제안한다.
4. 커밋 전에 만든 메시지를 사용자에게 보여주고 확인을 받는다.
```

## 규칙

맨 위 ---로 감싼 부분은 프런트매터(frontmatter)라고 부르는 메타데이터입니다. 여기서 가장 중요한 것은 description입니다. Claude Code는 시작할 때 모든 스킬의 이름과 설명만 미리 읽어 두고, 대화 내용이 설명과 맞아떨어지는 순간 본문 전체를 불러옵니다. 즉 description은 단순한 소개글이 아니라 스킬이 발동되는 '방아쇠'입니다. "언제 사용하는지"를 구체적인 키워드(커밋, commit 등)와 함께 적어야 원하는 순간에 정확히 발동됩니다.

[!WARNING]
> description을 "커밋 도우미"처럼 짧고 모호하게 쓰면 스킬이 발동되지 않습니다. "무엇을 하는 스킬인지 + 언제 사용해야 하는지"를 사용자가 실제로 쓸 법한 단어로 풀어서 적으세요.

## 산출물

```bash
SKILL.md
```

# 3 단계: code-reviewer.md 파일로 첫 번째 에이전트 만들기

서브에이전트는 자기만의 독립된 대화 공간(컨텍스트)과 시스템 프롬프트, 도구 권한을 가진 별도의 Claude입니다. 메인 대화를 어지럽히지 않고 일을 맡긴 뒤 결과만 돌려받을 수 있습니다. .claude/agents/code-reviewer.md 파일을 만들고 아래 내용을 붙여 넣으세요.

```bash
---
name: code-reviewer
description: 코드 변경 사항을 검토한다. 사용자가 코드 리뷰, 검토,
  review를 요청하거나 커밋 직전 품질 확인이 필요할 때 사용한다.
tools: Read, Grep, Glob, Bash
---
 
당신은 꼼꼼한 시니어 코드 리뷰어입니다.
 
호출되면 다음 순서로 작업하세요.
 
1. `git diff HEAD` 를 실행해 최근 변경 사항을 확인한다.
2. 다음 관점에서 문제를 찾는다.
   - 버그 가능성 (오타, 잘못된 조건문, null 처리 누락)
   - 보안 문제 (비밀번호/키 하드코딩, 입력값 검증 누락)
   - 가독성 (모호한 변수명, 중복 코드)
3. 발견한 문제를 심각도(높음/중간/낮음)로 나눠 보고한다.
   각 항목에 파일명과 줄 번호를 포함한다.
4. 각 문제에 대해 최소한의 수정 방법을 제안한다.
 
중요: 파일을 직접 수정하지 말고 보고서만 작성하세요.
```

## 규칙

스킬과 형식이 거의 같지만 결정적 차이가 하나 있습니다. 바로 tools 항목입니다. 이 에이전트에게는 읽기(Read), 검색(Grep, Glob), 명령 실행(Bash)만 허용하고 파일 쓰기/수정 도구(Write, Edit)는 주지 않았습니다. 리뷰어가 실수로 코드를 고쳐버리는 일을 구조적으로 막은 것이죠. 이것이 하네스 엔지니어링의 핵심 사고방식입니다. "하지 마"라고 부탁하는 대신, 애초에 할 수 없게 설계합니다.

프런트매터 아래의 본문은 이 에이전트의 시스템 프롬프트가 됩니다. 에이전트는 메인 대화 내용을 전혀 모르는 상태로 시작하므로, 본문에 '호출되면 무엇부터 할지'를 스스로 알아낼 수 있게 적어야 합니다. 위 예제에서 1번 단계가 git diff HEAD 실행인 이유가 바로 이것입니다.
