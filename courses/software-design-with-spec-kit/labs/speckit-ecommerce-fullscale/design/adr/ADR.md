# 아키텍처 결정 기록 (ADR)

멀티셀러 마켓플레이스 확장(3일차)의 핵심 설계 결정. 각 결정은 유스케이스·도메인·시퀀스·상태머신 산출물과 연결된다. 강의에서는 "왜 이 결정을 했는가"를 해석하는 근거로 쓴다.

## ADR-001 — 주문(Order)과 하위주문(SubOrder) 분리

- **맥락**: 한 주문에 여러 판매자의 상품이 섞인다.
- **결정**: 주문을 판매자별 `SubOrder`로 분할한다. 배송·정산·환불의 단위를 SubOrder로 둔다.
- **결과**: 정산이 판매자별로 독립한다. 결제는 Order 단위(구매자 1회 결제), 상태는 SubOrder 단위로 갈린다.
- **대안(기각)**: 주문을 단일 단위로 유지 → 판매자별 정산·부분 배송·부분 환불을 표현할 수 없다.

## ADR-002 — 결제 전 재고 선점(reserve)

- **맥락**: 동시 주문 시 같은 재고를 여러 명이 결제하는 오버셀 위험.
- **결정**: 주문 생성 시 재고를 `reserve`(선점)하고, 결제 성공 시 확정, 실패·취소 시 `release`(복원).
- **결과**: 오버셀을 막는다. 트레이드오프로 결제 실패 시 롤백(release) 경로가 필요하다.
- **대안(기각)**: 결제 후 차감 → "결제는 됐는데 재고가 없는" 상태가 발생할 수 있다.

## ADR-003 — 결제 멱등키(idempotencyKey)

- **결정**: `authorize`/`void`에 idempotencyKey를 요구한다. 같은 키의 재요청은 중복 처리하지 않는다.
- **결과**: 네트워크 재시도·중복 클릭·재발송에 안전하다(중복 결제/중복 취소 방지).

## ADR-004 — 정산은 배송 완료 트리거 + 배치 집계

- **결정**: SubOrder가 배송 완료(`markDelivered`)돼야 정산 큐에 진입한다. 정산 주기에 `aggregate`로 집계 후 수수료를 공제해 지급한다.
- **결과**: 미배송 건 과지급을 막는다. 환불이 발생하면 이미 정산된 건은 차기 정산에서 역산(차감)한다.
- **연결**: 상태머신의 `배송완료 → 정산대상` 전이가 이 결정의 시각화.

## ADR-005 — 얇고 교체 가능한 Store (Constitution III 계승)

- **결정**: 라우트·도메인은 Store 인터페이스에만 의존한다. 현재 구현은 in-memory.
- **결과**: 저장소 교체(예: PostgreSQL)가 핸들러에 영향을 주지 않는다. 단위 테스트가 쉬워진다.
- **연결**: 2일차 constitution의 원칙 III를 3일차에서도 유지·계승.
