# 강의 자료 작성 규격 (제안)

> 상태: **제안** · 제안자: 윤성열 · 확정: 워크숍 합의
> 지금까지 올라온 자료를 살펴보니 세 사람이 각자 다른 방식으로 쓰고 있었습니다. 어느 쪽이 틀린 게 아니라 기준이 없었기 때문입니다. 다음 기여자가 고민 없이 따라 쓸 수 있도록 하나로 모으자는 제안입니다.

## 지금 무엇이 다른가

| | 이선아 교수 · 하네스 | 박준성 회장 · Agentic Coding | 윤성열 · 3부작 |
|---|---|---|---|
| 위치 | `modules/ext-harness/` | `courses/` | `courses/` |
| 따른 규격 | 모듈 4종 (README·CLAUDE.md·skills·sample) | 강의 4종 (README·slides·labs·resources) | 강의 4종 |
| 회차 표기 | `M01`~`M15` | 과정 1~10 | 1편·2편·3편 |
| README 형식 | 마크다운 | HTML 태그 | 마크다운 표 |
| 상태·담당 표기 | 있음 | 없음 | 없음 |

세 자료 모두 내용은 충실합니다. 문제는 **처음 오는 사람이 어느 쪽을 따라야 할지 알 수 없다**는 것입니다.

## 1. 모듈인가 강의인가

이 구분이 가장 먼저입니다.

| | `modules/` | `courses/` |
|---|---|---|
| 무엇 | AI Native SDLC 방법론을 단계별로 쌓는 자산 | 그 방법론을 가르치는 교육 과정 |
| 단위 | SDLC 단계 (요구사항·SDD·BDD·TDD…) | 강의 하나 |
| 읽는 사람 | 이 방법론을 프로젝트에 적용하려는 실무자 | 수강생과 강사 |
| 산출물 | 가이드·규칙(CLAUDE.md)·자동화(skills)·샘플 | README·슬라이드·실습·참고자료 |

**회차가 있고 강사가 있으면 강의입니다.** `M01`처럼 시간 단위로 나뉘고 "이 가이드에서는 ~을 만들어 봅니다"로 진행되면 `courses/`가 맞습니다. `modules/`는 강의 회차가 아니라 SDLC 단계로 나뉩니다.

> 하네스 엔지니어링 자료는 지금 `modules/ext-harness/`에 있지만 회차(M01~M15) 구성이라 성격은 강의에 가깝습니다. 옮길지, 아니면 `modules/`에도 회차형을 허용할지 워크숍에서 정하면 좋겠습니다.

## 2. 폴더 이름

강의 폴더는 **주제를 영어 kebab-case**로 씁니다. 번호를 앞에 붙이지 않습니다. 순서는 README에서 밝힙니다.

```
courses/
  agentic-coding-using-claude-code/
  harness-engineering/
  vibe-coding-with-claude-code/
```

회차 폴더는 **두 자리 번호 + 주제**로 씁니다. 번호는 1씩 올립니다.

```
harness-engineering/
  01-first-harness/
  02-reusing-harness/
```

> `M01`·`M03`·`M05`처럼 건너뛰는 번호는 사이에 무엇이 빠졌는지 알 수 없습니다.

## 3. 강의 폴더 구성

| 항목 | 위치 | 필수 |
|------|------|:---:|
| 강의 개요 | `README.md` | ● |
| 슬라이드 | `slides/` (PDF 또는 외부 링크) | ● |
| 실습 | `labs/` | 실습이 있으면 |
| 참고자료 | `resources/` | |

회차가 여러 개면 강의 폴더 아래 회차 폴더를 두고, **강의 폴더 README에 회차 목록**을 둡니다. 회차 폴더에도 각각 README를 둡니다.

## 4. README 필수 항목

머리말에 **상태와 담당**을 밝힙니다. 초안인지 완성인지 몰라 손대지 못하는 일을 막습니다.

```markdown
# 강의 제목

> 상태: 초안 | 검토중 | 완성 · 담당: 이름
```

이어서 개요를 **표**로 씁니다. 항목을 나열하는 것보다 빠르게 읽힙니다.

| 항목 | 내용 |
|------|------|
| 제목 | |
| 대상 | 누가 듣는 강의인지 |
| 선수지식 | 없으면 "없습니다"라고 적습니다 |
| 학습목표 | 수료 후 무엇을 할 수 있는지 |
| 분량 | 예: 1일 8블록 (50분 × 8 + 휴식) |
| 강사 | 이름 (소속) |

그 아래 **커리큘럼**을 표나 번호 목록으로 둡니다. 블록마다 무엇을 다루고 무엇이 손에 남는지 적습니다.

## 5. 문서 작성

- **마크다운으로 씁니다.** `<h1>`·`<h3>` 같은 HTML 태그는 쓰지 않습니다. GitHub에서 목차가 잡히지 않고 표도 만들 수 없습니다.
- 한국어를 우선하고 핵심 용어는 영문을 병기합니다. 제품명은 정확히 씁니다(`Claude Code`, `Spec Kit`, `OpenSpec`).
- 격식체(합쇼체)로 씁니다.
- **논의 사항·TODO는 README가 아니라 이슈에 씁니다.** README는 수강생과 강사가 읽는 문서입니다.

## 6. 실습 자산과 라이선스

- 도구가 `init`으로 만들어 주는 파일은 저장소에 넣지 않습니다. 실습 첫 단계에서 직접 받게 하고, README에 명령어를 적습니다.
- 이유는 두 가지입니다. 상류 프로젝트(대개 MIT)의 저작물이라 사본에는 저작권 표기와 라이선스 전문이 따라붙어야 하고, 도구가 빨리 바뀌어 사본이 금방 낡습니다.
- 외부 저작물을 꼭 담아야 하면 출처와 라이선스를 폴더 안에 함께 둡니다.
- API 키·계정 정보는 어떤 형태로도 넣지 않습니다.

## 7. 고객사 자료를 가져올 때

기업 교육으로 만든 자료를 공개판으로 바꿀 때는 아래를 지웁니다.

- 표지의 고객사명과 강의 일자
- 회차 표현("2일차", "DAY 3") — 편·회차 번호로 바꿉니다
- 강사가 API 키를 나눠 주던 안내 — 수강자 본인 계정 발급으로 바꿉니다
- 개인 계정 저장소 URL

**슬라이드를 이미지로 굽는 방식이면 문자열 검색으로는 확인이 안 됩니다.** 다이어그램 제목처럼 그림에 글자가 들어간 곳이 남습니다. 완성본을 이미지로 뽑아 OCR로 한 번 훑어보시길 권합니다.

## 8. 올리기 전 체크리스트

- [ ] 상태와 담당을 적었다
- [ ] 대상·선수지식·학습목표를 적었다
- [ ] 슬라이드 또는 그 링크를 넣었다
- [ ] 실습이 있다면 따라 할 수 있게 정리했다
- [ ] 도구 `init` 산출물을 넣지 않았다
- [ ] API 키·계정 정보가 없다
- [ ] 고객사명·일자가 없다 (기업 교육 자료를 가져온 경우)
- [ ] HTML 태그 없이 마크다운으로 썼다
