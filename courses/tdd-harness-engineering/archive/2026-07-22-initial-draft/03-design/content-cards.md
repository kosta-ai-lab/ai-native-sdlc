# 개념과 실제 사례 카드

> 강의 슬라이드 한 묶음 또는 10~20분 설명 단위로 사용할 수 있는 카드입니다.

## 카드 1 — BDD는 테스트 문법이 아니라 공유 이해를 만드는 과정이다

### 개념

BDD는 관계자들이 실제 예제를 이용해 원하는 행동을 발견하고, 합의 가능한 형식으로 정리한 뒤, 이를 실행 가능한 검증으로 연결하는 개발 방식이다.

### 흔한 오해

“Given–When–Then 파일을 만들었으니 BDD를 했다.”

### 실제 용법

Cucumber는 BDD를 다음 세 활동으로 설명한다.

1. Discovery: 규칙, 예외와 모호함을 예제로 발견
2. Formulation: 사람이 읽고 자동화할 수 있는 예제로 정형화
3. Automation: 예제를 테스트에 연결하고 구현을 안내

### 강의 사례

“빈 제목의 할 일은 생성할 수 없다”를 바로 테스트로 쓰지 않는다. 먼저 공백, 최대 길이, 중복, 로그인 여부 같은 예외를 Example Mapping으로 찾는다. 합의된 예제만 인수조건으로 만든다.

### 데모 포인트

모호한 사용자 스토리 하나를 AI에게 바로 구현하게 한 결과와, 예제 4개를 합의한 뒤 구현하게 한 결과를 비교한다.

### 출처

- [Cucumber BDD 공식 문서](https://cucumber.io/docs/bdd/)

## 카드 2 — BDD는 바깥쪽 행동을, TDD는 안쪽 설계를 안내한다

### 개념

BDD 인수조건은 시스템이 사용자에게 보여야 하는 행동을 설명한다. TDD의 작은 테스트는 그 행동을 구현하기 위해 내부 객체와 함수가 가져야 할 계약을 발견한다.

### 실제 용법

```text
AC-02 빈 제목 거부
  ↓
인수 테스트: POST /todos가 400을 반환
  ↓
단위 테스트: normalizeTitle("   ")가 오류를 반환
  ↓
최소 구현
```

### 강의 사례

`samples/web-task-system`의 `05-acceptance.feature`와 `todo.test.ts`를 나란히 놓고 인수조건이 테스트로 변환되는 지점을 표시한다.

### 실패 사례

- Gherkin에는 규칙이 있지만 테스트에는 ID나 대응 관계가 없음
- 단위 테스트는 많지만 사용자가 원하는 행동과 연결되지 않음
- 모든 시나리오를 느린 UI E2E로 구현

### 데모 포인트

인수조건 하나에 대해 인수 테스트 1개와 단위 테스트 2개가 왜 필요한지 테스트 피라미드로 설명한다.

## 카드 3 — Red는 색상이 아니라 증거다

### 개념

유효한 Red는 원하는 행동이 아직 구현되지 않았기 때문에 테스트가 실패했다는 증거다.

### 실제 용법

하니스는 다음을 기록한다.

- 실행 명령과 시각
- 실패 테스트 이름
- 기대값과 실제값
- Git 상태 또는 변경 체크포인트
- 실패 원인이 미구현 행동인지 환경 문제인지 판정

### 유효하지 않은 Red

- 패키지가 설치되지 않아 테스트 러너가 시작하지 못함
- 문법 오류로 테스트 파일을 읽지 못함
- 잘못된 import 경로
- 테스트가 아닌 타입 검사만 실패

### MoAI 사례

MoAI의 TDD 스킬은 새 테스트가 첫 실행부터 모두 통과하거나 구현과 테스트가 같은 시점에 생성된 경우를 Red 누락 신호로 취급한다. 완료 검사에는 전체 테스트 출력과 Red 증거를 요구한다.

### 데모 포인트

환경 오류 Red, 의미 없는 Red, 올바른 행동 Red 세 가지를 연속 실행하여 구분하게 한다.

## 카드 4 — Green은 최소 구현이며 테스트 맞춤 하드코딩이 아니다

### 개념

Green은 현재 실패 테스트를 통과하는 가장 단순한 일반 해법을 구현하는 단계다. 특정 fixture 값만 반환하는 테스트 게이밍은 최소 구현이 아니다.

### 실제 용법

구현 에이전트에게 다음 제약을 준다.

- 테스트와 인수조건 변경 금지
- 현재 테스트와 관련 없는 기능 추가 금지
- 전체 회귀 테스트 실행
- 특정 입력값 하드코딩 금지

### MoAI 사례

MoAI `manager-develop`은 Green에서 테스트가 명시한 일반 해법을 작성하고, literal fixture에 맞춘 하드코딩을 금지한다. 테스트 통과 외에도 LSP 오류 0과 기존 테스트 보존을 후조건으로 둔다.

### 데모 포인트

AI가 `"보고서 작성"`만 통과하도록 하드코딩한 구현을 만든 뒤 hidden test 또는 parameterized test로 잡아낸다.

## 카드 5 — 테스트 작성자와 구현자를 분리한다

### 개념

한 에이전트가 인수조건, 테스트, 구현과 승인을 모두 바꿀 수 있으면 가장 쉬운 해결책은 기대값을 낮추는 것이다.

### 실제 용법

- test-writer: 인수조건과 테스트만 작성
- implementer: 소스 코드만 수정
- reviewer: 추적성, 테스트 강도와 회귀를 독립 검사

권한 규칙이나 작업 범위로 역할을 제한하고, 테스트 변경은 별도 승인 흐름으로 돌린다.

### 연구 사례

Test-Driven AI Agent Definition 연구는 행동 명세에서 테스트를 만드는 역할과 프롬프트·에이전트 구현을 개선하는 역할을 분리하고, hidden tests와 semantic mutation으로 스펙 게이밍을 줄이는 방식을 제안한다.

### 데모 포인트

단일 에이전트가 실패 테스트를 느슨하게 고쳐 Green을 만드는 장면과, 구현 역할에서 테스트 편집이 차단되는 장면을 비교한다.

### 출처

- [Test-Driven AI Agent Definition](https://arxiv.org/abs/2603.08806)

## 카드 6 — TDD 프롬프트보다 테스트 영향 컨텍스트가 중요할 수 있다

### 개념

에이전트가 TDD 절차를 알아도 어떤 기존 테스트가 변경의 영향을 받는지 모르면 회귀를 놓칠 수 있다.

### 실제 용법

- 변경 파일과 관련 테스트 매핑
- 의존 관계를 통한 간접 영향 테스트 추천
- 관련 테스트 → 모듈 테스트 → 전체 회귀 순서 실행

### 연구 사례

2026년 TDAD 사전 연구는 제한된 실험에서 TDD 지시만 추가했을 때 회귀율이 증가했으나, 코드–테스트 영향 정보를 제공했을 때 회귀가 감소했다고 보고한다. 결과를 보편화할 수는 없지만 “절차 지시보다 실행 컨텍스트”라는 강의 가설을 준다.

### 데모 포인트

공유 유틸리티 변경 후 인접 테스트만 실행한 경우와 영향 매핑으로 간접 테스트까지 실행한 경우를 비교한다.

### 출처

- [TDAD: Test-Driven Agentic Development](https://arxiv.org/abs/2603.17973)

## 카드 7 — Hook이 존재하는 것과 실제로 차단하는 것은 다르다

### 개념

하니스 설정 파일에 Hook이 등록돼 있어도 이벤트 계약, exit code, timeout 또는 fail-open 정책이 잘못되면 품질 게이트가 조용히 우회될 수 있다.

### MoAI 사례

MoAI의 자체 Hook 개선 보고서는 일부 완료 게이트에서 다음 가능성을 지적한다.

- 이벤트별 JSON 응답 계약 불일치
- wrapper가 차단 exit code를 덮어씀
- 짧은 timeout으로 검사가 완료되기 전에 종료
- 게이트 파일은 있지만 설정에 연결되지 않은 dormant 상태

### 실제 용법

Hook을 정적으로 검사하는 테스트와 함께 동적 contract test를 만든다.

```text
Given 테스트가 실패하는 프로젝트
When 에이전트가 작업 완료를 선언하면
Then Hook은 완료를 차단하고 실패 이유를 반환해야 한다
```

### 데모 포인트

Hook 명령을 일부러 잘못 연결해 “설정 있음, 실제 차단 안 됨”을 재현하고 contract test로 잡는다.

## 카드 8 — 신규 기능과 레거시 코드는 다른 출발점이 필요하다

### 개념

신규 기능은 원하는 행동을 먼저 테스트한다. 테스트가 부족한 레거시는 현재 행동을 characterization test로 보존한 뒤 변경한다.

### MoAI 사례

MoAI는 TDD의 Red–Green–Refactor와 레거시용 Analyze–Preserve–Improve를 별도 workflow로 둔다. MoAI 문서의 DDD는 Domain-Driven Design과 다른 자체 용어이므로 강의에서 명확히 구분해야 한다.

### 데모 포인트

같은 `todo` 코드에 신규 “완료 처리” 기능은 TDD로 추가하고, 기존 제목 정규화 코드는 characterization test를 먼저 만든 뒤 리팩터한다.
