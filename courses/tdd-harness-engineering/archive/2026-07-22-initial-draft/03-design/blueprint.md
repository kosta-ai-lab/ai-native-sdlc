# 표준 과정 거시 설계 — TDD Harness Engineering

## 표준설계의 범위

이 문서는 특정 기관, 일정과 프로그래밍 언어에 종속되지 않는 과정의 정본이다. 기관별 시간, 기술 스택과 강조점은 `06-deliveries/`에서 adaptation decision으로 관리한다.

## 해결하려는 수행 문제

AI 코딩 에이전트는 테스트를 생성하고 실행할 수 있지만, 테스트가 올바른 이유로 실패했는지, 요구를 충분히 검증하는지, 최신 결과인지와 실패 상태에서 완료가 차단되는지를 자동으로 보장하지 않는다. 학습자는 테스트 작성법뿐 아니라 이를 에이전트의 상태 전이와 증거 체계에 연결할 수 있어야 한다.

## 최종 수행

수강자는 BDD 예제에서 검증 가능한 행동을 도출하고, 실패 테스트부터 구현하며, 역할과 증거를 분리하고, 테스트 실패 또는 오래된 증거가 있으면 완료를 차단하는 최소 에이전트 하니스를 설계·구현·검증한다.

## 최종 평가 산출물

작동하는 최소 TDD 하니스와 실패 주입 보고서다. 다음 상태를 구분해야 한다.

1. 유효한 Red는 구현 단계 진입을 허용한다.
2. 실행 오류는 구현 단계 진입을 거부한다.
3. Green과 전체 회귀 성공은 완료 후보가 된다.
4. 오래된 성공 결과는 완료를 거부한다.
5. 테스트 실패는 완료 전이를 차단한다.

## 거시적 학습 진행

```text
행동 합의
→ 유효한 Red 판정
→ 작은 TDD 구현
→ 테스트·구현 역할 분리
→ 실행 증거 모델링
→ 완료 게이트
→ 실패 주입과 종합 설계
```

## Learning Experience 후보

| 순서 | ID | 수행 변화 | 최종 평가와의 관계 |
|---:|---|---|---|
| 1 | U-01 | 모호한 요구를 구체 예제로 바꾼다 | gate의 판정 기준 생성 |
| 2 | U-02 | 올바른 Red와 실행 오류를 구분한다 | 구현 진입 조건 검증 |
| 3 | U-03 | 작은 행동을 RGR로 구현한다 | test-first 실행 능력 |
| 4 | U-04 | 테스트와 구현 변경 권한을 분리한다 | 자기합리화 방지 |
| 5 | U-05 | 실행 결과를 현재 상태와 연결한다 | stale evidence 방지 |
| 6 | U-06 | 실패 상태의 완료를 차단한다 | 핵심 하니스 구현 |
| 7 | U-07 | gate 우회를 의도적으로 시험한다 | 최종 신뢰성 검증 |

현재 샘플링 범위는 `U-02` 하나다. 나머지는 표준 과정 확정 전에 후보로 유지한다.

## 설계 원칙

- 도구 명령을 외우는 것보다 통제 원리를 다른 도구로 이전할 수 있어야 한다.
- 모든 Learning Experience가 동일한 구성 형식을 가질 필요는 없다.
- 설명량이 아니라 최종 수행에 필요한 변화로 포함 여부를 판단한다.
- 도구별 사례는 목적이 아니라 원리를 드러내는 Evidence와 case로 사용한다.
