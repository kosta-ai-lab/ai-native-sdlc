# MoAI-ADK 사례 분석

> 대상: `modu-ai/moai-adk`
>
> 조사 방법: 2026-07-22 기준 공식 GitHub 저장소와 문서 확인, 저장소 shallow clone 후 TDD 스킬·Hook·상태 관리 코드 및 자체 품질 보고서 검색

## 왜 사례로 적합한가

MoAI-ADK는 Claude Code를 단순히 프롬프트 모음으로 확장하지 않는다. SPEC, 역할별 에이전트, 스킬, Hook, 품질 기준, 세션 상태와 실행 명령을 하나의 개발 환경으로 묶는다. 특히 신규 기능과 레거시 코드에 다른 테스트 전략을 적용한다는 점에서 본 과정과 직접 연결된다.

## 공식적으로 제시하는 전체 흐름

```text
Plan → Run → Sync
  |      |      |
 SPEC   TDD/DDD  문서·PR
```

- `moai plan`: 요구를 분석하여 SPEC 작성
- `moai run`: SPEC을 TDD 또는 DDD 방식으로 구현
- `moai sync`: 문서 동기화와 PR 준비

공식 README는 모델이 확률적 작업자이므로 품질 기준, 비용, 세션 지속성과 같은 조건을 프롬프트가 아니라 외부 하니스가 유지해야 한다고 설명한다.

## 소스에서 확인한 TDD 구조

`.claude/skills/moai-workflow-tdd/SKILL.md`에서 다음을 직접 확인했다.

- 기본 개발 모드를 `tdd`로 선택 가능
- Red → Green → Refactor를 별도 단계로 정의
- acceptance criteria에서 테스트 케이스 식별
- Green에서는 테스트가 요구하지 않은 기능을 추가하지 않음
- 각 리팩터 단계 후 테스트 재실행
- 모든 acceptance criteria가 통과할 때까지 반복
- 구현과 테스트가 동시에 만들어졌거나 첫 실행부터 전부 통과하면 Red 누락 신호로 간주
- 변경 파일 커버리지와 Red 증거를 완료 체크리스트에 포함

이는 현재 `modules/06-coding-tdd`의 원칙과 상당히 유사하지만, MoAI는 이를 더 큰 상태·역할·명령 체계 안에 넣는다.

## 신규와 레거시 분기

MoAI는 다음과 같이 방법을 나눈다.

| 상황 | 방법 | 핵심 흐름 |
|------|------|-----------|
| 신규 프로젝트·기능 | TDD | Red → Green → Refactor |
| 테스트 커버리지가 낮은 기존 코드 | DDD | Analyze → Preserve → Improve |

여기서 MoAI가 사용하는 DDD는 일반적으로 알려진 Domain-Driven Design이 아니라 문서상 기존 행동 보존 중심의 방법론 명칭이다. 교육에서는 혼동을 피하기 위해 “characterization-test-first legacy workflow”라고 풀어 쓰는 편이 안전하다.

## 하니스 구성요소별 분석

| 구성요소 | 테스트 규율에서의 역할 | 과정에서 재현할 최소형 |
|----------|-------------------------|------------------------|
| SPEC | 요구와 인수조건의 기준점 | Markdown 요구·인수조건 파일 |
| TDD skill | 단계와 체크리스트 제공 | `test-first` 스킬 |
| 전문 역할 | 테스트·구현·품질 책임 분리 | test-writer, implementer, reviewer |
| Hook | 단계 전이와 완료 조건 검사 | 완료 전 테스트 실행 및 실패 차단 |
| Session state | 중단 후 작업·증거 복구 | 진행 상태 JSON/Markdown |
| Quality framework | 테스트 외 품질 조건 통합 | test + typecheck + lint |
| Coverage command | 미검증 영역 탐색 | 변경 파일 중심 커버리지 보고 |
| Loop | 실패→수정→재검증 반복 | 제한 횟수 self-verify loop |

## 강점

### 프롬프트보다 구조를 제공한다

TDD가 일회성 지시가 아니라 스킬, 상태, 역할과 명령의 일부다.

### 완료 조건을 다차원으로 본다

테스트 통과만이 아니라 가독성, 일관성, 보안, 추적성을 함께 다룬다.

### 레거시 상황을 별도로 취급한다

모든 작업에 신규 기능 TDD를 기계적으로 적용하지 않고 현재 행동 보존 단계를 둔다.

### 하니스 자체를 실제 프로젝트에 사용한다

저장소에는 SPEC 식별자, 세션 체크포인트, 테스트, 품질 보고서가 함께 존재해 dogfooding 흔적을 확인할 수 있다.

## 중요한 한계와 교육 사례

MoAI 저장소의 `.moai/reports/hooks-improvement-plan-20260710.html`은 일부 Hook 게이트에 다음 위험이 있음을 기록한다.

- `TaskCompleted` 차단 응답이 공식 이벤트 JSON 계약과 다른 형태를 사용
- 일부 Stop 게이트의 응답 중첩 구조가 공식 계약과 다름
- wrapper가 하위 명령의 차단 exit code를 덮어쓸 가능성
- LSP 검증을 수행하는 블로킹 Hook의 timeout이 너무 짧아 느린 프로젝트에서 조용히 우회될 가능성
- 설정에 연결되지 않아 사실상 dormant 상태인 게이트 가능성

이 내용은 MoAI 전체가 동작하지 않는다는 뜻이 아니다. 오히려 다음 교훈을 준다.

> 하니스의 파일·규칙·Hook이 존재하는가와 실패 상황에서 실제로 차단하는가는 다른 질문이다.

과정에서는 MoAI를 완성품으로 소개하는 데 그치지 않고 다음 실험을 해야 한다.

1. 실패하는 테스트를 둔 채 완료를 시도한다.
2. Hook이 실제로 차단하는지 확인한다.
3. timeout과 exit code를 기록한다.
4. Hook을 의도적으로 잘못 구성해 silent bypass를 재현한다.
5. 정적 설정 검사와 동적 효과 검사의 차이를 비교한다.

## 그대로 복제하지 않을 것

- 처음부터 수십 개 에이전트와 스킬을 도입하지 않는다.
- 커버리지 숫자만 품질의 대리 지표로 사용하지 않는다.
- TDD 지시문을 길게 만드는 것을 하니스 개선으로 간주하지 않는다.
- Hook이 있다고 해서 fail-closed라고 가정하지 않는다.
- MoAI의 DDD 명칭을 Domain-Driven Design과 혼용하지 않는다.

## 과정에서 가져올 핵심 아이디어

1. SPEC과 acceptance criteria를 실행의 기준점으로 둔다.
2. 테스트 작성자와 구현자의 책임을 분리한다.
3. Red 증거와 회귀 결과를 세션 상태로 남긴다.
4. 완료 조건을 자연어 선언이 아닌 기계적 게이트로 만든다.
5. 신규 기능과 레거시 코드의 테스트 전략을 분기한다.
6. 하니스 자체도 실패 주입으로 검증한다.
