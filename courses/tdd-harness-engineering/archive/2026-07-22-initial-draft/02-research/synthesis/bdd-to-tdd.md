# BDD에서 TDD로 이어지는 추적성

## 먼저 구분할 것

BDD와 TDD는 경쟁 관계가 아니다. 서로 다른 질문을 다룬다.

| 구분 | 핵심 질문 | 대표 산출물 | 주요 참여자 |
|------|-----------|-------------|-------------|
| BDD | 어떤 행동이 사용자와 비즈니스에 가치 있는가? | 예제, 규칙, Gherkin 인수조건 | 비즈니스·개발·테스트 |
| TDD | 그 행동을 만족하는 가장 단순하고 유지 가능한 설계는 무엇인가? | 실패 테스트, 최소 구현, 리팩터링 | 개발자·개발 에이전트 |

Cucumber 공식 문서는 BDD를 Discovery, Formulation, Automation의 반복으로 설명한다. 중요한 점은 Gherkin 파일을 만드는 것이 끝이 아니라, 합의된 예제를 자동화하고 그 테스트로 구현을 안내한다는 것이다.

## 권장 변환 흐름

### 1. Discovery — 규칙과 예외를 찾는다

예: “제목이 있는 할 일만 생성할 수 있다.”

질문:

- 공백만 있는 제목은 유효한가?
- 제목 길이 제한은 있는가?
- 생성자는 누가 되는가?
- 중복 제목은 허용되는가?

### 2. Formulation — 구체적인 입출력 예제로 고정한다

```gherkin
Scenario: 제목이 있는 할 일 생성
  Given 사용자가 로그인되어 있고
  When 제목 "보고서 작성"으로 할 일을 생성하면
  Then 제목 "보고서 작성"인 할 일이 생성된다

Scenario: 빈 제목 거부
  Given 사용자가 로그인되어 있고
  When 공백뿐인 제목으로 할 일을 생성하면
  Then 입력 오류가 반환된다
```

### 3. Automation — 먼저 실패하는 바깥쪽 테스트로 연결한다

인수 테스트는 시스템 행동을 확인한다. 아직 구현되지 않은 행동이므로 처음에는 실패해야 한다.

### 4. TDD — 필요한 내부 설계를 작은 테스트로 만든다

인수 테스트를 한 번에 통과시키려 하지 않고 필요한 단위 행동을 내려 쓴다.

- 제목 앞뒤 공백 제거
- 빈 제목 판정
- ID와 생성 시각 생성
- 저장 실패 처리

각 행동마다 Red → Green → Refactor를 반복하고 마지막에 인수 테스트를 통과시킨다.

## 추적성 모델

| 계층 | 예시 식별자 | 검증 질문 |
|------|-------------|-----------|
| 요구사항 | `R-01` | 사용자가 원하는 가치인가? |
| 비즈니스 규칙 | `BR-01` | 허용·거부 조건이 명확한가? |
| BDD 예제 | `AC-01`, `AC-02` | 구체적인 사례로 합의됐는가? |
| 인수 테스트 | `AT-01`, `AT-02` | 시스템 경계에서 자동 검증되는가? |
| 단위 테스트 | `UT-01` 등 | 내부 설계를 빠르게 안내하는가? |
| 구현 | 함수·모듈 | 모든 상위 행동을 최소 코드로 충족하는가? |

하니스는 이 연결을 문서 관례에만 맡기지 않고 체크리스트나 메타데이터로 검사해야 한다.

## 에이전트 환경에서 추가되는 위험

### 요구사항 세탁

에이전트가 구현하기 쉬운 방향으로 인수조건을 바꾸면 모든 테스트가 통과해도 잘못된 제품이 된다. BDD 산출물은 구현 역할과 분리하고 변경 승인을 요구해야 한다.

### 테스트 세탁

구현 에이전트가 실패 테스트를 삭제하거나 단언을 약하게 바꾸면 가짜 Green이 된다. 테스트 소유권, diff 검사, mutation test가 필요하다.

### 추적성 단절

Gherkin과 테스트가 모두 존재해도 서로 연결되지 않으면 장식 문서가 된다. 인수조건 ID가 테스트 이름이나 태그에 남아야 한다.

### 과도한 E2E

모든 예제를 UI E2E로 구현하면 느리고 불안정한 하니스가 된다. 행동은 인수 수준에서 표현하되 가장 낮고 빠른 적절한 계층에서 자동화한다.

## 과정에서 다룰 핵심 판단

- BDD는 테스트 자동화의 동의어가 아니다.
- 인수 테스트와 단위 테스트는 같은 행동을 다른 해상도로 본다.
- 모든 Gherkin 시나리오를 UI 테스트로 만들 필요는 없다.
- 구현 에이전트는 합의된 인수조건을 독단적으로 변경할 수 없어야 한다.
- Red 증거와 요구사항 추적성이 없는 Green은 신뢰할 수 없다.
