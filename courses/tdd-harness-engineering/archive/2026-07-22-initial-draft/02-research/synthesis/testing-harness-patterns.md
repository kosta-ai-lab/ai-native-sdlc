# 테스트 중심 에이전트 하니스 패턴

## 하니스의 역할

에이전트 하니스는 모델 바깥에서 작업 환경, 도구, 상태, 피드백, 권한과 완료 조건을 설계한다. 테스트 중심 하니스는 에이전트가 좋은 의도를 가졌다고 가정하지 않고 관찰 가능한 결과로 다음 단계 진입을 통제한다.

## 패턴 1 — 역할 분리

| 역할 | 허용 | 금지 |
|------|------|------|
| BDD analyst | 규칙·예제·인수조건 작성 | 구현 코드 변경 |
| Test writer | 인수조건을 실패 테스트로 변환 | 프로덕션 구현 작성 |
| Implementer | 테스트를 통과하는 최소 구현 작성 | 승인 없이 테스트·인수조건 변경 |
| Reviewer | 추적성·테스트 강도·회귀 확인 | 자신의 결과를 단독 승인 |

목적은 멀티에이전트 자체가 아니라 이해상충을 줄이는 것이다. 한 에이전트가 요구사항, 테스트, 구현, 승인을 모두 소유하면 스펙 게이밍이 쉬워진다.

## 패턴 2 — Red 증거 캡처

실패 테스트 파일이 존재하는 것만으로는 test-first를 증명하지 못한다. 하니스는 다음 증거를 남긴다.

- 실행 명령
- 실패한 테스트 이름
- 실패 이유
- 실행 시점의 Git diff 또는 체크포인트
- 실패가 환경 오류가 아니라 기대 행동 미구현 때문인지 판정

`Cannot find module`, 문법 오류, 패키지 미설치도 빨간색이지만 유효한 TDD Red와 동일하지 않다. 과정에서는 “의미 있는 실패”를 구분해야 한다.

## 패턴 3 — 테스트 불변 영역

Green 단계에서 테스트 변경을 기본 차단한다.

구현 도중 테스트 수정이 정말 필요하면:

1. 변경 사유를 기록한다.
2. BDD 인수조건과의 일치 여부를 다시 검사한다.
3. test-writer 또는 사람이 승인한다.
4. 수정한 테스트의 Red를 다시 확인한다.

## 패턴 4 — 계층형 피드백 루프

모든 변경마다 전체 E2E를 실행하면 느리고 비싸다. 다음처럼 피드백 속도를 계층화한다.

1. 변경 파일 관련 단위 테스트
2. 관련 통합 테스트
3. 타입 검사·린트·정적 분석
4. 전체 회귀 테스트
5. 핵심 사용자 여정 E2E

에이전트에게는 현재 변경과 관련 테스트의 관계를 제공해야 한다. 2026년 TDAD 연구는 절차적 TDD 지시보다 코드–테스트 영향 컨텍스트가 회귀 감소에 유용할 수 있음을 보여준다. 단, 해당 연구는 제한된 로컬 모델과 SWE-bench 표본에 대한 사전 공개 연구이므로 일반화에는 추가 검증이 필요하다.

## 패턴 5 — 완료 게이트

완료는 에이전트의 자연어 선언이 아니라 조건식이다.

```text
DONE =
  모든 인수조건이 테스트에 매핑됨
  AND 신규 테스트의 Red 증거가 있음
  AND 관련 테스트 통과
  AND 전체 회귀 테스트 통과
  AND 타입·린트 기준 통과
  AND 승인되지 않은 테스트 완화가 없음
```

Hook은 조건을 검사하고 실패하면 작업 완료, 커밋 또는 PR 전이를 막는다. 단, Hook 자체도 이벤트 계약, exit code, timeout, fail-open/fail-closed 동작을 테스트해야 한다.

## 패턴 6 — 테스트의 테스트

통과하는 테스트가 결함을 잡는다는 보장은 없다.

- Mutation testing: 구현에 작은 결함을 넣어 테스트가 실패하는지 확인
- Negative control: 핵심 단언을 제거했을 때 품질 게이트가 탐지하는지 확인
- Hidden tests: 구현 역할이 보지 못하는 검증 케이스 유지
- Contract tests: 테스트와 인수조건의 ID·예상 결과 연결 검사

## 패턴 7 — 신규와 레거시의 분기

| 상황 | 권장 시작점 | 흐름 |
|------|-------------|------|
| 신규 기능 | 원하는 행동 | BDD → 실패 테스트 → 최소 구현 |
| 테스트가 충분한 기존 시스템 | 변경할 행동과 영향 테스트 | 영향 분석 → TDD → 전체 회귀 |
| 테스트가 거의 없는 레거시 | 현재 행동 | 분석 → Characterization Test → 안전한 개선 |

Characterization Test는 현재 버그도 고정할 수 있다. 따라서 현재 행동과 원하는 행동을 구분하고, 승인된 변경만 별도 TDD 사이클로 전환해야 한다.

## 사용 사례

### 기능 개발

인수조건에서 테스트를 생성하고 구현 에이전트가 최소 코드만 작성하도록 통제한다.

### 버그 수정

버그를 재현하는 실패 테스트를 먼저 추가하고, 수정 후 관련 회귀 테스트를 실행한다.

### 레거시 리팩터링

현재 행동을 characterization test로 고정하고 작은 구조 변경마다 회귀를 확인한다.

### 대규모 병렬 에이전트 작업

각 작업을 격리된 브랜치나 worktree에서 수행하고, 공통 계약 테스트와 전체 회귀 게이트를 통과한 결과만 통합한다.

### 하니스 자체 변경

Hook이나 완료 조건을 수정할 때 일부러 실패 조건을 만들어 실제로 차단되는지 검증한다. 설정 파일이 존재한다는 정적 검사만으로는 충분하지 않다.
