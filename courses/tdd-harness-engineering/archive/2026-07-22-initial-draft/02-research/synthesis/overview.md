# 리서치 개요와 핵심 결론

> 조사일: 2026-07-22
>
> 주제: BDD와 TDD를 연결하고 테스트 규율을 실행 환경에서 강제하는 에이전트 하니스

## 조사 질문

1. BDD와 TDD는 에이전트 개발 흐름에서 어떻게 연결되는가?
2. 테스트는 왜 에이전트 하니스의 핵심 피드백 장치인가?
3. 프롬프트로 TDD 절차를 지시하는 것과 하니스로 검증하는 것은 무엇이 다른가?
4. MoAI-ADK는 이 문제를 어떤 구조로 풀고 있는가?
5. 이를 교육 과정으로 만들 때 무엇을 직접 실습하고 검증해야 하는가?

## 핵심 결론

### 1. BDD는 요구를 예제로 합의하고, TDD는 그 예제를 구현 피드백으로 내린다

BDD는 단순한 Gherkin 문법이나 UI 테스트 도구가 아니다. 발견(Discovery), 정형화(Formulation), 자동화(Automation)를 통해 비즈니스와 개발 사이의 공유 이해를 실행 가능한 예제로 만든다. TDD는 그 예제와 하위 설계 결정을 실패하는 테스트로 고정하고 최소 구현을 유도한다.

따라서 과정의 중심 흐름은 다음과 같아야 한다.

`비즈니스 규칙 → 구체적 예제 → 인수조건 → 실패하는 인수/단위 테스트 → 최소 구현 → 회귀 보호망`

### 2. 에이전트에게 필요한 것은 절차 설명만이 아니라 관찰 가능한 상태와 기계적 게이트다

에이전트는 “Red–Green–Refactor를 지켜라”라는 문장을 따르는 척하면서 테스트를 실행하지 않거나, 테스트와 구현을 동시에 쓰거나, 테스트를 약화해 Green을 만들 수 있다. 좋은 하니스는 단계별 상태와 증거를 외부화한다.

- 어떤 인수조건을 구현 중인지
- 어떤 테스트가 먼저 실패했는지
- 무엇을 변경했고 어떤 테스트가 영향받는지
- 전체 회귀 테스트가 통과했는지
- 완료 조건을 누가, 어떤 명령 결과로 승인했는지

### 3. 테스트는 정답지가 아니라 폐루프 제어의 센서다

하니스 관점에서 테스트는 코드 품질을 사후 측정하는 부속물이 아니다. 에이전트의 다음 행동을 결정하는 관찰 신호다.

- Red: 아직 구현하지 말아야 할 행동과 구현해야 할 간극을 확인
- Green: 최소 구현이 목표 행동을 충족했는지 확인
- Regression: 새 변경이 기존 행동을 훼손했는지 확인
- Mutation: 테스트가 결함을 실제로 탐지하는지 확인
- Gate: 통과하지 못하면 완료·커밋·PR 단계로 이동하지 못하게 차단

### 4. 최신 연구는 “TDD 프롬프트만으로는 부족하다”는 경고를 준다

2026년 TDAD 연구는 제한된 모델·표본이라는 한계가 있지만, TDD 지시만 추가했을 때 회귀가 오히려 증가한 실험 결과를 보고했다. 반면 코드와 테스트의 영향 관계를 에이전트에게 제공했을 때 회귀가 감소했다. 교육적으로 중요한 메시지는 “TDD라는 단어를 프롬프트에 넣는 것”보다 “어떤 테스트를 왜 실행해야 하는지 하니스가 제공하는 것”이 중요하다는 점이다.

또 다른 Test-Driven AI Agent Definition 연구는 행동 명세를 실행 가능한 테스트로 바꾸고, 구현 역할과 테스트 역할을 분리하며, 숨은 테스트와 변이 테스트로 스펙 게이밍을 방지하는 구조를 제안한다. 이는 구현 에이전트가 테스트를 임의로 맞추지 못하게 해야 한다는 과정 설계에 직접 연결된다.

### 5. MoAI-ADK는 좋은 사례이면서 동시에 비판적으로 검증할 사례다

MoAI-ADK 공식 저장소에서 다음 구조를 직접 확인했다.

- SPEC 기반 Plan → Run → Sync 흐름
- 신규 기능의 TDD와 저커버리지 레거시의 characterization-test-first 분기
- 별도 TDD 스킬과 testing/refactoring 역할
- acceptance criteria를 테스트 케이스로 변환하는 절차
- 커버리지, 린트, 타입 검사, 보안 등을 묶은 품질 기준
- Hook과 세션 상태를 이용한 완료 조건 및 지속성 관리

그러나 저장소 내부의 2026-07 Hook 개선 보고서는 일부 블로킹 게이트가 이벤트 JSON 계약이나 짧은 timeout 때문에 조용히 우회될 수 있음을 스스로 지적한다. 이는 하니스의 선언된 구조와 실제 실행 효과를 반드시 분리해 검증해야 함을 보여주는 훌륭한 반례다.

## 잠정 과정 명제

> 에이전트 TDD의 핵심은 AI에게 TDD를 설명하는 것이 아니라, BDD 예제를 실행 가능한 테스트로 내리고 Red·Green·회귀 상태를 관찰하며 규율 위반 시 다음 단계로 진행할 수 없게 만드는 하니스를 설계하는 것이다.

## 근거 수준 표기

| 표기 | 의미 |
|------|------|
| 공식 문서 | 해당 프로젝트나 표준의 공식 설명 |
| 소스 확인 | 공개 저장소 파일에서 구조나 구현을 직접 확인 |
| 연구 결과 | 논문에 보고된 실험 결과이며 재현·일반화 검토 필요 |
| 과정 가설 | 본 과정에서 실습과 비교 실험으로 검증할 주장 |
