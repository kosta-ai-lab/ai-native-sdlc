# MoAI-ADK 심층 사례 연구

## 1. 사례를 선택한 이유

MoAI-ADK는 Claude Code 위에서 동작하는 Agentic Development Kit다. 이 프로젝트가 본 과정의 사례로 유용한 이유는 TDD라는 지침 하나를 제공하는 데 그치지 않고, 명세, 역할, 스킬, Hook, 세션 상태와 품질 기준을 하나의 실행 흐름으로 묶기 때문이다.

공식 저장소는 MoAI를 모델 바깥에서 신뢰성과 비용 예측 가능성을 제공하는 하니스로 설명한다. 모델은 토큰 단위로 다음 행동을 생성하는 확률적 작업자이므로, 지난 세션의 상태, 반드시 통과해야 하는 테스트, 허용된 비용과 완료 조건을 모델 자체 기억에만 맡길 수 없다는 관점이다.

이 문서는 MoAI가 훌륭하다는 결론을 미리 정해두고 기능을 소개하지 않는다. 공식 문서가 설명하는 의도, 공개 저장소에서 확인한 구조, 실제 적용 전에 검증해야 할 한계를 구분한다. 특히 MoAI 저장소 자체에 포함된 Hook 개선 보고서는 복잡한 하니스도 품질 게이트가 조용히 무력화될 수 있음을 보여준다.

## 2. Plan–Run–Sync라는 전체 구조

MoAI의 대표적인 개발 흐름은 Plan, Run, Sync 세 단계다. 사용자는 프로젝트를 초기화한 뒤 Claude Code 안에서 명령을 실행한다.

```bash
moai init todo-harness-lab
cd todo-harness-lab
claude
```

이 초기화는 단순히 빈 프로젝트 폴더를 만드는 명령으로 이해하면 안 된다. 공식 설명에 따르면 언어와 프레임워크, 개발 방법을 감지하고 Claude Code가 사용할 에이전트, 스킬, 명령, Hook과 MoAI 상태 디렉터리를 구성한다. 즉 애플리케이션 코드만 만드는 것이 아니라 에이전트가 일할 작업 환경을 만든다.

그다음 Claude Code 세션에서 다음과 같은 흐름을 사용한다.

```text
/moai plan "로그인한 사용자의 할 일 생성 기능"
/moai run SPEC-TODO-001
/moai sync SPEC-TODO-001
```

`plan`은 자연어 요구를 분석해 구현 전에 SPEC과 관련 산출물을 만든다. `run`은 SPEC을 읽고 설정된 방법론에 따라 구현한다. `sync`는 구현 이후 문서 상태를 맞추고 PR 준비까지 연결한다. 중요한 점은 세 명령이 단순한 편의 명령이 아니라 상태 전이를 표현한다는 것이다. 구현은 승인되지 않은 요구에서 바로 시작해서는 안 되고, 완료되지 않은 품질 검증을 건너뛰고 동기화 단계로 넘어가서도 안 된다.

강의에서 이 흐름을 시연할 때는 명령을 실행하는 화면만 보여주면 부족하다. 각 단계 전후에 어떤 파일이 생겼고 어떤 상태 필드가 바뀌었는지, 다음 단계가 이전 산출물을 실제로 읽고 있는지 확인해야 한다.

## 3. SPEC이 테스트의 기준점이 되는 방법

MoAI의 TDD workflow는 구현 전에 SPEC 문서를 읽고 acceptance criteria에서 테스트 케이스를 식별하도록 정의돼 있다. 이는 테스트 생성의 기준을 현재 코드나 에이전트의 추측이 아니라 승인된 명세에 두려는 구조다.

예를 들어 다음과 같은 요구와 인수조건이 있다고 하자.

```markdown
## REQ-TODO-001

시스템은 로그인한 사용자가 제목으로 할 일을 생성할 수 있게 해야 한다.

## Acceptance Criteria

- AC-TODO-001: 유효한 제목이면 생성된 할 일을 반환한다.
- AC-TODO-002: 공백뿐인 제목이면 입력 오류를 반환한다.
- AC-TODO-003: 생성된 할 일에는 현재 사용자 ID가 기록된다.
```

구현 에이전트는 이 문장을 읽고 바로 코드를 쓰지 않는다. 먼저 각 인수조건이 어느 테스트에서 검증될지 계획한다. 공백 제목 검사는 빠른 단위 테스트와 API 인수 테스트로 나뉠 수 있고, 사용자 ID 기록은 인증과 저장소를 포함하는 통합 테스트가 적합할 수 있다.

MoAI의 plan auditor 자료에서는 모든 요구가 적어도 하나의 acceptance criterion을 가져야 하고, 모든 criterion은 존재하는 요구를 참조해야 하며, 사람이 주관적으로 해석하지 않고 PASS/FAIL을 판정할 수 있어야 한다는 검토 기준을 확인할 수 있다. 이 구조는 명세를 많이 작성하는 것보다 테스트 가능한 명세를 만드는 데 초점을 둔다.

그러나 실제 강의에서는 MoAI의 명세 형식을 그대로 정답으로 가르치면 안 된다. EARS나 GEARS 같은 특정 형식은 도구가 선택한 한 가지 방법이다. 더 일반적인 원칙은 요구, 인수조건과 테스트 사이에 고아 항목이나 누락이 없어야 하고, 합격 기준이 이진적으로 판정 가능해야 한다는 것이다.

## 4. 개발 모드와 신규·레거시 분기

조사한 MoAI TDD 스킬은 `.moai/config/sections/quality.yaml`의 `development_mode`를 기준으로 TDD와 레거시 workflow를 구분한다.

```yaml
constitution:
  development_mode: tdd
```

TDD 모드는 새 기능을 원하는 행동의 실패 테스트에서 시작해 Red–Green–Refactor로 구현하는 데 사용한다. 기존 코드의 행동 보존이 우선이고 테스트가 부족한 경우에는 `ddd` 모드를 사용할 수 있다.

```yaml
constitution:
  development_mode: ddd
```

여기서 주의할 점이 있다. MoAI 문서에서 사용하는 DDD는 일반적인 Domain-Driven Design을 뜻하지 않는다. 문서상 Analyze–Preserve–Improve 흐름으로, 현재 행동을 characterization test로 고정한 뒤 구조를 개선하는 자체 방법론 명칭이다. 강의에서 이 용어를 그대로 사용하면 수강생이 도메인 주도 설계와 혼동할 수 있으므로 “레거시 행동 보존 workflow”라고 풀어서 설명해야 한다.

또한 설정값을 선택하는 것만으로 올바른 방법이 자동 보장되는 것은 아니다. 신규 파일이 포함됐다는 이유만으로 TDD를 선택할 수 없고, 기존 파일을 수정한다는 이유만으로 characterization 방식이 필요한 것도 아니다. 작업이 원하는 새 행동을 추가하는지, 현재 행동을 보존하는지, 기존 테스트가 충분한지를 먼저 판단해야 한다.

## 5. MoAI가 정의하는 Red 단계

공개 저장소의 `.claude/skills/moai-workflow-tdd/SKILL.md`에서 Red 단계의 구체적인 규율을 확인했다. 구현 전에 요구를 이해하고, 한 번에 하나의 행동을 표현하는 테스트를 쓰며, 테스트 이름은 함수 이름보다 기대 행동을 설명해야 한다. 테스트는 실제로 실행해 올바른 이유로 실패하는지 확인한다.

특히 교육적으로 가치 있는 부분은 Red 누락 신호다. MoAI 자료는 구현 파일과 테스트 파일이 같은 커밋에서 만들어졌거나, 새 테스트 파일의 모든 테스트가 첫 실행부터 통과하면 Red 단계가 생략됐을 가능성을 의심한다. 물론 같은 커밋에 테스트와 구현이 있다는 사실만으로 TDD를 하지 않았다고 단정할 수는 없다. 한 커밋 안에서도 Red와 Green 실행 증거를 남길 수 있기 때문이다. 그래서 MoAI의 검증 목록도 Git 이력 또는 같은 커밋 안의 Red 증거를 요구한다.

강의에서는 다음과 같은 증거 형식을 사용할 수 있다.

```markdown
## RED EVIDENCE — AC-TODO-002

- 실행 명령: pnpm vitest run test/todo.test.ts
- 기대한 실패: 공백 제목이 거부되어야 함
- 실제 실패: 오류 대신 빈 제목 Todo 객체가 반환됨
- 관련 없는 실패: 없음
- 소스 상태: AC-TODO-002를 위한 production 변경 전
```

이 기록의 목적은 문서를 늘리는 것이 아니다. 실패가 환경 문제가 아니라 원하는 행동의 부재 때문이었는지, 구현이 테스트보다 먼저 작성되지 않았는지를 재검토할 수 있게 하는 것이다.

## 6. Green과 Refactor에서의 통제

MoAI의 `manager-develop` 자료는 Green 단계에서 테스트가 지정한 일반 해법을 작성하라고 요구한다. 특정 fixture 입력에만 맞춘 하드코딩을 금지하고, 구현 직후 테스트를 실행하며, 기존 테스트가 계속 통과하고 LSP 오류가 없어야 한다고 정의한다.

이 규칙은 “테스트를 통과하는 최소 코드”라는 표현에서 흔히 생기는 오해를 줄인다. 최소라는 말은 가장 짧은 문자열이나 특정 예제만 통과하는 편법을 뜻하지 않는다. 현재 합의된 행동을 일반적으로 만족하되 아직 요구되지 않은 확장 기능과 추상화를 넣지 않는다는 뜻이다.

Refactor 단계에서는 중복 제거, 이름 개선, 책임 분리 같은 구조 개선을 수행한다. MoAI 자료는 변경 뒤 테스트를 재실행하고, 전체 스위트와 커버리지 조건을 확인하며, 각 Red–Green–Refactor 사이클 뒤 체크포인트를 남기는 구조를 설명한다. 체크포인트는 세션이 중단돼도 작업 상태를 복구하고, 큰 리팩터가 실패했을 때 어느 지점으로 돌아갈지 결정하는 데 도움이 된다.

## 7. 역할과 소유권 경계

MoAI 공개 저장소에는 명세, 개발, E2E, 품질과 감사에 특화된 여러 에이전트 정의가 있다. 중요한 것은 에이전트 수가 아니라 역할 사이의 소유권 경계다.

예를 들어 `manager-develop`은 구현과 테스트 실행을 담당하지만 SPEC 본문을 임의로 고칠 수 없도록 규정돼 있다. 구현 도중 요구 문장이 부족하거나 acceptance criterion을 강화해야 한다는 사실을 발견하면, 자신이 문서를 조용히 바꾸는 대신 blocker를 반환하고 명세 담당 역할로 다시 위임해야 한다.

`plan-auditor`는 구현 전에 명세를 비판적으로 검토하며 작성자의 추론 맥락을 무시하고 최종 문서만 독립적으로 평가하도록 설계돼 있다. 이는 작성자와 검토자가 같은 결론을 합리화하는 위험을 줄이려는 장치다. `e2e-tester`는 애플리케이션 소스를 부수적으로 고치지 않고 E2E 산출물과 설정 범위에서 작업하도록 제한된다.

강의에서는 이 구조를 수십 개 에이전트로 복제할 필요가 없다. 다음 세 역할이면 핵심 위험을 보여줄 수 있다.

- test-writer: 인수조건을 테스트로 만들고 Red를 확인한다.
- implementer: 승인된 테스트를 바꾸지 않고 최소 구현을 작성한다.
- reviewer: 요구 추적, 테스트 강도와 회귀 결과를 독립 확인한다.

## 8. Hook이 상태 전이를 통제하는 방식

조사한 `.claude/settings.json`에는 도구 실행 전후, 세션 종료, 팀 작업 완료 같은 여러 이벤트에 Hook이 연결돼 있다. 예를 들어 `PreToolUse`는 Write, Edit와 Bash 전에 실행되고, `PostToolUse`는 파일 변경 뒤 상태 전이와 관찰을 수행한다. `Stop`, `TeammateIdle`, `TaskCompleted`에도 종료 또는 완료 조건을 검사하는 Hook이 배치돼 있다.

이 구조의 목적은 에이전트가 지침을 기억하기를 기대하는 대신 중요한 전환점마다 외부 검사를 실행하는 것이다. 테스트가 실패한 상태에서 작업 완료를 선언하거나, 필수 명세 없이 팀 작업을 끝내려 할 때 Hook이 상태 전이를 막을 수 있다.

그러나 Hook은 설정됐다는 사실만으로 안전장치가 되지 않는다. 이벤트마다 기대하는 입력과 출력 계약이 다르고, process exit code와 timeout의 의미도 다르다. 검사 스크립트가 올바른 판단을 해도 wrapper가 exit code를 0으로 바꾸거나 반환 JSON의 필드가 틀리면 Claude Code 런타임이 차단을 인식하지 못할 수 있다.

## 9. MoAI 자체 보고서가 보여주는 한계

MoAI 저장소의 `.moai/reports/hooks-improvement-plan-20260710.html`은 이 문제를 구체적으로 기록한다. 보고서에는 일부 `TaskCompleted` 차단 응답이 공식 이벤트 계약과 다른 필드를 사용하고, Stop 응답의 중첩 구조가 맞지 않으며, wrapper가 하위 명령의 차단 exit code를 덮어쓸 가능성이 있다는 분석이 있다. 또한 LSP 검증을 수행하는 Hook의 timeout이 짧으면 큰 프로젝트에서 검사 완료 전에 종료되어 조용히 우회될 수 있고, 파일은 존재하지만 실제 설정에 연결되지 않은 dormant 게이트 가능성도 지적한다.

이 보고서를 “MoAI가 나쁜 도구”라는 증거로 해석해서는 안 된다. 오히려 복잡한 하니스가 자기 문제를 분석하고 개선 기록을 남기는 dogfooding 사례다. 동시에 선언된 아키텍처와 실제 실행 효과를 구분해야 한다는 교훈을 준다.

강의에서는 이 사례를 슬라이드로만 소개하지 말고 작은 Hook으로 재현하는 편이 좋다. 테스트 실패 상태에서 완료 이벤트를 보내고 올바른 JSON을 반환할 때는 차단되는지 확인한다. 그다음 필드 이름을 일부러 바꾸거나 timeout을 매우 짧게 만들어 정적 설정은 그대로지만 동적 차단이 사라지는 모습을 보여준다.

## 10. MoAI에서 가져올 것과 가져오지 않을 것

MoAI에서 가져올 핵심은 SPEC을 실행 기준으로 삼는 구조, 신규와 레거시 workflow의 구분, 단계별 증거와 체크포인트, 역할 소유권, 완료 Hook과 품질 기준이다.

반면 첫 수업부터 수십 개 에이전트와 스킬을 설치하는 것은 피해야 한다. 수강생은 어떤 구성요소가 어떤 실패를 막는지 이해하지 못한 채 완성된 시스템의 명령만 외울 수 있다. 커버리지 수치를 품질 그 자체로 받아들이거나, Hook 파일의 존재를 실제 검증으로 간주해서도 안 된다.

따라서 교육 순서는 최소 하니스를 먼저 직접 만드는 방향이 적절하다. test-writer와 implementer를 분리하고, Red 증거 파일과 테스트 실패 완료 차단 Hook을 만든다. 수강생이 각 장치의 필요성을 경험한 뒤 MoAI를 보면 대형 하니스의 구성요소가 왜 존재하는지 이해할 수 있다.

## 맺음말

MoAI-ADK는 TDD를 프롬프트 문구가 아니라 개발 환경의 상태 흐름으로 다루는 실제 사례다. 명세에서 테스트를 도출하고, 역할과 권한을 나누며, 테스트와 품질 결과를 완료 조건에 연결한다. 동시에 자체 Hook 보고서는 하니스도 소프트웨어이므로 테스트와 관찰성이 필요하다는 사실을 보여준다.

이 사례를 강의에 사용할 때 가장 중요한 질문은 “MoAI 명령을 어떻게 쓰는가”가 아니다. “이 구성요소는 어떤 실패를 막고, 그 차단 효과를 어떤 증거로 확인할 수 있는가”다.
