# BDD, TDD와 에이전트 하니스의 연결

## 들어가며

AI 코딩 에이전트를 개발에 도입하면 코드가 만들어지는 속도는 빨라진다. 그러나 코드 생성 속도가 빨라졌다는 사실과 올바른 소프트웨어를 안정적으로 만들 수 있다는 사실은 다르다. 에이전트는 모호한 요구를 그럴듯하게 해석하고, 아직 합의되지 않은 정책을 임의로 구현하며, 자신이 작성한 테스트를 자신에게 유리하게 수정할 수 있다. 테스트를 실행했다고 말하면서 실제 실행 결과를 남기지 않거나, 새 기능은 통과시키면서 기존 기능을 깨뜨리는 일도 생긴다.

이 문제를 “더 자세한 프롬프트를 쓰면 해결된다”고 보는 접근에는 한계가 있다. 프롬프트는 행동 지침을 전달하지만, 그 지침이 실제로 지켜졌는지를 외부에서 확인하고 다음 행동을 통제하지는 못한다. 사람에게 안전수칙을 읽어주는 것과 안전장치가 설치된 작업 환경을 제공하는 것이 다른 것처럼, 에이전트에게 TDD를 설명하는 것과 TDD를 지키도록 실행 환경을 설계하는 것은 다른 문제다.

이 장에서는 BDD와 TDD가 각각 무엇을 해결하는지 살펴보고, 두 방법을 에이전트 하니스 안에서 어떻게 연결할 수 있는지 설명한다. 핵심 주장은 간단하다.

> BDD는 무엇을 만들어야 하는지 구체적인 예제로 합의하고, TDD는 그 합의를 실행 가능한 피드백으로 바꾸며, 하니스는 그 피드백이 실제 개발 행동을 통제하도록 만든다.

## 1. 요구사항이 코드로 넘어갈 때 생기는 간극

“사용자는 할 일을 생성할 수 있다”라는 요구를 생각해보자. 문장 자체는 이해하기 쉽지만 구현하기에는 정보가 부족하다. 제목이 비어 있으면 어떻게 해야 하는지, 공백만 입력한 경우를 빈 제목으로 볼 것인지, 로그인하지 않은 사용자의 요청을 허용할 것인지, 제목 길이나 중복을 제한할 것인지가 정해져 있지 않다.

사람 개발자는 이런 모호함을 발견하면 기획자나 사용자에게 질문할 수 있다. 하지만 AI 에이전트는 질문 대신 가장 그럴듯한 정책을 만들어 코드에 넣는 경향이 있다. 코드가 동작하고 테스트까지 통과하더라도, 그 테스트와 구현이 에이전트가 스스로 만든 정책을 검증하고 있을 수 있다. 이 경우 기술적으로는 일관돼 보이지만 비즈니스 요구와는 어긋난다.

따라서 첫 번째 문제는 코딩이 아니다. 합의되지 않은 부분을 발견하고, 실제 사례를 통해 기대 행동을 명확히 만드는 일이다. 이것이 BDD가 담당하는 영역이다.

## 2. BDD가 해결하는 문제

BDD, 즉 Behaviour-Driven Development는 흔히 Given–When–Then 문법이나 Cucumber 테스트와 같은 것으로 소개된다. 그러나 Cucumber 공식 문서는 BDD를 특정 문법이나 테스트 도구보다 넓은 협업 방식으로 설명한다. 관계자들이 구체적인 예제를 중심으로 문제를 이해하고, 그 예제를 사람이 읽을 수 있으면서 자동화 가능한 형태로 정리한 뒤, 실제 시스템 행동과 계속 맞춰가는 과정이다.

공식 문서가 제시하는 세 활동은 Discovery, Formulation, Automation이다.

### 2.1 Discovery: 구현 전에 모호함을 발견한다

Discovery에서는 사용자 스토리를 곧바로 테스트 문장으로 바꾸지 않는다. 먼저 실제 사례를 놓고 규칙과 예외를 질문한다. “할 일 생성” 사례라면 다음과 같은 대화가 필요하다.

- 제목 `보고서 작성`은 유효하다.
- 제목이 빈 문자열이면 거부한다.
- 제목이 공백 세 칸뿐이어도 거부한다.
- 제목 앞뒤 공백은 제거한다.
- 제목 중복은 현재 범위에서는 허용한다.
- 로그인하지 않은 사용자는 생성할 수 없다.

이 과정의 목적은 가능한 모든 경우를 나열하는 것이 아니다. 구현에 영향을 주는 비즈니스 규칙과 아직 답하지 못한 질문을 드러내는 것이다. 규칙, 예제, 질문을 구분해 놓으면 무엇이 확정됐고 무엇이 추가 합의를 기다리는지 보인다.

에이전트는 Discovery를 보조할 수 있다. 입력한 사용자 스토리에서 경계값과 예외 후보를 제안하고, 빠진 질문을 찾게 할 수 있다. 그러나 최종 정책을 정하는 권한까지 에이전트에게 넘기면 안 된다. 예제를 생성하는 일과 예제를 승인하는 일은 구분해야 한다.

### 2.2 Formulation: 합의된 예제를 읽을 수 있는 명세로 만든다

Discovery에서 합의한 사례는 자동화 가능한 문장으로 정리한다. Gherkin은 이를 위한 한 가지 표현 방법이다.

```gherkin
Feature: 할 일 생성

  Scenario: 유효한 제목으로 할 일 생성
    Given 사용자 "user-01"이 로그인되어 있고
    When 제목 "  보고서 작성  "으로 할 일을 생성하면
    Then 제목 "보고서 작성"인 할 일이 생성되고
    And 생성자 ID는 "user-01"이다

  Scenario: 공백뿐인 제목 거부
    Given 사용자 "user-01"이 로그인되어 있고
    When 제목 "   "으로 할 일을 생성하면
    Then "제목은 필수입니다" 오류가 반환된다
```

좋은 시나리오는 사용자에게 보이는 행동과 비즈니스 규칙을 표현한다. 특정 UI 버튼의 CSS 선택자나 내부 함수 이름 같은 구현 세부사항을 넣지 않는다. 그래야 UI나 내부 구조가 바뀌어도 비즈니스 행동 문서로 남을 수 있다.

또한 모든 Gherkin 문장이 좋은 명세인 것은 아니다. “적절히 처리한다”, “정상적으로 동작한다” 같은 표현은 합격과 불합격을 판정할 수 없다. 에이전트가 테스트를 생성하려면 입력, 행동과 기대 결과가 이진적으로 판단 가능해야 한다.

### 2.3 Automation: 문서를 시스템 행동과 연결한다

Formulation 결과가 문서로만 남으면 시간이 지나면서 실제 코드와 어긋날 수 있다. Automation에서는 합의된 예제를 실행 가능한 테스트에 연결한다. 아직 행동이 구현되지 않았다면 이 테스트는 실패해야 한다. 구현이 끝난 뒤에는 통과하고, 이후 변경으로 행동이 깨지면 다시 실패해야 한다.

이 지점에서 BDD는 TDD와 만난다. BDD 예제는 바깥에서 관찰할 수 있는 행동을 말하고, TDD는 그 행동을 구현하는 데 필요한 더 작은 설계 결정을 테스트로 내려 쓴다.

## 3. TDD가 해결하는 문제

TDD, 즉 Test-Driven Development는 테스트를 먼저 작성한다는 규칙만을 뜻하지 않는다. 기대 행동을 작은 테스트로 표현하고, 그 테스트의 실패와 통과를 이용해 구현 범위와 설계를 점진적으로 결정하는 개발 리듬이다. 전형적인 흐름은 Red, Green, Refactor다.

### 3.1 Red: 아직 충족하지 못한 행동을 관찰한다

Red 단계에서는 원하는 행동을 표현하는 테스트를 먼저 작성하고 실행한다. 테스트가 실패하는 것을 실제로 확인해야 한다. 이 확인은 테스트가 무언가를 검증하고 있으며, 현재 시스템과 원하는 시스템 사이에 간극이 있음을 보여준다.

여기서 모든 실패가 유효한 Red는 아니다. 테스트 패키지가 설치되지 않았거나 import 경로가 틀려 테스트가 시작조차 되지 않았다면, 원하는 행동의 부재를 관찰한 것이 아니다. 다음과 같은 실패가 더 의미 있는 Red다.

```text
expected createTodo("   ") to throw "제목은 필수입니다"
received { id: "todo-1", title: "", ... }
```

이 결과는 테스트 환경이 동작하고 있으며, 현재 구현이 공백 제목을 잘못 허용한다는 사실을 보여준다. 반대로 `vitest: command not found`는 환경 설정 오류이므로 먼저 환경을 고쳐야 한다.

에이전트 환경에서는 Red를 말로 보고하게 하는 것만으로 충분하지 않다. 실행 명령, 실패한 테스트 이름, 기대값과 실제값, 당시 소스 변경 상태를 증거로 남기는 편이 좋다. 그래야 구현이 테스트보다 먼저 작성됐는지, 실패 이유가 올바른지 나중에 검토할 수 있다.

### 3.2 Green: 테스트를 통과하는 가장 단순한 일반 해법을 만든다

Green 단계에서는 현재 실패 테스트를 통과시키는 데 필요한 코드만 작성한다. 미래에 필요할 것 같은 옵션이나 추상화를 미리 추가하지 않는다. 테스트가 요구한 행동에 집중함으로써 에이전트가 명세에 없는 기능을 지어내는 범위를 줄인다.

다만 “최소 구현”을 특정 fixture에 대한 하드코딩으로 오해하면 안 된다. 테스트 입력이 `보고서 작성`일 때 항상 같은 Todo 객체를 반환하는 코드는 한 테스트를 통과하지만 행동을 일반적으로 구현하지 않는다. 최소 구현은 단순하되 테스트가 표현한 규칙을 다른 유효 입력에도 적용할 수 있어야 한다.

이 단계에서 구현 에이전트가 테스트 파일을 자유롭게 수정할 수 있으면 위험하다. 실패하는 단언을 약하게 바꾸거나 예외 케이스를 삭제하는 것이 구현을 고치는 것보다 쉽기 때문이다. 따라서 구현 단계에서는 테스트 변경을 기본적으로 금지하고, 테스트 자체가 잘못됐다고 판단되면 별도 승인 흐름으로 돌아가야 한다.

### 3.3 Refactor: 행동을 유지하며 구조를 개선한다

Green은 동작하는 코드를 만들지만 반드시 좋은 구조를 만들지는 않는다. Refactor 단계에서는 테스트가 계속 통과하는 상태에서 중복을 제거하고 이름을 개선하며 책임을 분리한다. 한 번에 큰 구조 변경을 하지 않고 작은 변경 뒤마다 테스트를 실행한다.

에이전트는 큰 리팩터링을 한꺼번에 제안하기 쉽다. 하니스는 변경 범위를 작게 유지하고, 각 단계에서 회귀 테스트를 실행하며, 실패하면 어느 작은 변경이 원인이었는지 되돌릴 수 있도록 체크포인트를 남겨야 한다.

## 4. BDD와 TDD가 만나는 실제 구조

BDD와 TDD의 관계를 하나의 테스트 파일로 단순화하면 오해가 생긴다. 바깥쪽 인수 테스트와 안쪽 단위 테스트는 서로 다른 해상도에서 같은 행동을 보호한다.

예를 들어 “공백뿐인 제목을 거부한다”라는 인수조건은 HTTP API 수준에서 `400 Bad Request`를 기대할 수 있다. 이 행동을 구현하기 위해 내부에는 제목을 정규화하고 검증하는 작은 함수가 필요할 수 있다. TDD에서는 이 함수의 행동을 빠른 단위 테스트로 안내한다.

```text
요구사항 R-02
  공백뿐인 제목으로 할 일을 생성할 수 없다
        ↓
BDD 인수조건 AC-02
  공백 제목 요청은 입력 오류를 반환한다
        ↓
인수/통합 테스트 AT-02
  POST /todos → 400
        ↓
단위 테스트 UT-02a
  normalizeTitle("   ") → error
        ↓
구현
  normalizeTitle + API 오류 매핑
```

이 연결에는 추적성이 필요하다. 요구사항과 인수조건에 식별자를 부여하고 테스트 이름이나 메타데이터에 연결하면, 어떤 요구가 테스트되지 않았는지와 어떤 테스트가 더 이상 유효한 요구를 가리키지 않는지 찾을 수 있다.

추적성을 문서 규칙에만 맡기면 에이전트가 새 테스트를 만들 때 연결을 빼먹을 수 있다. 하니스는 모든 인수조건에 테스트가 있는지, 테스트가 존재하는 인수조건을 참조하는지 자동 검사할 수 있다.

## 5. 왜 에이전트 하니스가 필요한가

하니스는 모델을 둘러싼 실행 환경이다. 어떤 파일과 도구를 사용할 수 있는지, 작업 상태를 어디에 기록하는지, 실패했을 때 무엇을 다시 시도하는지, 언제 작업이 완료됐다고 볼 수 있는지를 모델 바깥에서 정의한다.

TDD 하니스에는 적어도 네 가지 기능이 필요하다.

첫째, 역할과 권한을 분리해야 한다. BDD 분석 역할은 인수조건을 만들지만 구현을 바꾸지 않는다. 테스트 작성 역할은 테스트를 만들지만 프로덕션 코드를 작성하지 않는다. 구현 역할은 소스 코드를 바꿀 수 있지만 승인 없이 테스트나 인수조건을 바꾸지 못한다. 리뷰 역할은 이 연결과 실행 증거를 독립적으로 검사한다.

둘째, 상태를 외부화해야 한다. 현재 어느 인수조건을 다루는지, Red를 확인했는지, Green이 됐는지, 전체 회귀 테스트가 통과했는지를 파일이나 구조화된 상태로 남긴다. 세션이 끊기거나 다른 에이전트가 작업을 이어받아도 같은 상태에서 재개할 수 있어야 한다.

셋째, 피드백을 계층화해야 한다. 작은 변경마다 전체 E2E 테스트를 실행하면 느리고 비용이 커진다. 관련 단위 테스트, 관련 통합 테스트, 타입과 린트, 전체 회귀, 핵심 E2E 순으로 범위를 넓히면 빠른 피드백과 최종 안전성을 함께 얻을 수 있다.

넷째, 완료 조건을 기계적으로 검사해야 한다. 에이전트가 “작업을 완료했습니다”라고 말하는 것은 증거가 아니다. 모든 인수조건 매핑, Red 증거, 관련 테스트와 전체 회귀 통과, 테스트 약화 없음 같은 조건이 충족되지 않으면 완료 상태로 넘어가지 못하게 해야 한다.

## 6. 프롬프트만으로 부족한 이유

“반드시 TDD로 구현하고 테스트를 수정하지 마”라는 프롬프트는 도움이 된다. 하지만 다음 문제를 해결하지 못한다.

- 에이전트가 실제로 테스트를 먼저 실행했는지 확인할 방법이 없다.
- 어떤 기존 테스트가 변경의 영향을 받는지 알려주지 않는다.
- 구현 에이전트가 테스트 파일을 수정하는 것을 기술적으로 막지 않는다.
- 테스트 실패 상태에서 작업 완료를 선언해도 외부에서 차단하지 않는다.
- 세션이 끊긴 뒤 어느 단계였는지 보존하지 않는다.

2026년 공개된 TDAD 사전 연구는 이 차이에 관한 흥미로운 실험 결과를 보고한다. 연구에 사용된 제한된 로컬 모델과 SWE-bench 표본에서는 TDD 절차 지시만 추가했을 때 회귀가 오히려 늘었고, 코드와 테스트의 영향 관계를 제공했을 때 회귀가 감소했다. 이 결과를 모든 모델과 프로젝트에 일반화할 수는 없다. 그러나 교육적으로는 중요한 질문을 제기한다. 에이전트에게 “어떻게 일하라”고 말하는 것보다 “무엇이 영향을 받으며 무엇을 검증해야 하는지”를 실행 가능한 형태로 제공하는 것이 더 중요할 수 있다는 점이다.

## 7. 하니스 자체도 테스트해야 한다

품질 게이트 Hook 파일이 존재하고 설정에 등록돼 있다는 사실만으로는 실제 차단을 보장하지 못한다. 이벤트가 기대하는 JSON 응답 형식이 틀리거나, wrapper가 실패 exit code를 덮어쓰거나, 검사 시간이 timeout을 넘으면 Hook이 조용히 무시될 수 있다.

따라서 하니스에는 하니스 자체의 contract test가 필요하다. 예를 들면 다음과 같다.

```gherkin
Scenario: 실패 테스트가 있는 상태에서 완료 차단
  Given 프로젝트에 실패하는 테스트가 있고
  When 에이전트가 작업 완료를 선언하면
  Then 완료 Hook은 상태 전이를 차단하고
  And 실패한 테스트 이름을 이유로 반환한다
```

이 테스트는 Hook 스크립트가 존재하는지를 보는 정적 검사가 아니다. 실제 이벤트 입력을 전달하고 반환값과 프로세스 종료 상태를 확인하는 동적 검사다. 일부러 잘못된 응답, 긴 실행 시간과 누락된 설정을 주입해 fail-open 여부도 확인해야 한다.

## 8. 신규 기능과 레거시 코드의 차이

TDD는 원하는 새 행동을 먼저 테스트할 때 가장 자연스럽다. 반면 테스트가 거의 없는 기존 코드를 바로 리팩터하면 무엇을 깨뜨렸는지 알기 어렵다. 이런 경우에는 현재 동작을 관찰해 characterization test로 고정한 뒤 구조를 개선한다.

Characterization test에는 위험도 있다. 현재 코드에 버그가 있으면 그 버그까지 “현재 행동”으로 고정할 수 있다. 따라서 관찰된 현재 행동과 비즈니스가 원하는 행동을 구분해야 한다. 현재 행동을 보존할 것인지 수정할 것인지는 사람이 승인하고, 수정이 필요한 행동은 별도의 실패 테스트로 전환한다.

결국 하니스는 상황을 판단해야 한다.

- 신규 행동이면 BDD 예제에서 TDD로 시작한다.
- 테스트가 충분한 기존 시스템이면 영향 테스트를 확인하고 변경 TDD를 수행한다.
- 테스트가 거의 없는 레거시면 현재 행동을 먼저 보존한다.

## 맺음말

BDD, TDD와 하니스는 각각 독립된 유행어가 아니다. 세 가지는 요구를 구현으로 바꾸는 과정에서 서로 다른 실패를 막는다. BDD는 잘못된 것을 만드는 위험을 줄이고, TDD는 구현 범위와 설계를 빠른 피드백으로 안내하며, 하니스는 그 규율이 에이전트의 실제 행동과 완료 조건에 반영되게 한다.

좋은 TDD 하니스의 목적은 에이전트에게 더 많은 지시를 주는 것이 아니다. 에이전트가 무엇을 알고, 무엇을 바꿀 수 있으며, 어떤 증거를 남기고, 어떤 조건에서만 다음 단계로 이동할 수 있는지를 설계하는 것이다.
