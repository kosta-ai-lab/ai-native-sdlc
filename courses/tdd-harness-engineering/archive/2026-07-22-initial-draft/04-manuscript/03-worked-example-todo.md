# 할 일 생성 기능으로 보는 관통 사례

## 사례의 목적

이 문서는 BDD, TDD와 에이전트 하니스가 하나의 작은 기능 안에서 어떻게 연결되는지 처음부터 끝까지 보여준다. 대상 기능은 현재 저장소의 `samples/web-task-system`에 있는 “할 일 생성”이다. 기능은 작지만 요구의 모호함, 인수조건, 단위와 통합 테스트, 에이전트 역할 분리와 완료 게이트를 모두 설명할 수 있다.

여기서 목표는 완성 코드를 빠르게 얻는 것이 아니다. 각 단계에서 어떤 정보가 확정되고, 다음 단계가 무엇을 입력으로 받으며, 에이전트가 임의로 바꿀 수 없는 경계가 어디인지 확인하는 것이다.

## 1. 시작 요구

최초 요청은 다음 한 문장이라고 가정한다.

> 로그인한 사용자는 제목을 입력해 할 일을 생성할 수 있다.

이 문장만으로 구현을 시작하면 에이전트는 여러 결정을 대신 내리게 된다. 제목이 비어 있을 때의 처리, 공백 정규화, 생성자 기록과 오류 메시지 등이 정해지지 않았다. 따라서 구현 에이전트를 호출하기 전에 BDD Discovery를 수행한다.

## 2. Discovery 결과

분석 역할에게 구현을 허용하지 않고 규칙, 예제와 질문을 분리하게 한다.

### 확정된 규칙

- 로그인한 사용자만 할 일을 생성할 수 있다.
- 제목은 필수다.
- 제목 앞뒤 공백은 제거한다.
- 공백 제거 후 빈 문자열이면 거부한다.
- 생성된 할 일에는 생성자 ID를 기록한다.

### 구체적인 예제

- `"보고서 작성"`은 같은 제목으로 생성된다.
- `"  보고서 작성  "`은 `"보고서 작성"`으로 생성된다.
- `"   "`은 입력 오류다.
- 인증 정보가 없으면 권한 오류다.

### 아직 답하지 않은 질문

- 제목 최대 길이는 얼마인가?
- 같은 사용자가 동일 제목을 중복 생성할 수 있는가?
- 저장소 장애 시 사용자에게 어떤 오류를 보여줄 것인가?

답하지 않은 질문을 에이전트가 임의로 구현하지 않도록 이번 기능 범위 밖으로 명시한다. 이것이 과잉 구현을 막는 첫 번째 경계다.

## 3. 인수조건 작성

확정된 예제를 다음과 같이 정리한다.

```gherkin
Feature: 할 일 생성

  Scenario: AC-01 유효한 제목으로 생성
    Given 사용자 "user-01"이 로그인되어 있고
    When 제목 "보고서 작성"으로 할 일을 생성하면
    Then 제목 "보고서 작성"인 할 일이 생성되고
    And 생성자 ID는 "user-01"이다

  Scenario: AC-02 제목 앞뒤 공백 제거
    Given 사용자 "user-01"이 로그인되어 있고
    When 제목 "  보고서 작성  "으로 할 일을 생성하면
    Then 제목 "보고서 작성"인 할 일이 생성된다

  Scenario: AC-03 공백 제목 거부
    Given 사용자 "user-01"이 로그인되어 있고
    When 제목 "   "으로 할 일을 생성하면
    Then "제목은 필수입니다" 입력 오류가 반환된다

  Scenario: AC-04 비로그인 사용자 거부
    Given 사용자가 로그인하지 않았고
    When 제목 "보고서 작성"으로 할 일을 생성하면
    Then 인증 오류가 반환된다
```

각 시나리오에 ID를 붙인 이유는 나중에 테스트와 구현의 추적성을 검사하기 위해서다. 자연어 제목만으로도 사람이 읽을 수 있지만, 자동 검사에서는 안정적인 식별자가 유용하다.

## 4. 테스트 계층 결정

모든 시나리오를 브라우저 E2E로 구현할 필요는 없다. 빠른 피드백을 위해 행동을 가장 낮은 적절한 계층에 배치한다.

| 인수조건 | 단위 | 통합/API | E2E |
|----------|------|-----------|-----|
| AC-01 정상 생성 | 모델 생성 규칙 | 인증·저장·응답 | 핵심 사용자 여정 1건 |
| AC-02 공백 제거 | 제목 정규화 | 선택 | 불필요 |
| AC-03 빈 제목 거부 | 제목 검증 | 400 오류 매핑 | 불필요 |
| AC-04 비로그인 거부 | 불필요 | 인증 경계 | 선택 |

인수조건은 사용자 행동 수준에서 유지하지만 자동화는 빠르고 결정적인 테스트를 우선한다. E2E는 시스템 전체 배선을 확인할 가치가 있는 핵심 여정에 제한한다.

## 5. test-writer 역할 실행

test-writer는 인수조건과 테스트 파일만 읽고 쓸 수 있다. 프로덕션 소스를 수정할 수 없게 한다. 이 역할의 작업은 다음과 같다.

1. AC-01~AC-04에서 테스트 케이스를 도출한다.
2. 테스트 이름이나 태그에 AC ID를 남긴다.
3. 가장 작은 첫 행동 하나를 테스트로 작성한다.
4. 테스트를 실행한다.
5. 올바른 이유로 실패했는지 기록한다.

예를 들어 AC-03의 단위 테스트는 다음 형태가 될 수 있다.

```ts
it('AC-03: rejects a title containing only whitespace', () => {
  expect(() => createTodo('   ', 'user-01')).toThrow('제목은 필수입니다')
})
```

이 테스트를 실행했을 때 `createTodo`가 빈 제목 Todo를 반환해 실패한다면 의미 있는 Red다. 모듈을 찾지 못하거나 테스트 러너가 설치되지 않아 실패했다면 먼저 환경 문제를 해결하고 다시 실행해야 한다.

Red 증거에는 명령과 핵심 실패 결과를 남긴다.

```markdown
## AC-03 RED

- command: pnpm test -- --run test/todo.test.ts
- result: FAIL
- expected: throws "제목은 필수입니다"
- actual: returned Todo with empty title
- production change for AC-03: none
```

## 6. implementer 역할 실행

implementer는 인수조건과 테스트를 읽을 수 있지만 테스트 파일은 수정하지 못한다. 현재 Red를 Green으로 만드는 프로덕션 코드만 작성한다.

```ts
export function createTodo(rawTitle: string, userId: string): Todo {
  const title = rawTitle.trim()

  if (!title) {
    throw new Error('제목은 필수입니다')
  }

  return {
    id: crypto.randomUUID(),
    title,
    createdBy: userId,
  }
}
```

이 코드는 설명을 위한 예시다. 실제 저장소 모델과 필드명은 기존 명세를 따라야 한다. 중요한 것은 현재 테스트가 요구한 제목 정규화, 빈 제목 거부와 생성자 기록만 구현한다는 점이다. 최대 길이, 중복 금지 같은 미합의 기능은 넣지 않는다.

구현 뒤 관련 테스트를 즉시 실행한다. AC-03 테스트만 통과하고 기존 정상 생성 테스트가 깨졌다면 Green이 아니다. 관련 테스트와 현재 모듈 회귀 테스트가 모두 통과해야 한다.

## 7. 테스트 세탁 시도와 차단

구현이 어렵거나 테스트가 계속 실패하면 에이전트는 다음처럼 테스트를 약하게 바꿀 수 있다.

```diff
- expect(() => createTodo('   ', 'user-01')).toThrow('제목은 필수입니다')
+ expect(createTodo('   ', 'user-01')).toBeDefined()
```

수정된 테스트는 빈 제목을 허용하는 기존 구현도 통과시킨다. 테스트 파일이 존재하고 초록색 결과가 나오지만 인수조건은 검증되지 않는다. 이것이 테스트 세탁이다.

하니스는 implementer의 테스트 파일 변경을 기본 차단한다. 테스트가 정말 잘못됐다고 판단하면 구현 역할이 직접 고치지 않고 blocker를 반환한다. test-writer나 사람이 인수조건과 비교해 수정 여부를 승인하고, 수정된 테스트의 Red를 다시 확인한다.

## 8. 추적성 게이트

다음과 같은 작은 상태 파일을 둘 수 있다.

```json
{
  "R-01": {
    "acceptance": ["AC-01", "AC-02", "AC-03", "AC-04"],
    "tests": {
      "AC-01": ["test/todo.test.ts#creates-valid-todo"],
      "AC-02": ["test/todo.test.ts#trims-title"],
      "AC-03": ["test/todo.test.ts#rejects-blank-title"],
      "AC-04": ["test/todo-api.test.ts#rejects-anonymous-user"]
    }
  }
}
```

완료 게이트는 모든 AC에 적어도 하나의 테스트가 있는지, 참조한 테스트 파일과 케이스가 실제 존재하는지 확인한다. 테스트를 삭제하거나 이름을 바꾸면서 매핑을 갱신하지 않으면 완료를 차단한다.

이 매핑만으로 테스트 내용이 올바르다고 보장할 수는 없다. 그래서 reviewer는 테스트의 단언이 인수조건의 입력과 결과를 실제로 검증하는지도 확인한다.

## 9. 완료 Hook

에이전트가 작업을 끝내려 할 때 다음 조건을 검사한다.

```text
모든 AC가 테스트에 매핑됨
AND 각 신규 행동에 유효한 Red 증거가 있음
AND 관련 테스트 통과
AND 전체 회귀 테스트 통과
AND 타입 검사와 린트 통과
AND 승인되지 않은 테스트 변경 없음
```

조건이 하나라도 실패하면 Hook은 완료를 차단하고 구체적인 이유를 반환한다. “품질 기준 미달”처럼 추상적으로 말하지 않고 실패한 테스트, 누락된 AC나 변경된 테스트 파일을 알려줘야 에이전트가 다음 행동을 결정할 수 있다.

## 10. 하니스 자체 실패 주입

완료 Hook을 만든 뒤 정상 성공만 확인해서는 안 된다. 다음 실패를 일부러 만든다.

1. 테스트를 실패 상태로 둔다.
2. AC-04 매핑을 삭제한다.
3. implementer가 테스트 파일을 수정하게 한다.
4. Hook 응답 JSON의 필드명을 틀리게 만든다.
5. 검사 명령이 timeout보다 오래 걸리게 한다.

각 상황에서 실제로 완료가 차단되는지 확인한다. 1~3은 애플리케이션 품질 조건을 시험하고, 4~5는 하니스 계약과 운영 조건을 시험한다. 정적 설정 검사에서는 4~5를 놓칠 수 있으므로 실제 이벤트를 사용하는 contract test가 필요하다.

## 11. 레거시 변형 사례

이미 `createTodo`가 운영 중이고 테스트가 없다고 가정하자. 현재 코드는 제목 앞뒤 공백을 보존하고 있을 수 있다. 바로 `trim()`을 추가하면 기존 사용자나 외부 연동이 기대하던 행동을 바꿀 수 있다.

이때는 먼저 다양한 입력에 대한 현재 출력을 관찰하고 characterization test로 고정한다. 그다음 공백 제거가 버그 수정인지 새로운 요구인지 사람과 합의한다. 행동을 변경하기로 했다면 기존 characterization test를 몰래 고치지 않고 새로운 원하는 행동의 실패 테스트를 만들고 TDD 사이클로 전환한다.

이 사례는 “기존 코드에는 테스트를 나중에 붙이면 된다”는 단순한 이야기가 아니다. 현재 행동 보존과 원하는 행동 변경 사이에 승인 경계를 만드는 과정이다.

## 12. 실습 종료 후 남아야 할 것

수강생에게 최종 소스 코드만 남으면 이 과정의 목적을 달성하지 못한 것이다. 다음 자산이 함께 남아야 한다.

- 합의된 BDD 예제와 미결 질문
- 요구–인수조건–테스트 추적표
- 유효한 Red 실행 증거
- 테스트와 최소 구현
- 역할별 권한 또는 작업 범위 정의
- 완료 품질 게이트
- 하니스 실패 주입 결과
- 신규 TDD와 레거시 workflow 선택 근거

이 자산들은 한 번의 실습 결과가 아니라 다음 기능에도 재사용할 개발 환경의 일부다.

## 맺음말

작은 “할 일 생성” 기능에서도 요구를 합의하고, 테스트 계층을 고르고, Red의 의미를 확인하며, 테스트 변경 권한과 완료 조건을 설계해야 한다. 기능이 커질수록 이 과정의 필요성은 더 커진다.

에이전트 하니스는 개발자를 대신해 정답을 정하지 않는다. 대신 사람이 합의한 정답이 실행 가능한 테스트로 이어지고, 에이전트가 그 경계를 지키며, 위반이 발생했을 때 즉시 관찰할 수 있도록 만든다.
