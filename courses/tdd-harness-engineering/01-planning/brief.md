# 과정 Brief — TDD Harness Engineering

## 만들려는 이유

AI 코딩 에이전트가 테스트를 생성하거나 실행하는 것과 test-first 개발을 실제로 수행하는 것은 다르다. BDD로 합의한 행동을 테스트로 내리고, 올바른 Red와 최신 Green 증거를 판정하며, 실패 상태에서는 완료할 수 없는 실행 환경을 설계하는 과정이 필요하다.

## 잠정 대상

- 기본적인 소프트웨어 개발과 Git·터미널 사용 경험이 있는 실무 개발자
- 테스트를 작성해 본 적은 있어도 요구에서 테스트를 설계하거나 실패 이유를 판정하는 경험은 제한적인 개발자
- 테스트를 구현 후 첨부하거나 CI 통과를 위한 요식행위로 다뤄온 개발자
- AI 코딩 도구의 결과를 테스트·평가·Hook과 CI로 통제하려는 개발자·교육 담당자

프로그래밍 언어 기초와 테스트 프레임워크 문법 전체를 가르치는 입문 과정으로 만들지 않는다. 대신 테스트 경험이 적은 수강생도 따라올 수 있도록 좋은 테스트의 관찰 대상, 올바른 실패, 요구 추적과 회귀 판단은 기초부터 구체 사례로 다룬다.

## 기대하는 수행 변화

수강자는 “TDD로 구현하라”는 프롬프트를 작성하는 수준에서 벗어나, 명세·테스트·역할·실행 증거와 완료 게이트를 연결한 최소 하니스를 설계하고 실패 주입으로 검증한다.

## 잠정 학습 진행

과정은 기능 하나의 개발에서 시작한다. 수강자는 BDD로 원하는 행동을 구체화하고, TDD로 실패 테스트부터 구현하며, 기능·회귀·비기능 관점에서 어떤 평가가 필요한지 학습한다. 이후 이 경험을 일반화해 개발 하니스의 테스트 단계와 평가 단계를 설명하고 설계하며, 마지막에는 필요한 역할·증거·품질 게이트를 실제로 구성한다.

```text
기능 하나
→ BDD·TDD와 평가 경험
→ 필요한 평가의 종류와 판정 기준
→ 테스트·평가 단계의 하니스 원리
→ 최소 하니스 설계·구현
→ 실패 주입 검증
```

기능 구현은 최종 목적이 아니라 하니스가 필요한 이유와 효과를 관찰하는 관통 사례다.

## 교정하려는 기존 습관

- 구현을 끝낸 뒤 coverage를 채우기 위해 테스트를 추가한다.
- 테스트가 초록이면 무엇을 검증하는지 묻지 않는다.
- mock 호출 횟수처럼 구현 세부사항만 확인한다.
- 실패 테스트가 실행 오류인지 행동 부재인지 구분하지 않는다.
- AI가 생성한 테스트와 완료 보고를 독립적으로 검토하지 않는다.

과정은 테스트 코드의 존재보다 요구와의 연결, 결함 탐지력, 실행 증거와 상태 전이 통제를 품질 기준으로 삼는다.

## Test와 Evaluation의 경계

과정에서는 결정적 소프트웨어의 `Test`와 LLM 동작의 `Evaluation`을 명확히 분리한다.

| 구분 | 결정적 소프트웨어 Test | LLM 동작 Evaluation |
|---|---|---|
| 판정 대상 | 명확한 입력·출력, 상태 전이, 계약 | 의미적 품질, 유용성, 안전성, 선호와 일관성 |
| 판정 방식 | 정확한 assertion과 pass/fail | dataset, rubric, grader, score와 threshold |
| 반복성 | 같은 조건에서 같은 결과를 기대 | 표본·반복 실행에 따른 분포와 변동을 고려 |
| 대표 증거 | unit·integration·E2E 결과 | eval run, score breakdown, 실패 사례와 회귀 추세 |

LLM을 포함한 소프트웨어에서도 인증, 권한, 데이터 변환, tool contract와 상태 관리는 결정적 테스트로 검증한다. LLM 응답의 의미적 적합성에는 별도의 평가를 추가한다. Evaluation은 Test를 대체하지 않고, 실제 개발 하니스는 두 결과를 구분해 수집한 뒤 완료·배포 판단에서 결합한다.

## 용어 경계

이 과정에서 학습자가 설계·구축하는 것은 `개발 하니스`다. 명세, Test, LLM Evaluation, 권한, 실행 증거와 품질 gate를 AI 개발 workflow에 연결한다.

이 과정을 만드는 Planning·Research·Design·Manuscript·Materials·Deliveries workflow는 `과정 제작 하니스`다. 두 시스템은 증거와 상태 전이라는 원리를 공유하지만 목적과 산출물이 다르므로 활성 문서에서 구분해 표기한다.

## 현재 상태

과정은 `research-and-design` 상태다. 도구별 조사와 장문 원고 초안은 충분히 축적됐지만 표준 Unit 전체, 관통 실습과 시간별 납품 과정은 아직 확정되지 않았다.

## 아직 확정하지 않은 것

- 표준 과정의 기본 분량
- TypeScript와 Java 중 첫 실습 구현 언어
- BDD와 레거시 characterization test의 포함 깊이
- MoAI를 설치 실습으로 다룰지 구조 해부 사례로만 다룰지
- Claude Code 전용 Hook과 도구 중립적 CI gate의 비중
