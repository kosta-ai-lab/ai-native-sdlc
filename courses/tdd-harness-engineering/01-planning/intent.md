# TDD 과정 의도

이 문서는 TDD Harness Engineering 과정의 대상, 학습 내용과 수행 수준에 영향을 주는 의도를 기록한다. 과정 제작 방식에 관한 요구와 결정은 [`../harness/production-intent.md`](../harness/production-intent.md)에서 관리한다.

## Explicit — 사용자가 직접 밝힌 의도

| ID | 의도 | 설계 영향 | 출처 |
|---|---|---|---|
| CINT-001 | 개념 설명과 실제 사용 사례의 구체적 용법이 모두 필요하다 | 교재는 정의뿐 아니라 workflow·사례·한계를 포함 | 대화 |
| CINT-002 | 기능 하나를 중심으로 TDD·BDD와 필요한 평가를 먼저 학습한다 | 과정 앞부분은 구체적인 기능 개발과 평가 경험으로 구성 | 대화 |
| CINT-003 | 기능 수준에서 배운 테스트·평가 개념을 개발 하니스의 핵심 단계로 확장한다 | 미시적 개발 루프와 거시적 개발 하니스 workflow를 연결 | 대화 |
| CINT-004 | 수강자는 테스트·평가 단계를 설명할 수 있을 뿐 아니라 실제로 만들 수 있어야 한다 | 설명형 평가와 구현·실패 주입 평가를 모두 포함 | 대화 |
| CINT-005 | 수강생은 기본 개발 경험이 있지만 체계적인 테스트 경험은 부족할 수 있다 | 프로그래밍 기초는 생략하되 테스트 설계와 판정은 기초부터 다룸 | 대화 |
| CINT-006 | 기존 테스트가 품질 증거보다 요식행위로 사용되는 문제를 교정해야 한다 | 통과 여부보다 결함 탐지력·요구 연결·실패 이유를 평가 | 대화 |
| CINT-007 | 결정적 소프트웨어의 테스트와 LLM 소프트웨어의 평가를 명확히 구분한다 | Test와 Eval을 별도 개념·산출물·gate로 설계 | 대화 |
| CINT-008 | LLM의 확률적·의미적 동작에는 전통 테스트와 다른 평가 체계가 필요하다 | dataset·rubric·grader·반복 측정과 threshold를 별도 학습범위로 고려 | 대화 |
| CINT-009 | 강의 주제인 개발 하니스와 강의를 만드는 과정 제작 하니스를 혼동하지 않는다 | 과정 내용에서는 개발 하니스만 학습 대상으로 다룸 | 대화 |

## Inferred — 확인이 필요한 해석

| ID | 추론 | 근거 | 확인이 필요한 시점 |
|---|---|---|---|
| CINF-001 | 표준 과정은 도구 사용법보다 이전 가능한 개발 하니스 원리를 중심으로 해야 한다 | 기능 경험을 개발 하니스의 테스트·평가 단계로 확장하려는 의도 | Planning 종료 전 |
| CINF-002 | 첫 표준 과정은 8시간 안팎의 실습형 과정이 유력하다 | 기존 조사 문서의 권고 | Blueprint 승인 전 |
| CINF-003 | 과정은 구체 경험에서 원리화와 개발 하니스 구축으로 올라가는 나선형 진행이 적합하다 | 기능 하나부터 시작해 확장된 개념으로 설명·구현하려는 의도 | Blueprint 승인 전 |
| CINF-004 | 실제 AI 소프트웨어 개발 하니스는 결정적 코드 테스트와 LLM 평가 결과를 하나의 완료 판단으로 결합해야 한다 | Test와 Eval을 나누되 개발 하니스로 확장하려는 의도 | Blueprint 승인 전 |

## Assumed — 진행을 위한 임시 가정

| ID | 가정 | 잘못됐을 때의 영향 | 만료 시점 |
|---|---|---|---|
| CASM-001 | 첫 관통 예제는 Todo 생성 기능을 유지한다 | 사례·실습과 원고 일부 재설계 | Outline 확정 전 |
| CASM-002 | U-02 유효한 Red를 첫 세로 샘플로 사용한다 | 샘플 Unit과 fixture 교체 | 다음 샘플 선택 시 |
| CASM-003 | 수강생은 Git, 터미널과 한 언어의 기본 개발 workflow를 사용할 수 있다 | 선수학습과 실습 난이도 재설계 | 대상 프로파일 확정 시 |
