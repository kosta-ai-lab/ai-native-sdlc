# Intent Ledger

이 문서는 전체 대화를 보존하지 않는다. 이후 과정 설계에 실제로 영향을 주는 사용자의 의도, 확인이 필요한 추론, 임시 가정과 열린 결정을 기록한다.

## Explicit — 사용자가 직접 밝힌 의도

| ID | 의도 | 설계 영향 | 출처 |
|---|---|---|---|
| INT-001 | 개념 설명과 실제 사용 사례의 구체적 용법이 모두 필요하다 | 교재는 정의뿐 아니라 workflow·사례·한계를 포함 | 대화 |
| INT-002 | Markdown 문서는 앞뒤 맥락 없이 짧게 요약하지 않고 자세히 기술한다 | Manuscript를 자기완결적으로 작성 | 대화 |
| INT-003 | 사실과 의견을 구분하고 사실에는 각주·미주 형태의 출처를 사용한다 | 원고 인용 규칙과 정성 gate 적용 | 대화 |
| INT-004 | 정보와 지식을 구분한다 | Research를 inbox·wiki·synthesis로 구성 | 대화 |
| INT-005 | 거시 설계와 세부 설계를 분리한다 | blueprint와 Unit을 별도 산출물로 관리 | 대화 |
| INT-006 | 표준 과정과 기관별 요구 설계를 분리한다 | Design과 Deliveries를 분리 | 대화 |
| INT-007 | 폴더와 workflow는 복잡하지 않으면서 실제 작업 순서를 지원해야 한다 | 01~06 단계형 구조와 최소 하니스 채택 | 대화 |
| INT-008 | 하니스는 단계 gate뿐 아니라 질문과 유도장치로 사용자의 의도를 읽어야 한다 | 단계별 facilitation loop와 사용자 확인 필요 | 대화 |
| INT-009 | 기능 하나를 중심으로 TDD·BDD와 필요한 평가를 먼저 학습한다 | 과정 앞부분은 구체적인 기능 개발과 평가 경험으로 구성 | 대화 |
| INT-010 | 기능 수준에서 배운 테스트·평가 개념을 개발 하니스의 핵심 단계로 확장한다 | 미시적 개발 루프와 거시적 하니스 workflow를 연결 | 대화 |
| INT-011 | 수강자는 테스트·평가 단계를 설명할 수 있을 뿐 아니라 실제로 만들 수 있어야 한다 | 설명형 평가와 구현·실패 주입 평가를 모두 포함 | 대화 |
| INT-012 | 수강생은 기본 개발 경험이 있지만 체계적인 테스트 경험은 부족할 수 있다 | 프로그래밍 기초는 생략하되 테스트 설계와 판정은 기초부터 다룸 | 대화 |
| INT-013 | 기존 테스트가 품질 증거보다 요식행위로 사용되는 문제를 교정해야 한다 | 통과 여부보다 결함 탐지력·요구 연결·실패 이유를 평가 | 대화 |
| INT-014 | 결정적 소프트웨어의 테스트와 LLM 소프트웨어의 평가를 명확히 구분한다 | Test와 Eval을 별도 개념·산출물·gate로 설계 | 대화 |
| INT-015 | LLM의 확률적·의미적 동작에는 전통 테스트와 다른 평가 체계가 새로 필요하다 | 데이터셋·루브릭·grader·반복 측정과 임계값을 별도 학습범위로 고려 | 대화 |
| INT-016 | 강의 주제인 개발 하니스와 강의를 만드는 과정 제작 하니스를 혼동하지 않는다 | 모든 활성 문서에서 두 용어와 목적·산출물을 명시적으로 분리 | 대화 |
| INT-017 | 기존 문서는 삭제하지 않고 아카이브한 뒤 새 과정에서 다시 정립한다 | 초기 Research·Design·Manuscript·Materials·Delivery를 읽기 전용 보존 | 대화 |

## Inferred — 확인이 필요한 해석

| ID | 추론 | 근거 | 확인이 필요한 시점 |
|---|---|---|---|
| INF-001 | 표준 과정은 도구 사용법보다 이전 가능한 하니스 원리를 중심으로 해야 한다 | 기능 경험을 하니스의 테스트·평가 단계로 확장하려는 의도 | Planning 종료 전 |
| INF-002 | 첫 표준 과정은 8시간 안팎의 실습형 과정이 유력하다 | 기존 조사 문서의 권고 | Blueprint 승인 전 |
| INF-003 | 장문 교재를 먼저 만들고 슬라이드는 그 투영으로 만들려 한다 | 사용자가 설명한 저작 workflow | Manuscript 시작 전 |
| INF-004 | 과정은 구체 경험에서 원리화와 하니스 구축으로 올라가는 나선형 진행이 적합하다 | 기능 하나부터 시작해 확장된 개념으로 설명·구현하려는 의도 | Blueprint 승인 전 |
| INF-005 | 실제 AI 소프트웨어 하니스는 결정적 코드 테스트와 LLM 평가 결과를 하나의 완료 판단으로 결합해야 한다 | Test와 Eval을 명확히 나누되 개발 하니스로 확장하려는 의도 | Blueprint 승인 전 |

## Assumed — 진행을 위한 임시 가정

| ID | 가정 | 잘못됐을 때의 영향 | 만료 시점 |
|---|---|---|---|
| ASM-001 | 첫 관통 예제는 Todo 생성 기능을 유지한다 | 사례·실습과 원고 일부 재설계 | Outline 확정 전 |
| ASM-002 | U-02 유효한 Red를 첫 세로 샘플로 사용한다 | 샘플 Unit과 하니스 fixture 교체 | 다음 샘플 선택 시 |
| ASM-003 | 수강생은 Git, 터미널과 한 언어의 기본 개발 workflow를 사용할 수 있다 | 선수학습과 실습 난이도 재설계 | 대상 프로파일 확정 시 |
