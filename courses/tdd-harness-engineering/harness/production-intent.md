# 과정개발 하네스 의도

이 문서는 특정 TDD 학습 내용이 아니라, 과정을 조사·설계·저작·납품하는 방식에 대한 사용자의 의도와 운영 가정을 기록한다.

## Explicit — 사용자가 직접 밝힌 의도

| ID | 의도 | 하네스 영향 | 출처 |
|---|---|---|---|
| PINT-001 | Markdown 문서는 앞뒤 맥락 없이 짧게 요약하지 않고 자세히 기술한다 | Manuscript를 자기완결적으로 작성 | 대화 |
| PINT-002 | 사실과 의견을 구분하고 사실에는 각주·미주 형태의 출처를 사용한다 | 근거·인용 규칙과 정성 gate 적용 | 대화 |
| PINT-003 | 정보와 지식을 구분한다 | Research를 inbox·wiki·synthesis로 구성 | 대화 |
| PINT-004 | 거시 설계와 세부 설계를 분리한다 | blueprint와 Unit을 별도 산출물로 관리 | 대화 |
| PINT-005 | 표준 과정과 기관별 요구 설계를 분리한다 | Design과 Deliveries를 분리 | 대화 |
| PINT-006 | 폴더와 workflow는 복잡하지 않으면서 실제 작업 순서를 지원해야 한다 | 01~06 단계형 구조와 최소 하니스 채택 | 대화 |
| PINT-007 | 단계 gate뿐 아니라 질문과 유도장치로 사용자의 의도를 읽어야 한다 | facilitation loop와 사용자 확인을 전이 조건으로 사용 | 대화 |
| PINT-008 | 개발 하니스와 과정 제작 하니스를 혼동하지 않는다 | 규칙·상태·과정 산출물의 위치와 용어를 분리 | 대화 |
| PINT-009 | 기존 문서는 삭제하지 않고 아카이브한 뒤 새 과정에서 다시 정립한다 | 초기 자산을 읽기 전용으로 보존 | 대화 |

## Inferred — 확인이 필요한 해석

| ID | 추론 | 근거 | 확인이 필요한 시점 |
|---|---|---|---|
| PINF-001 | 장문 교재를 먼저 만들고 슬라이드는 그 투영으로 만든다 | 사용자가 설명한 저작 workflow | Manuscript 시작 전 |

## 적용 범위

이 기록은 현재 TDD 과정 안에서 인큐베이션한다. 서로 다른 과정 두 개 이상에서 같은 요구가 확인되기 전에는 저장소 공통 방법론이나 스킬로 확정하지 않는다.
