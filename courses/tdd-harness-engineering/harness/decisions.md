# 과정개발 하네스 결정 기록

## D-001 — 작업 단계형 폴더 사용

- 결정: `01-planning`부터 `06-deliveries`까지 실제 저작 흐름을 폴더에 반영한다.
- 이유: 완성 자산의 분류만으로는 현재 해야 할 작업과 다음 gate를 알기 어렵다.

## D-002 — 정보와 지식은 Research 안에서 구분

- 결정: 미가공 source note는 `inbox/`, 도구·개념별 정규화 정보는 `wiki/`, 여러 자료를 종합한 판단 모델은 `synthesis/`에 둔다.
- 이유: Evidence, Wiki와 Knowledge를 각각 최상위 폴더로 만들면 구조가 과도하게 복잡해진다.

## D-003 — 표준과 납품 설계 분리

- 결정: 기관 중립 설계는 `03-design`, 기관별 요구와 변형은 `06-deliveries`에서 관리한다.
- 이유: 특정 기술·시간 제약이 표준 과정의 학습성과를 조용히 바꾸는 것을 방지한다.

## D-004 — 교재를 시각 자료보다 먼저 작성

- 결정: 자기완결적인 `04-manuscript`를 먼저 검토하고, 슬라이드·실습·평가는 `05-materials`에서 파생한다.
- 이유: 슬라이드부터 만든 뒤 원고를 확장하면 지식의 깊이와 앞뒤 맥락이 부족해지기 쉽다.

## D-005 — 하니스 규칙 최소화

- 결정: 하니스는 출처, 지식 종합, 설계 정렬, 납품 변형과 실제 사용 가능성만 검사한다.
- 이유: 파일 수·슬라이드 수·고정 구성 같은 형식 규칙은 교육적 유용성을 직접 증명하지 못한다.

## D-006 — 두 하니스의 용어 분리

- 결정: 강의 내용은 `개발 하니스`, 강의 제작 시스템은 `과정 제작 하니스`로 부른다.
- 이유: 기존 초안에서 학습 대상과 저작 환경이 같은 `하니스`라는 단어로 표현돼 논의 층이 혼합됐다.
- 적용: 활성 문서에서는 수식어 없는 `하니스`를 피하고 `harness/terminology.md`를 운영 용어의 정본으로 사용한다.

## D-007 — 초기 자료의 무손실 아카이브

- 결정: 기존 Research·Design·Manuscript·Materials·Delivery는 `archive/2026-07-22-initial-draft/`에 당시 구조로 보존한다.
- 이유: 새 규격에 맞지 않는다고 삭제하면 조사와 원고 자산이 휘발되고 이후 판단 근거도 잃는다.
- 적용: 아카이브는 참고만 하며 활성 단계로 자동 승격하지 않는다.
