# 근거·인용 작성 규칙

## 목적

이 과정의 조사 문서는 도구 소개, 소스 분석과 교육 설계 의견을 함께 다룬다. 따라서 독자가 공식적으로 확인된 사실, 제작자의 자기 주장, 작성자의 분석과 과정 설계 제안을 구분할 수 있어야 한다. 각주는 사실의 출처를 추적하기 위한 장치이며, 사실과 의견의 구분 자체는 문장 표현과 문서 구조로 수행한다.

## 근거의 네 가지 유형

### 확인된 사실

공식 문서, 공개 저장소의 소스 또는 직접 실행 결과에서 확인한 내용이다. 중요한 사실 바로 뒤에 각주를 붙인다. 소스를 확인했다면 파일 경로, 기준 commit과 확인일을 각주에 기록한다.

```markdown
OpenSpec의 verify workflow는 구현을 세 차원으로 검토한다.[^openspec-verify]
```

### 프로젝트 측 주장

제작자가 설명한 효과나 품질 주장이다. 공식 출처가 있다는 사실과 주장 내용이 독립적으로 검증됐다는 것은 다르다. 본문에 주체와 검증 범위를 함께 쓴다.

```markdown
프로젝트는 이 구조가 신뢰성을 높인다고 설명한다.[^project-readme]
이번 조사에서는 해당 효과를 독립적으로 측정하지 않았다.
```

### 분석과 해석

확인된 사실이 TDD, BDD와 에이전트 하니스 관점에서 무엇을 의미하는지 해석한 내용이다. `분석`, `해석`과 같은 절에 배치하거나 “본 과정의 관점에서 보면”처럼 판단의 주체를 드러낸다. 분석 자체를 외부 사실처럼 표현하지 않는다.

### 교육 적용 제안

과정에서 무엇을 채택하고 보완할지 제안하는 내용이다. `교육 적용`, `권장 구성`과 같은 절로 분리한다. 도구의 기본 기능과 과정에서 추가할 장치를 혼동하지 않는다.

## 각주 사용 원칙

각주는 다음 내용에 사용한다.

- 공식 명령, workflow, 기본값과 상태 전이
- 템플릿이나 소스에 정의된 구체적인 규칙
- 버전, 날짜, 수치와 등급
- 제작자의 효과 주장
- 연구 결과와 외부 사례

일반적인 설명, 바로 앞의 사실에서 도출한 분석과 명시적인 과정 설계 제안에는 불필요하게 각주를 반복하지 않는다.

각주 ID는 문서 안에서 의미가 드러나게 작성한다.

```markdown
[^superpowers-tdd]
[^openspec-verify-archive]
[^speckit-tests-optional]
[^bmad-trace-gate]
```

## 각주 형식

```markdown
## 주석

[^source-id]: Fission-AI, OpenSpec,
    `src/core/templates/workflows/verify-change.ts`,
    commit `60f720c43acd94de7645ac8629c614ede4682b6a`,
    2026-07-22 확인.
    <https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts>
```

웹 문서처럼 commit을 고정할 수 없다면 문서 제목, URL과 확인일을 남긴다. 저장소 소스는 가능하면 `main` 링크와 함께 기준 commit을 기록한다.

## 문서 권장 구조

```text
조사 질문과 범위
→ 공식적으로 확인된 구조
→ 구체적인 workflow와 사례
→ 분석
→ 확인된 한계
→ 미확인 사항
→ 교육 적용 제안
→ 주석
```

모든 문서를 이 제목에 기계적으로 맞출 필요는 없지만, 공식 설명에서 작성자의 판단으로 넘어가는 경계는 독자가 알아볼 수 있어야 한다.

## 검토 체크리스트

- 강한 사실 주장에 인접한 각주가 있는가.
- 각주가 실제로 해당 문장을 뒷받침하는가.
- 프로젝트의 자기 주장을 객관적으로 검증된 효과처럼 쓰지 않았는가.
- 소스 파일의 존재와 런타임 동작 보장을 구분했는가.
- `강제한다`, `보장한다` 같은 표현의 강제 층을 명시했는가.
- 분석과 교육 제안의 주체가 드러나는가.
- 확인하지 않은 부분을 추측으로 채우지 않았는가.
- 각주의 commit 또는 확인일이 기록됐는가.
